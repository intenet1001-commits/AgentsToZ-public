# Community transport v2

This transport carries opaque device records. It neither launches a human Viewer nor enables capture/input.
The deployed issuer and native signed build remain the trust anchors; `/health`, DNS labels and relay ACKs cannot grant access.

## Native screen integration

`CommunityRelayMultiplexer.open(authority:context:ticketProvider:proofSigner:incoming:)` opens one outbound WSS connection.
`context` binds community, enrollment, device, exact public key, host/client role and optional mobile session.
The provider supplies a fresh issuer-verified `CommunityRelayTicket` for the supplied connection ID.
The proof closure signs only `CommunityRelayBindProof`. The initial challenge requires the corresponding private key.

- Desktop/mobile client tickets use `relay-ticket`. A mobile ticket uses its live RAM session key.
- A Screen host uses `receiver-ticket` and its own Screen host key. It cannot adopt a Viewer operation-key certificate as its private authority.
- `openChannel(to:)` creates a bounded virtual stream; `incoming` receives a new host stream for protocol-6 admission.
- `binding` exposes channel ID and both connection epochs. Protocol 6 verifies these, both issuer credentials, both device IDs, roles and ephemeral keys.
- `isClosed` is an async liveness getter. Restoring a closed receiver listener never resumes an old interactive session.
- Per-channel cancellation sends a close record. WebSocket termination forwards `peer-ended`; only streams bound to that exact peer connection close.
- A dropped multiplexer closes its native socket. No unknown record or command is automatically resent.

The native stream starts with a 16 KiB pre-authentication limit. Encrypted records can rise to 8 MiB + 25 bytes.
180,000-byte fragments stay below the relay's 262,144-byte JSON limit. Frame sequence, part index/count/length,
ten-second assembly deadline, eight-channel limit, aggregate partial-buffer limit and bounded ordered send queues constrain resources.
Large records are paced; ordinary control traffic and separate peers retain independent stream state.
Legacy phone protocol 4 and Mac protocol 5 are unchanged.

## JavaScript integration

`CommunityAccessClient` takes a pinned origin/issuer and an injected native typed-request signer.
The native signer returns its complete signed `{payload,signature}` envelope. The client verifies the intent and signature,
then dispatches those exact bytes, preserving native object-key ordering. No JavaScript private key is generated by this SDK.

`CommunityRelayClient` requires a native header-capable socket factory and a typed relay-proof signer.
The standard browser WebSocket API cannot provide the required Authorization header.
Control and media queues have separate budgets; explicit media coalescing does not discard control/key-up records.
Each peer has at most four in-flight records. Socket generation fences exclude callbacks from an earlier connection.

`sendRecord` accepts an opaque authenticated record, not plaintext. Its caller must perform the issuer-pinned,
peer/epoch/purpose-bound handshake and encryption. The JavaScript transport alone does not implement or claim E2EE.
`{stage:'forwarded',reachable}` proves routing only. The target's original request ID and durable execution receipt determine execution outcome.

## Reproducible isolated checks

From this repository, first install the separately locked Worker test dependency set:

```sh
cd cloud/screen-community
bun install --frozen-lockfile
bun tests/access-worker.mjs
```

From the repository root:

```sh
bun test ./tests/community-relay-sdk.test.ts
swift test --package-path native/screen-control --filter 'Community(ScreenRelaySocket|RelaySocket|RelayTransport)Checks'
```

The Worker harness runs actual workerd, SQLite Durable Objects and WebSockets on ephemeral loopback ports.
It refuses all outbound networking and uses generated software fixture keys. The native fixture uses a DEBUG-only
`ws://127.0.0.1:<ephemeral>/relay` seam; release builds always use the pinned authority's WSS endpoint.
The tests do not contact installed app ports, change TCC/Keychain, capture screens or inject input.

The checks cover ticket possession/single use, same-community host substitution, connection epochs, mobile session-key requirements,
class/key DTO spoofing, 8 MiB fragmentation, ordered frames, peer isolation, per-channel cancellation, socket EOF and expired-lease alarms.
Input/video payloads in these checks are synthetic bytes. They are not evidence of Mac1↔Mac3 real-screen operation,
iPad 5G connectivity, production TLS, native biometric UX or release input-origin gate completion.

The hibernating DO uses `acceptWebSocket`, serialized attachments and lease alarms, following
[Cloudflare's WebSocket hibernation contract](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).
The common registry remains responsible for fresh membership/session admission; application memory and business data stay in their existing stores.

## Agent and Teams control carrier

`AuthenticatedCommunityTransport` plugs into `AgentDialogueHost.controlTransport` for the four control send/inbox/result/respond operations.
Selecting this carrier never retries a failed operation through the Supabase mailbox. Existing dialogue records, endpoint discovery and current
community-membership reads still use their existing database contract; this is not a migration of every network operation.

The native component certificate binds both the CF device ID and the distinct AgentsToZ portal device ID. Each channel verifies current issuer
credentials, role-specific native signatures over the shared nineteen-field transcript and both HMAC key confirmations. Nonextractable ephemeral
ECDH/AES/HMAC keys live only in RAM; long-term component identity keys stay in the native broker. New encrypted requests enter the target's existing
dispatcher only after endpoint membership checks. Host-local receipts are AES-GCM encrypted using a domain-separated key derived from the existing
dialogue store key; neither that key nor the dialogue secret enters a relay frame.

The local encrypted ledger keeps at most 512 full rows / 16 MiB, plus 4,096 compact consumption records / 4 MiB; each encrypted row is at most 300,000 bytes.
It never evicts unresolved, unconsumed or legacy UUIDv4 receipts to make room. A full store explicitly refuses new work.
New opaque control IDs use UUIDv7, whose embedded timestamp must exactly equal the authenticated request's `createdAt`; the receiver admits them only
within the 30-second execution window (up to five seconds of future clock skew). A durable admission watermark prevents clock rollback from reopening old IDs.
Each peer admits eight outgoing operations. Channels and
partial assemblies are bounded to 32, with five-second fragment and eight-second handshake deadlines. Issuer lookups reuse a lease for at most five
seconds while native local-off/identity is rechecked. Receipt reads are throttled to once per second per original control ID, and large replies are
paced below the DO's control-byte budget. Receipt responses may be resent; execution requests are never automatically resent.

`control-result` consumption retains its existing meaning: the upper Host has received the returned result, not that a relay acknowledged delivery.
The sender first durably records consumption, then sends a separate encrypted `result-consumed` packet bound to the original ID, timestamp, digest,
endpoints, purpose and both certificate policies. Only this packet clears the receiver's full result. A `consumed-confirmed` reply permits the sender
to stop retrying that acknowledgement; lost acknowledgements survive restart and only the acknowledgement is resent. A durable round-robin scan retries at most sixteen records per RPC, so old offline peers cannot monopolize the retry batch. Compact records retain the routing
and authority binding until the ID's admission window ends. Unconfirmed sender acknowledgements remain retained. Expired compact records may then be
removed, because their time-bound IDs cannot be admitted again. An expired receipt reports `COMMUNITY_CONTROL_RECEIPT_EXPIRED` with an unknown outcome;
it is never permission to resubmit execution. Legacy UUIDv4 records remain available without automatic retirement.

Teams is a separate authenticated purpose. A trusted caller passes `transportPurpose:'teams'`; the receiving Host requires its
`trustedTeamsDispatcher`. An ordinary OPS body does not confer Teams authority. The Teams receiver remains responsible for strict DTO validation,
the human-selected registered-project allowlist, settled launch choices and its durable execution receipt.

Focused carrier checks:

```sh
bun test ./tests/community-control-ledger.test.ts ./tests/authenticated-community-transport.test.ts ./tests/agent-dialogue-host.test.ts ./tests/community-relay-sdk.test.ts
```

The actual workerd harness additionally sends an authenticated agent request and a paced 180 KB synthetic reply through the DO.
Its native-signing provider is an explicit software-key stand-in. The Host regression checks the real call/poll/respond/result methods,
response loss, encrypted target-ledger reopening, original request-ID preservation and zero database-mailbox fallback.

The carrier regression additionally completes and consumes 600 encrypted requests with an injected clock, restarts both endpoints mid-run, and checks consumption-ack loss, byte budgets, legacy receipt migration, stale-ID timestamp rewrapping and clock rollback. This is a software fixture, not real device operation.

## Mobile non-screen relay purposes

Mobile control-v2 uses `mobile-agent`, `mobile-teams`, `mobile-agent-settings` and `mobile-browser`.
They map respectively to `agent.communicate`, `teams.run`, `computer-use.agent-settings` and `computer-use.browser`.
Each alias admits a mobile `client` using its current shared episode key, and a desktop `host` using its distinct Control component key.
Desktop clients cannot mint alias tickets; mobile clients cannot mint bare `agent`/`teams`/`agent-settings`/`browser` tickets.
Existing mobile Screen and desktop non-screen ticket routes remain separate. Relay replacement/routing uses the exact purpose string,
so a mobile alias socket cannot replace the same desktop's v1 component socket or forward data into it.

`component-session` has actor = receiving desktop enrollment and exact args
`[communityId, wirePurposeAlias, mobileEnrollmentId, sessionId]`, signed by that desktop's Control component key.
It requires the desktop purpose capability, the source's current same-community mobile enrollment/revision, and the same capability
in the current mobile episode. Its issuer-signed reply has kind `session` and the existing shared-use-session payload; it does not add
an endpoint, a portal device ID, or any Plan/Authorization key field. Closing, replacing, revoking or idle-expiring the source episode
blocks fresh session verification and ticket admission. An already admitted opaque socket is still bounded by its existing short lease;
the end-to-end consumer must verify fresh authorization and must not interpret routing acknowledgement as execution.

The SDK exposes `CommunityMobileRelayPurpose`, `communityComponentSessionArgs(...)` and
`CommunityAccessReply.isVerified(...)`; the last checks the private verified-response WeakSet, so a prototype-shaped object is not a credential.
The four aliases retain the non-screen 65,536-byte outer JSON frame limit and existing byte/rate budgets.

The isolated Worker harness exercises all four alias paths with real workerd/SQLite/WebSockets and software fixture keys,
including a simultaneous legacy desktop socket, stolen-ticket proof refusal and replaced/closed mobile episode rejection.
These checks carry opaque synthetic records; native mobile control-v2 encryption, device UI and real mobile actions are separate checks.
