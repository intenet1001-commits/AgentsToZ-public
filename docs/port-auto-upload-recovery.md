# 포트 자동 업로드의 DB 복구

자동 업로드는 필수 Pull 조회와 영구 삭제 보호 스키마가 준비된 뒤 시작한다.
설치 앱은 로컬 파일 읽기와 별도로 API 시작을 최대 15초 기다린다. 준비 확인은
읽기 전용 health 조회이며, 성공해도 필수 Pull을 생략하거나 업로드 권한을 열지 않는다.
시작 대기 실패와 Supabase 인증·스키마 오류는 구분해서 표시한다.
스키마가 없으면 로컬 목록을 보존하고 업로드를 중단한다. 인증 실패와 DB 업데이트
필요 상태는 다르게 표시한다. 수동 Push 성공만으로 실패한 초기 Pull을 대신하지 않는다.

## 적용 순서

1. 현재 앱의 Supabase URL과 CLI가 연결한 프로젝트가 같은지 확인한다. 자격 증명은
   로그에 출력하지 않는다. `portmgr_ports`의 열·RLS·권한·트리거·행 수와
   `portmgr_is_member()`의 service-role 지원을 읽기 전용으로 검사한다.
2. 포트 원본과 관련 스키마를 접근 제한된 로컬 파일에 백업한다. 다른 단말의
   프로젝트를 지우거나 소유자를 바꾸지 않는다. 기존 fence가 있다면 operation
   receipt까지 백업하고, 이력을 초기화하지 않는다.
3. `bun run verify`의 `port-durable-fence-sql.test.ts`는 PGlite의 실제 PostgreSQL
   엔진에서 이전 스키마의 보존, 재적용, RPC, RLS/ACL, 충돌과 삭제 후 부활 차단을
   검증한다. 브라우저 smoke는 별도 API/앱 데이터와 가짜 DB 응답으로 검증한다.
4. 공유 DB의 모든 쓰기 클라이언트를 확인한다. Mac·Windows 앱과 개인 웹 포털이
   `714ccf030237e9b21b6a85b87cb6b498898e4932` 이후의 guarded RPC를 써야 한다.
   구버전은 전환 후 읽기·로컬 저장은 유지되지만 원격 쓰기는 거절된다. 구버전의
   직접 쓰기 권한을 복원하거나 RLS를 끄는 방법으로 우회하지 않는다.
5. 누락 열만 복구할 때는 `20260908030000_port_fence_prerequisites.sql`을 사용한다.
   기존 열의 값과 알 수 없는 생성 시각을 보존한다. fence가 처음 필요한 DB에는
   선행 열 복구를 포함한 `20260830020000_port_durable_fence.sql`이 필요하다.
   임의로 전체 미적용 마이그레이션을 한 번에 실행하지 않는다.
6. 운영 적용은 `BEGIN`, 짧은 `lock_timeout`, 제한된 `statement_timeout` 안에서
   실행한다. backfill과 trigger 설치를 다른 트랜잭션으로 나누지 않는다.
   동시 쓰기를 잠금으로 직렬화하고 적용 직전 읽은 원본 행과 변경 여부를 재확인한다.
   잠금·동시 변경·권한 오류가 있으면 전체를 롤백하고 원인을 먼저 해결한다.
7. 원본 필드 비교, 행 수, RLS/권한, active fence의 소유자·세대를 다시 확인한다.
   PostgREST schema cache 갱신 뒤, 승인된 설치 앱에서 실제 편집 → 자동 업로드 →
   DB readback을 검증한다. 준비가 안 된 단말의 대기 항목은 남긴다.

## 앱의 예약·복구 계약

- 카테고리·설명·메모를 포함한 실제 저장 내용이 바뀌면 3초 뒤 업로드한다.
- 실행 상태 polling, 화면 순서, 서버 generation 영수증은 재업로드 원인이 아니다.
- 느린 업로드 도중의 편집은 최신 상태 한 건으로 합쳐 순서대로 전송한다.
- 메모리 ID의 부가 조회가 실패하면 기존 원격 연결을 지우지 않는다.
- 오류가 나면 로컬 편집을 유지하고 중단 이유를 표시한다. 원격 CAS 충돌을
  강제 덮어쓰기로 해결하지 않는다. 초기 Pull 실패는 재시작 후 준비를 재검사한다.
- 초기 Pull의 준비 결과는 확인한 DB 연결과 기기 ID에만 적용한다. 설정 없이
  시작했거나 연결 대상을 바꾸면 이전 준비 결과를 재사용하지 않는다.
- 시작/Pull 시 업로드하는 프로젝트명·포트·경로·실행 명령·배포/GitHub 주소·즐겨찾기·
  카테고리·설명·별도 메모를 모두 비교한다. 알려진 값이 다르면 해당 로컬 행과 메모,
  원래 generation을 유지하고 도구 메뉴의 `프로젝트 정보 차이 보기`에서 비교한다.
  충돌 행에는 원격 worktree 마커 등 일부 필드만 합치거나 중복 폴더 정리를 적용하지 않는다.
- 충돌이 없는 행의 로컬 결측 값은 원격에서 채운다. 최신 원격 NULL은 기존 로컬 값을
  조용히 지우지 않으며, 선택적 텍스트의 빈 문자열과 NULL은 같은 지우기로 비교한다.
  프로젝트 편집과 상세 인라인 편집에서 지운 문자열은 빈 문자열, GitHub 주소는 빈 배열로
  저장한다. 이 명시적 지우기는 자동 Git 감지로 다시 채우지 않으며, Pull에서 원격의 이전
  값과 충돌하면 양쪽을 보존한다. 사용자가 누르는 GitHub 감지는 계속 이용할 수 있다.
  포트 번호를 지우면 기존 폴더 항목 표현인 `port: 0`을 저장하고 편집 화면에는 빈칸을
  표시한다. `0`과 원격 NULL은 모두 포트 없음이며, 실행 환경에 PORT=0을 전달하지 않는다.
  과거의 `port` 결측은 여전히 원격의 실제 포트 번호를 채울 수 있다. 새 스키마나 마커를
  추가한 것이 아니라 기존 빈 값과 폴더 항목 표현을 사용자 편집에도 유지하는 동작이다.
  과거 조회나 DB 복원으로 원격 generation이 더 낮아져도 로컬 generation을 내리지 않는다.
  fence RPC로 저장한 NULL 지우기는 세대가 전진한다. 전환 전 generation 0의 NULL은
  미지원 열의 결측과 구분할 이력이 없어 기존 로컬 값을 채우는 호환 동작을 유지한다.
- `memory_id`는 비교용 UI 필드가 아니라 검증된 로컬 기억 설정에서 연결한다.
  기존 부가 조회가 실패하면 원격 연결을 삭제하지 않는 별도 계약을 유지한다.
- 수동 Push도 같은 필드를 새로 조회해 알려진 충돌과 더 최신 원격 편집을 차단한다.
  같은 generation에서 사용자가 새로 편집한 정상 수동 업로드는 허용한다. 충돌은 이 기기
  또는 웹 포털에서 사용할 값으로 맞춘 뒤 재시작한다. 단순 Push/Pull만으로 승인하지 않는다.
- 공유 DB 전환과 실제 설치본 readback까지 끝나기 전에는 해당 VOC를 완료 처리하지 않는다.
