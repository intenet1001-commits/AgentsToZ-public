# 기기 간 OPS 작업 요청과 결과

다른 기기에 명시적으로 맡긴 작업은 호출한 에이전트의 종류와 관계없이 받는 기기의 OPS에서 처리한다.
양쪽 AgentsToZ가 같은 공유 운영 프로필의 커뮤니티에 참여하고, 받는 쪽에 등록 OPS 폴더와 사용할
AI CLI·AgentsToZ MCP 연결이 준비되어 있어야 한다. 이 기능이 포함된 앱과 MCP를 양쪽에서 사용한다. 기존 AI 대화에서 새 도구가 보이지 않으면 MCP를 재연결하거나 새 대화에서 확인한다.
기존 대화 메시지의 본문은 자동 실행하지 않는다.

## 호출하기

- 앱: 아젠투지 음성 도크 메뉴의 **OPS 열고 작업 맡기기 · 기기 이름** → 작업 작성 → 전송.
  받는 기기의 메인 창이 숨겨져 있어도 해당 앱의 OPS 워크룸을 별도 창으로 연다. 새 창이 차단되면 받는 기기의 본창 워크룸으로 연결하며 두 표시 결과를 구분한다. 결과는 작성기에 표시한다.
  **상대 워크룸 보기**로 기존 원격 워크룸 화면도 볼 수 있다.
- MCP: `agentstoz_use_list_ops_devices`에서 정확한 `endpointId`를 고르고,
  `agentstoz_use_submit_ops_request(endpointId, requestId, text)`로 접수한다.
  같은 `endpointId`·UUID `requestId`로 `agentstoz_use_wait_ops_request`를 반복하여 결과를 받고,
  중단 후에는 `agentstoz_use_get_ops_request_result`로 확인한다. Codex·Claude·Hermes·agy가 같은 도구를 쓴다.
- 로컬 OPS 음성: `list_ops_devices` → `prepare_remote_ops_instruction` → 기존 초안 확인·전송.
  같은 요청의 후속 결과를 기존 음성 관찰 경로로 읽는다. 필요하면 `read_remote_ops_request`로 조회한다.
  기존 휴대폰의 프로젝트별 음성 grant에는 다른 기기 실행 권한을 추가하지 않는다.

호출한 AI는 받는 쪽 AI를 지정하지 않는다. 수신 기기의 OPS AI 설정을 사용하며 별도 작업 세션을 연다.
사용 중인 대화나 승인 화면에 다른 작업 글을 끼워 넣지 않는다. CLI 로그인·신뢰·승인은 사용자가
상대 OPS 화면에서 처리한다. 다른 기기의 요청으로 권한 우회 모드를 켜지 않는다.

## 상태와 완료 기준

`queued → starting → running` 뒤 실제 결과 제출이 있어야 `completed`가 된다.
로그인·신뢰·승인 화면은 `needs-attention`, 명시적인 실패 결과는 `failed`, 시작 응답 유실·실행 중
앱 재시작·결과 제출 전 CLI 종료는 `unknown`이다. 접수, 창 열림, 조용한 터미널은 완료 근거가 아니다.

대화형 CLI는 차례가 끝나도 종료하지 않으므로, 결과를 제출하지 않고 멈춘 작업이 받는 기기의 대기열을
영원히 막지 않게 두 한도를 둔다(`src/opsRequestHost.ts`). 출력도 결과 제출도 없이 **10분**이 지나면
`needs-attention`(「OPS AI가 결과를 제출하지 않고 입력을 기다립니다」)이 되고, 출력이 다시 나오면
`running`으로 돌아간다. 마지막 출력(출력이 없으면 시작)부터 **60분**이 지나면 `unknown`으로 바꿔 다음
작업에 차례를 넘긴다. 어느 경우에도 워크룸을 **닫지 않고 다시 실행하지 않으며**, 늦게 제출된 결과는
`unknown`에서도 받는다(그 결과가 오면 끝난 워커처럼 15초 뒤 정리한다). 그래서 60분 뒤에도 그 CLI가 실제로
일하고 있었다면 다음 작업과 함께 두 OPS CLI가 동시에 돌 수 있다 — 자동 종료보다 이쪽을 골랐다. 출력이
계속 나오는 작업은 시간 제한이 없다.

- **신뢰·승인·y/n 화면에서 사람의 답을 기다리는 워커에는 60분 한도를 적용하지 않는다.** 그런 화면은 아무것도
  출력하지 않으므로, 한도를 적용하면 사람이 없는 밤 동안 대기 작업마다 CLI가 하나씩 열려 각자 같은 화면에서
  멈추고, 아침에 승인하면 한꺼번에 돈다. 그 워커는 `needs-attention`으로 대기열을 계속 잡고, 뒤의 작업은
  24시간이 지나면 실행하지 않고 실패로 남는다.
- **차례를 넘긴(`unknown`) 워커가 열린 채 2개면 다음 작업을 시작하지 않는다.** 그 CLI가 종료되거나, 늦은
  결과를 제출하거나, 사람이 그 워크룸에 입력해 이어 쓰면(그때부터 그 사람의 워크룸이다) 자리가 난다.
  대기 작업은 그동안에도 24시간 뒤에 만료된다.

수신 OPS의 첫 요청에는 작업별 결과 제출 capability를 전달한다. 수신 AI가 실제 수행 결과와 근거를
`agentstoz_use_complete_ops_request`로 제출하면 그 결과가 호출 측 대기 도구·앱·음성으로 돌아온다.
결과 제출 권한은 둘 중 하나다: ① capability, ② **그 작업의 워커 워크룸 세션 자신**에서 온 호출
(MCP 서버가 보내는 워크룸 호출자 정보 — 프로세스 조상·`AGENTSTOZ_WORKROOM_SESSION_ID` — 가 영수증의
세션과 같을 때). capability를 주면 그것이 맞아야 하고, 다른 워크룸 세션은 capability 없이 제출할 수 없다.
capability는 당분간 첫 요청에 그대로 남는다(호출자 정보를 보내지 못하는 경로를 위해). 그래서 워크룸
기록·원격 화면에 보일 수 있다는 점은 그대로다. 호출자 정보는 같은 프로필 토큰을 가진 로컬 프로세스가
흉내 낼 수 있는 힌트이고, 그 토큰은 이미 그 워크룸에 입력할 권한을 주므로 새 권한을 열지 않는다.
이것은 수신 AI가 제출한 수행 보고이며 모든 외부 효과를 독립적으로 검증했다는 뜻은 아니다.
capability는 원격 영수증에 포함하지 않고 대표적인 credential 형식도 결과에서 가린다.

호출 측이 끝난 AI 대화를 임의로 재시작하지 않는다. MCP 호출자는 결과 대기 도구를 사용하며,
앱 작성기는 열려 있는 동안 자동 조회한다. 브라우저에는 마지막 상대 endpoint와 요청 ID만 보존한다.
음성 후속 관찰은 기존 대화 수명과 관찰 상한을 따른다. 음성이 끝난 뒤에도 호스트 작업은 유지되고
같은 ID로 결과를 조회할 수 있다.

## 재연결·권한·자원

- 기존 커뮤니티 `control-send/inbox/result` 통로를 재사용하므로 새 Supabase 마이그레이션은 없다.
  전달 envelope의 인증된 호출 기기·endpoint만 사용한다. 본문의 기기 ID·경로·실행 AI·명령은 받지 않는다.
- 수신 장부의 소유는 공유 프로필·수신 기기·OPS 장기기억(memoryId)·인증된 호출 기기·요청 ID에 결속한다.
  OPS 폴더 경로와 등록 프로젝트 ID는 **넣지 않는다** — 폴더 이름 변경(`AgentsToZ-Control` → `AgentsToZ-OPS`)이나
  다시 연결로 바뀌어도 같은 요청 ID가 같은 작업을 가리키고 두 번 실행되지 않는다. 실행할 OPS 프로젝트와 AI는
  시작할 때의 바인딩에서 읽는다. 프로필·기기·장기기억이 바뀌면 다른 장부 범위가 되고, 옛 범위의 미완료
  작업은 한 번 정리한다(대기 중이면 `failed`, 진행 중이면 `unknown` — 다시 실행하지 않고 워커의 결과 제출은 받는다).
  호출 기기의 AI나 endpoint가 바뀌어도 현재 커뮤니티 권한을 통과하면 같은 결과를 찾는다.
  대기 작업을 시작할 때 원래 호출 endpoint의 현재 멤버십을 다시 확인한다.
- 접수 내용을 먼저 영속화하고 `starting`을 기록한 뒤 CLI를 시작한다. 같은 ID와 다른 내용은 거부한다.
  시작 이후 미확정 작업은 재시작·시간 초과로 자동 실행하지 않는다. 같은 ID로 상태부터 확인한다.
- CLI 시작·화면 읽기·호출 기기 멤버십 확인은 장부 잠금 **밖에서** 한다. 그 결과는 다시 잠근 뒤 행의 현재
  상태를 보고 적용한다(그 사이 결과가 제출됐으면 덮지 않는다). 느린 CLI 시작이 다른 기기의 접수·상태
  조회를 줄 세우지 않게 하기 위해서다(보내는 쪽 대기 예산은 8~20초).
- **받는 쪽 OPS 워커 세션 자신은 받은 작업을 또 다른 기기로 넘길 수 없다**(`OPS_REQUEST_FORWARD_DENIED`).
  호출한 워크룸 세션이 아직 끝나지 않은(대기·시작·처리 중·확인 필요·`unknown`) 작업의 워커 세션이면 접수를
  거절한다 — 워커가 받은 작업을 그대로 되넘기는 A→B→A 왕복이 실수로 일어나지 않게 하는 **한 단계짜리
  권고 장치이지 보안 경계가 아니다.** 워커는 `agentstoz_use` 도구를 모두 가지므로 OPS 워크룸을 새로 열어 그
  세션이 접수하게 할 수 있고(한 단계 더 거친 전달), 호출자 정보를 알아내지 못하면(헤더 없음) 막지 않는다 —
  평범한 로컬 사용을 막지 않기 위해서다. 유료 AI 증폭을 실제로 묶는 것은 받는 쪽의 상한(바인딩마다 하나씩
  실행, 호출 기기당 대기 8건, 전체 32건)이다. 끝난 작업의 세션을 사람이 이어 쓰면 그 사람의 작업으로 보고 막지 않는다.
- 받기와 실행은 **설치된 앱의 사이드카에서만** 한다. `bun api-server.ts`·워크트리의 `API_PORT=…` 서버는 실제
  앱 데이터를 함께 쓰므로, `AGENTSTOZ_OPS_REQUESTS=1` 없이는 주기 실행(재시작 복구 포함)을 돌리지 않고 다른
  기기의 작업을 `OPS_REQUEST_DISABLED`로 거절한다(`opsRequestsAllowed`, OPS 폴더 이름 변경과 같은 규칙).
- `ops-requests.v1.sqlite`는 앱 데이터의 OS 보호 키로 AES-256-GCM 암호화하고 POSIX에서는 0600으로 연다.
  키 유실·변경 시 새 키로 기존 장부를 덮어쓰지 않는다. 작업 내용·결과·capability는 암호화 본문에 있다.
- 받는 기기 전체에서 미완료 32건, 그중 **호출 기기 하나당 8건**까지 받는다 — 한 기기가 모든 자리를 차지하지
  못한다. 내용이 남은 장부 행은 1,000건까지이고, 끝난 작업(완료·실패·`unknown`)은 접수 30일 뒤 **묘비**로
  줄인다: 작업 내용·capability·결과를 지우고 요청 정체성과 상태만 남겨, 같은 요청 ID가 와도 다시 실행하지
  않고 「보존 기간이 지나 정리했다」는 영수증을 돌려준다(같은 ID에 다른 내용은 여전히 거부한다). 묘비는
  10,000개를 넘으면 오래된 것부터 지우고, **지운 묘비의 요청 ID는 중복 방지를 잃는다** — 호출 AI가 그 ID를
  새 전달로 다시 보내면 새 작업으로 접수된다. 기기 간 제어 통로의 2분 제한은 전달(envelope)의 나이를
  제한할 뿐 요청 ID의 나이를 제한하지 않는다. 그 뒤로 묘비 10,000개가 쌓일 만큼 오래된 ID에만 해당한다.
  끝나지 않은 작업은 자동으로 지우지 않는다.
  24시간 안에 시작하지 못한 대기 요청은 실행하지 않고 실패로 남긴다.
- 작업은 OPS 바인딩마다 하나씩 시작한다. 완료한 전용 CLI는 15초 뒤 정리하되, 사용자가 입력을 이어
  쓴 세션은 유지한다. 결과와 기존 대화 기록은 유지한다. 빈 장부에서는 AI·키 저장소·DB를 호출하지 않는다.
  정리하는 워커는 **세션 종료 장기기억 저장을 하지 않는다**(`memoryPolicy:'skip'`) — 다른 기기에서 온 내용을
  검토 없이 OPS 장기기억에 쓰는 유료 저장이 작업마다 일어나지 않게 하기 위해서다. 기억이 필요하면 사람이
  그 워크룸에서 세션 기억하기를 한다. 세션이 기록되지 않은 작업(시작 응답 유실)은 정리할 워커가 없으므로
  정리 대기열을 막지 않는다.
- 앱이 완전히 종료됐거나 기기가 잠자기 상태면 이 기능만으로 OS를 깨우지 않는다. 전송 실패·미확정
  상태를 표시하고 같은 ID로 조회한다. 로컬 웹의 백그라운드 팝업이 차단되면 본창 워크룸을 사용한다.

## 검증 범위

`ops-request.test.ts`는 실제 암호화 SQLite와 재시작·중복·권한·수명·창 영수증을, 그리고 폴더 이동 뒤의 같은 정체성·
10분/60분 한도·승인 화면 대기 중의 대기열 유지·차례를 넘긴 워커 상한·느린 시작 중의 접수·30일 묘비·호출 기기당 상한·세션 없는 작업의 정리·기억 저장 없는 정리·
워커 세션의 결과 제출과 전달 금지·사이드카 한정을,
`ops-request-mcp.test.ts`는 네 종류 MCP 클라이언트의 실제 loopback HTTP 왕복과 인증 경계, 그리고 워커 워크룸에서
온 MCP 호출이 capability 없이 결과를 내고 다른 기기로 넘기지는 못하는 것을 검사한다.
음성 회귀는 초안 확인·같은 요청의 결과 관찰·휴대폰 권한 유지에 연결한다.
`tests/fixtures/ops-request-screen.ts`는 개인 API와 분리된 앱 작성기 화면 검사 서버이고,
`bun tests/ops-request-screen.e2e.mjs`가 그 서버를 직접 띄워 실제 작성기를 돈다(접수·결과·접수 전 거절 뒤 새 작업·
다시 열기·이 Mac에서의 거절·접수 시간 초과·받는 쪽 업데이트 필요·응답 유실·바이트 한도). 작성기는 같은 ID의 조회가
「찾지 못함」(`OPS_REQUEST_NOT_FOUND`) 또는 「받는 쪽 업데이트 필요」(`OPS_HOST_OUTDATED`)라고 답할 때만 새 작업(새 ID)을
연다 — 받는 쪽은 제어 요청을 차례로 처리하므로 거절된 접수 뒤에 보낸 조회가 그 접수를 놓치지 않는다. ⚠️ 「찾지 못함」은
받는 쪽 장부가 **지금의 OPS 연결 기준으로** 모른다는 뜻일 뿐이다(OPS 폴더를 옮기거나 앱 데이터를 잃으면 실행 중인 작업도
잊힌다). 그래서 화면은 「접수하지 않았다」고 단정하지 않고 상대 워크룸을 확인한 뒤 보내라고 말한다. 미확정 결과에서 새 ID로
자동 재전송하지 않는다. 받는 쪽 답의 코드: 원문만 오므로 위 둘과 함께, 받는 쪽 실행 마감·응답 크기 초과는
`OPS_REQUEST_OUTCOME_UNKNOWN`(같은 ID로 확인), 그 밖의 답은 중립 `OPS_REQUEST_FAILED`다 — 「거절」 코드는 두지 않는다.
글만으로는 접수 전이었다고 증명할 수 없어서, 그런 코드가 새 ID 재전송(= 중복 실행)을 부르기 때문이다.
이 격리 검사는 실제 두 기기 설치본과 유료 AI 계정의 왕복을 대체하지 않는다.

### 사용자 역할 검토 초안

기존 카탈로그의 커뮤니티 대화 탐색자·음성 사용자 외에 **기기 간 OPS 작업 요청자** 역할을 제안했다.
`personas propose`는 기존 후보 목록 상한(`Persona candidate budget reached`)으로 등록되지 않았으며
새 역할을 활성화하거나 기존 후보를 삭제하지 않았다. 아래는 이후 앱 검토용 초안이다.

- 이유·목표: 호출 AI와 상대 OPS AI가 달라도 작업 결과와 수행 근거를 받고, 전달과 완료를 구분한다.
- 시작 상황: 같은 공유 OPS 커뮤니티의 두 기기에서 서로 다른 AI를 사용한다.
- 여정: 정확한 상대 선택 → 명시적 작업 접수 → 상대 OPS 표시·상태 확인 → 연결 유실 시 같은 ID 조회 → 결과·근거 확인.
- 성공 기준: 상대 설정 AI 실행, 접수·창 열림과 완료 구분, 응답 유실·재시작 뒤 중복 실행 방지.
- 근거 파일: `src/opsRequestHost.ts`, `src/OpsRequestPanel.tsx`, `src/opsRequestMcp.ts`.
- 연결할 실제 검사: maintainer `ops-requests`. 초안은 활성 페르소나나 페르소나 PASS가 아니다.
