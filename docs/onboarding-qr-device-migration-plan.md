# 공통 모바일 웹앱과 기존 단말 전환 계획

작성: 2026-09-07. 상태: 사용자와 합의한 제품 방향 및 구현 계획. 기존 환경 진입 화면과 설정 보호의 1차 구현을 로컬 소스에 추가했다. 현재 설치본이나 전체 전환 기능의 완료를 뜻하지 않는다.

후속 [상세 설계와 구현 순서](design/README.md)에 고객 Supabase gateway, 기기별 인증·QR, 저장·복구, 서명 배포와 단계별 모델 권유를 구체화했다. 이 문서는 제품 방향과 최초 1차 구현의 이력이며, 신규 계약과 착수 조건은 상세 설계를 따른다.

## 사용자 경험

배포된 Mac·Windows 앱을 받은 사용자가 자신의 Supabase를 연결하고, QR을 통해 공통 모바일 웹앱을 연결한다. 사용자는 개인 Vercel 가입·배포를 할 필요가 없다. 공통 HTTPS 모바일 웹앱과 등록 중계는 배포자가 운영하며, 개인 데이터는 각 사용자의 Supabase와 기존 프로젝트 로컬 기억에 보관한다. 개인 포털 직접 배포는 고급 선택 경로로 유지한다.

첫 단말은 계정·프로젝트 연결과 DB 구성, 인증 상태를 확인한다. 이후 새 단말에서는 ‘기존 계정에 기기 추가’를 선택하고, 소유자 권한이 확인된 기존 휴대폰 또는 데스크톱에서 등록을 승인한다. 휴대폰이 없거나 분실된 경우에는 기존 데스크톱 승인 또는 소유자 계정 재인증으로 복구한다.

GitHub 연결, 각 단말의 프로젝트 폴더, AI 로그인은 해당 기능의 설정 단계에서 다룬다. 다른 단말의 로그인 토큰이나 프로젝트 절대경로를 그대로 복사해 설정 완료로 표시하지 않는다.

## 현재 코드에서 확인한 출발점

- `src/SetupWizard.tsx`와 `src/onboardingHandoff.ts`: 추가 PC용 v3 연결 정보는 공개 Supabase URL·키·추천 이름을 전달한다. 새 PC가 새 ID를 만들고 로컬 Supabase 관리자 인증을 진행하는 구조다.
- `src/remote-control-portal-main.tsx`: 배포 시점의 `VITE_SUPABASE_URL`·`VITE_SUPABASE_ANON_KEY`에 연결한다. 공통 웹앱에서 사용자별 DB를 선택하는 동작은 추가 구현이 필요하다.
- `src/remoteControlRelayContract.ts` 등의 인터넷 QR: 현재의 원격제어 연결 승인이다. 이 승인을 새 단말 등록 권한으로 자동 승격하지 않는다.
- `src/remoteDeviceSql.ts`와 관련 마이그레이션: 클라우드 호스트의 별도 등록·credential·이전 신원 연결·기억 접근 관계가 존재한다. 이를 데스크톱 등록 행으로 대체하지 않는다.
- `src/portalDeviceIdentity.ts`: 데스크톱의 기존 신원과 웹의 조회 선택은 구분된다. 앱 업그레이드가 단말 ID를 새로 발급하는 계기가 되어서는 안 된다.

## 기존 Mac 2대·Windows 1대·클라우드 1대의 전환

이 구성은 사용자가 제공한 운영 현황이다. 이번 계획 작성에서 네 단말의 실제 로그인·접속 상태나 동일 Supabase 사용 여부를 검증한 것은 아니다.

| 대상 | 유지할 항목 | 새 흐름에서 추가할 항목 |
|---|---|---|
| 기존 Mac A·B | 각각의 device ID, 로컬 프로젝트 경로, 프로젝트·기억 연결, 동기화 이력 | 소유자 확인 후 새 단말 인증 연결 |
| 기존 Windows | 기존 device ID, Windows 경로, 프로젝트·기억 연결, 동기화 이력 | 새 인증 연결과 Windows 실기기 검증 |
| 기존 클라우드 | 호스트 ID, 유효한 credential, 접근 가능한 memory ID와 계보 | 기존 에이전트의 호환성 확인 및 필요한 버전 갱신 |
| 모바일 | 검증된 기존 연결과 선택한 권한 | 공통 웹앱 연결 및 별도 소유자 승인 권한 |

전환은 다음 순서로 수행한다.

1. 각 단말의 실제 Supabase 프로젝트, 등록 ID, 앱/에이전트 버전, 마지막 동기화 상태를 읽기 전용으로 대조한다. 같은 이름만으로 동일 단말이라고 판단하지 않는다.
2. 각 단말의 설정과 로컬 기억을 복구 가능한 위치에 백업하고, 서버 스키마 버전과 호환 범위를 확인한다. 비밀값은 공개 문서나 진단 출력에 기록하지 않는다.
3. 기존 설정이 감지되면 ‘기존 환경 이어쓰기’를 제공한다. 새 Supabase 생성이나 기존 네 단말의 신규 등록을 기본 동작으로 삼지 않는다. 소유권 증명과 기존 ID 보존은 각각 검증한다.
4. Mac 한 대에서 먼저 전환한다. 신원·프로젝트 수·기억 ID/해시·북마크·동기화 cursor를 비교하고, 정상 동작을 확인한 뒤 다른 Mac·Windows·클라우드로 확대한다.
5. 실제 신규 단말에만 새 ID를 발급한다. 재설치로 기존 신원을 잃은 경우에는 검증된 이전 ID 연결 절차를 사용하고 이력을 재작성하지 않는다.

서로 다른 Supabase 프로젝트를 쓰고 있다면 별도 연결 공간으로 유지한다. DB, 계정, memory ID를 자동 합병하지 않는다. 오프라인 단말은 다음 접속 때 전환할 수 있어야 하며, 접속하지 않았다는 이유로 등록이나 기록을 삭제하지 않는다.

## 새 단말 QR 등록의 인증 경계

- 등록 전용 요청·권한·수명·폐기 경로를 원격제어와 구분한다. 등록 요청은 짧은 유효기간, 원자적 일회용 소비, 대상 단말 키에 대한 바인딩, 양쪽의 확인번호 검증을 갖는다.
- 새 PC가 아직 사용자의 Supabase 주소를 모르는 상태에서 승인 결과를 받을 수 있도록 초기 등록 중계가 필요하다. 공통 정적 웹 호스팅만으로 이 부분이 완성된다고 가정하지 않는다.
- 중계에 전달할 정보를 최소화하고, 소유권 확인 및 대상 단말 증명 전에는 DB 접근 권한을 발급하지 않는다. QR 원문·credential·사용자 콘텐츠를 로그로 남기지 않는다.
- 공유 웹앱은 연결 공간별 인증 저장소·클라이언트·캐시를 분리한다. 현재의 고정 인증 storage key와 장수 Supabase client cache를 그대로 다중 프로젝트에 적용하지 않는다.
- 기존 휴대폰의 원격조작 권한은 기기 추가 승인 권한이 아니다. 소유자 재인증을 거친 관리 단말에만 등록 승인을 허용한다.
- 모바일이나 QR에 Supabase 관리자 키를 넣지 않는다. 새 단말은 서버에서 검증·갱신·회수할 수 있는 전용 인증으로 필요한 데이터에만 접근한다.
- 기존 데스크톱의 관리자 키 직접 접근을 유지한 채 ‘단말 해제로 모든 접근이 차단된다’고 표시하지 않는다. 레거시 인증의 전환·회수, RLS/RPC 정책, 구버전 호환성을 함께 설계하고 실제 거부 응답으로 검증한다.
- 승인 직후 앱 종료, 네트워크 끊김, 중복 승인, 결과 저장 실패에서도 중복 단말을 만들지 않도록 claim과 로컬 저장 완료 확인을 나눈다.

## 모바일 기능

프로젝트·북마크·장기기억·What I Said를 공통 모바일 화면으로 구성한다. DB에 동기화된 정보의 조회와 실제 실행 호스트에 대한 명령을 구분한다.

- 프로젝트: 마지막 동기화 상태와 현재 호스트 응답을 구분해 표시한다. 실행·AI 요청은 지원되는 연결 권한 및 호스트 실행 준비 상태를 검증한다. Windows·클라우드의 모든 실행 기능이 Mac과 같다고 가정하지 않는다.
- 북마크: 조회·검색·편집·동기화와 실패 복구를 제공한다.
- 장기기억: 검증된 백업 조회·검색, 기억 후보 작성과 갱신 요청을 제공한다. 프로젝트 로컬 정본, 충돌 검사, 계보와 journal을 보존한다.
- What I Said: 기존 수집·동기화 opt-in, 제외 프로젝트, 민감정보 제거와 열람 권한을 유지한다. QR 연결이 전체 원문 공개 동의가 되어서는 안 된다.
- PWA: 설치 전후 저장소 차이, OAuth 복귀, 연결 복원, 로그아웃과 연결 해제를 검증한다. 원격 실행 요청은 중복 실행을 방지하며 앱이 숨겨져도 실행 호스트의 작업과 저장은 유지한다.

## 개발 저장소와 공개 검증 폴더

개발의 정본은 기존 `AgentsToZ_byCS` 폴더로 유지한다. 현재 `publish` remote와 `scripts/publish.ts`가 공개 스냅샷 배포를 담당한다. private 이력을 넘기지 않는 orphan 스냅샷, 파일 검사, 대상 저장소 검증 및 고정 refspec을 보존한다.

개발 프로젝트 내부의 `release/AgentsToZ-public/`은 공개 저장소에서 독립적으로 clone하여 일반 사용자 설치·문서·빌드 검증에 사용한다. 앱에는 기존 개발 프로젝트 하나만 등록하며 공개 검증 clone은 별도 프로젝트로 등록하지 않는다. 개발 폴더의 전체 복사나 같은 Git 이력을 공유하는 worktree로 공개 경계를 대신하지 않는다. 발견한 수정은 개발 정본에 반영한 뒤 공개 절차를 따른다.

AI 작업과 세션 기억은 상위 개발 프로젝트에서 진행하여 기존 기억을 함께 사용한다. 중첩된 독립 Git 저장소는 위치만으로 상위 기억을 자동 상속하지 않으므로, 검증 clone에서 별도 기억을 초기화하지 않는다. 상세 운영 기준은 `release/README.md`를 따른다.

장기기억 철학·기능을 추출한 독립 SDK 저장소는 `release/AgentsToZ-memory/`에 함께 둔다. 이 저장소 역시 별도 프로젝트로 등록하지 않고 개발 맥락은 상위 프로젝트에서 관리하되, SDK 자체 소스·검증·릴리스 이력은 독립 Git 저장소에서 보존한다. 실제 개인 기억의 백업 폴더로 사용하지 않는다.

공개 스냅샷은 배포마다 이력이 달라질 수 있으므로 검증 clone의 갱신도 원격 SHA와 로컬 변경을 확인한다. 실패한 fast-forward를 이유로 로컬 변경을 강제로 지우지 않는다. 개인 `.env`, `.agent-memory`, 앱 데이터, credential을 검증 폴더에 복사하지 않는다.

폴더 분리만으로 실행 데이터가 격리되지는 않는다. 현재 앱은 동일한 앱 데이터 경로와 로컬 API 포트를 사용한다. 최초 사용자 테스트는 별도 OS 사용자·VM 또는 검증된 데이터 경로 격리 환경에서 수행하고, 운영 중인 등록 정보에 테스트 데이터를 쓰지 않는다.

최초 별도 프로젝트로 등록했던 공개 검증 clone은 개발 프로젝트 내부로 통합하는 방식으로 변경한다. 개발 프로젝트의 기존 ID와 기억 정체성은 보존하고, 공개 검증 프로젝트의 별도 로컬 등록만 해제한다. 공개 clone의 파일·이력과 원격 저장소는 이 정리 작업으로 변경하지 않는다.

## 구현 순서와 완료 증거

1. **기존 환경 진단·전환 계약:** 기존 신원 보존, 프로젝트 선택, 백업, 변경 미리보기와 실패 복구를 구현한다.
2. **인증과 등록:** 사용자별 DB bootstrap, 로그인 redirect, 등록 중계, 전용 단말 인증 및 RLS/RPC·credential 전환을 구현한다. 현재 Supabase가 해당 승인 프로토콜을 자동 제공한다고 가정하지 않는다.
3. **공통 모바일과 QR:** 소유자 승인, 모바일 설치·재접속, 연결 공간 격리와 권한별 네 기능을 구현한다.
4. **통합 마법사·매뉴얼:** 최초 사용자, 기존 사용자, 추가 PC, 모바일, 클라우드 경로를 나눈다. 사용자용 Vercel 설정은 고급 개인 배포 문서로 이동하고 운영자용 공통 배포 문서를 제공한다.
5. **실제 배포 검증:** 기존 네 단말은 단계적으로 확인하고, 별도의 깨끗한 환경에서는 DMG/Windows 설치본만으로 시작하는 경로를 검증한다. 앱 서명·공증과 각 플랫폼의 지원 범위를 실제 산출물 기준으로 확인한다.

필수 검증은 다른 사용자의 QR/DB 접근 거부, 만료·재사용·중복 승인, 기존 ID 불변, 신규 ID 유일성, 재설치 계보, 인증 회수 후 접근 거부, 오프라인·구버전 복귀, Mac/Windows 경로 차이, 기존 기억·북마크·동기화 이력 보존이다. 기능 변경은 관련 회귀와 `bun run verify`를 통과시킨다. 아래 1차 구현의 검증이 전체 전환 검증의 완료를 뜻하지 않는다.

### Mac 우선 1차 구현 — 기존 환경 진입

`SetupWizard`에 기존 단말용 ‘기존 환경 이어쓰기’를 추가했다. 이 경로는 설정 완료 저장을 호출하지 않고 기존 앱으로 돌아간다. 현재 Supabase 응답, 로컬 연결 정보의 존재, 마지막 동기화 기록을 구분하며 상태 조회 실패 시 재시도할 수 있다. 조회는 화면 진입·수동 재시도에서만 실행하고 8초 제한과 unmount 취소를 둔다.

`onboardingEntryPolicy`는 확인 중·응답 오류·미지원 상태를 새 설치로 처리하지 않는다. 기존 단말에는 첫 등록 화면을 제공하지 않고 중단된 추가 등록에는 기존 재개 경로를 제공한다. 완료 직전에도 최신 로컬 설정을 읽어 이미 등록된 단말을 다시 저장하는 동작을 거부한다. 여러 프로세스의 모든 저장을 원자적으로 잠그는 DB 전환 기능은 아직 포함하지 않는다.

격리된 실제 React 화면에서 오류·미지원 상태·느린 응답·최초 사용·중단된 등록·부모가 확인한 기존 단말·오프라인·재시도 성공·재조회 실패·390px 화면의 10개 그룹을 검증했다. 테스트 API는 모두 대체했으며 저장 요청과 미지정 API 요청은 0건이었다. 이 결과는 실제 Supabase 인증·단말 전환 검증과 구분한다. 관련 정책 회귀 6개와 기존 온보딩 회귀 22개가 통과했고 frontend production 빌드가 성공했다.

최종 `bun run verify`는 TypeScript 오류 0, Bun 3,216 pass / 0 fail, Rust 54 pass로 완료했다. 화면 빌드에는 기존 대형 chunk 경고가 남아 있다. 125% 확대 화면도 육안으로 확인했다. 인증·설치와 수개월 자원 안정성의 실측 결과로 확대 해석하지 않는다.

실제 네 단말의 대조·백업·인증 전환, 신규 QR 등록과 공통 모바일 기능은 다음 단계로 남아 있다. Mac DMG의 앱스토어 외 배포는 [직접 배포 절차](macos-direct-distribution.md)를 따른다.
