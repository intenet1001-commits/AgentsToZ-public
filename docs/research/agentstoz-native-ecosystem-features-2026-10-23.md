# AgentsToZ 자체 생태계에 구현할 기능

- 작성일: 2026-10-23 (Asia/Seoul)
- 상태: 제품 기능 분석. 구현·성능 실측 전.
- 브랜치: `codex/ego-aside-analysis`
- 기준 소스: `3619c91bc90ef83dd3b1ce6888db7e24edb45f09`
- 범위: **ego-lite·Aside의 앱·CLI·MCP·계정·서비스 사용을 전제하지 않는다. 두 제품의 기능 원리를 AgentsToZ 자체 기능으로 설계한다.**
- 사용자 정정: 앞선 [외부 브라우저 연동 중심 분석](ego-aside-ecosystem-2026-10-23.md)은 요청을 잘못 해석했다. 이후 제품 제안의 기준은 이 문서다.

## 1. 가장 가치 있는 방향

**업무를 실행하고, 필요한 시점에 개입하고, 검증된 절차를 재사용·공유하는 기능을 AgentsToZ가 소유하는 것**이다.

우선 추천은 ① 필요한 현재 상태를 AI에 전달하는 작업 맥락 묶음, ② 등록된 도구를 한 절차로 조합하는 실행 묶음, ③ 성공한 절차를 재실행·공유하는 작업 팩과 개발 SDK다. 워크룸·장기기억·규격 명령·USE·테스터를 연결하면 기존 자산을 발전시킬 수 있다. 아래 제안은 독자 설계 판단이며 외부 제품에서 같은 기능을 가져다 실행한다는 뜻이 아니다.

## 2. 참고한 기능과 자체 적용안

ego의 Experience는 공식 문서상 coming soon·limited beta다. 완성 기능을 복제한다는 판단이 아니라 재사용 원리에서 착안한 자체 제안이다. Aside의 기억 관리가 실행 가능한 팩이나 자동 성능 향상을 보장한다는 뜻도 아니다.

Snapshot의 원래 대상은 브라우저 페이지다. 여기서는 그 원리를 프로젝트 상태에 적용한다. DOM·브라우저 엔진·외부 브라우저 로그인은 이 기능의 전제 조건이 아니다.

## 3. 실제 사용 모습과 기존 기능 대비 추가 가치

### A. 작업 맥락 묶음 — 반복 설명을 줄이는 작은 시작

사용자가 프로젝트에서 “지금 실패한 부분 고쳐줘”라고 요청하면 AI에 해당 프로젝트·워크트리의 최신 브랜치와 commit, 변경 요약, 최근 검사 결과, 실행 상태, 관련 기억의 제한된 발췌를 제공한다. 사용자는 전송할 내용을 확인할 수 있다.

기존의 기억 참고·프로젝트 선택·각종 상태 조회를 재사용하되, **같은 시점·같은 대상의 현재 상태를 모으는 계약**을 추가한다. 프로젝트 기억 전체를 매번 보내거나 다른 프로젝트 상태를 함께 넣지 않는다. 첫 버전은 요청 시 한 번 수집하고, 동일 내용 재전달과 변경분 전송은 실제 필요가 확인된 뒤 추가한다. 상태 수집을 위해 새 AI를 호출하지 않는다.

참고 기반: [DEV·USE 문맥](../dev-use-context.md), [Runtime SDK](../../packages/runtime-sdk/README.md), [프로젝트 기억](../../.agents/skills/project-memory/SKILL.md).

### B. 실행 가능한 작업 팩 — 자체 생태계의 재사용 단위

예: **“릴리즈 전 점검”** 팩에 대상 입력, 실행할 검사, 결과 정리, 필요한 확인, 완료 기준을 정의한다. 다른 프로젝트에서는 입력·프로젝트별 검사 설정을 바꿔 사용한다. **“자료 생성→음성 준비”**도 해당 제품의 허용된 도구로 같은 방식으로 구성할 수 있다.

규격 명령·스킬·테스터가 이미 있으므로 또 다른 프롬프트 보관함을 추가하지 않는다. 기존 규격 명령을 바탕으로 **입력 schema·도구 단계·권한·산출물·검사 근거·버전**을 가진 실행 규격을 마련한다. 팩 자체가 프로젝트 소속이라는 뜻은 아니며 실행 시 정확한 대상에 결속한다.

성공한 업무에서 팩의 초안을 제안하고 사용자가 검토·활성화한다. 한 번 성공하거나 AI가 좋다고 평가했다는 이유로 자동 공개하지 않는다. 기억 속 사실·교훈과 실행 코드는 별도로 관리한다.

### C. 공통 도구 규격과 SDK — 개발자가 기능을 추가하는 기반

제품 개발자가 `자료 생성`, `보고서 조회`, `테스트 실행`처럼 제한된 기능을 구현하면 Codex·Claude·Hermes 등에서 같은 정의로 사용하도록 한다. 팩 작성자는 그 도구를 조합하고, 사용자는 필요한 동작만 활성화한다.

현재 USE의 `scope → execute → receipt`, 요청 ID·권한 revision·결과 확인을 일반화할 기반으로 삼는다. **현재는 ShadowLoop 도구 6종과 설치 코드 등록 방식이므로 범용 SDK가 이미 완성된 것은 아니다.** Runtime SDK도 공개 제품 확장 SDK와 구분한다. [현재 제품 도구 연결](../service-use-integration.md), [`serviceUseProtocol.ts`](../../src/serviceUseProtocol.ts), [Runtime SDK](../../packages/runtime-sdk/README.md)

여러 조회를 한 요청으로 묶어 AI와 호스트 사이의 왕복을 줄이는 기능도 이 규격에 포함할 수 있다. 첫 버전은 등록된 도구의 타입 있는 단계 목록으로 구성한다. 임의 JavaScript·셸 실행기를 새로 노출할 필요는 없다. 독립 조회만 병렬화하고 의존 작업·쓰기·확인은 순서대로 처리하며, 각 단계의 권한과 부분 실패를 보존한다. 호출 수 감소가 전체 비용 감소를 보장하는지는 별도 측정한다.

### D. 작업 단위 공간과 결과 카드 — 기존 워크룸을 완성

예: “회원가입 오류 수정” 업무를 다시 열면 요청·사용한 워크트리·진행한 AI 세션·수정 파일·테스트 결과·남은 문제가 함께 보인다. 다른 업무와 자료가 섞이지 않고 Mac·승인된 모바일에서 같은 작업 위치를 찾을 수 있다.

**프로젝트별 워크룸과 공동 업무 스레드는 이미 있다.** 새 독립 작업 탭을 만들지 않고 기존 스레드에 산출물·검사 run·맥락 묶음·결과의 명시적 연결을 추가한다. 기존의 AI 결과 게시와 실제 검사 통과·파일 생성 증거를 구분한다. [현재 업무 스레드](../community-workspace.md)

### E. 사람이 수정하고 이어가기 — 동작 중인 AI를 다루기 쉽게

입력 옆에서 **“현재 작업 뒤에 처리”**와 **“진행 방향 수정”**을 구분한다. 예를 들어 “A 대신 B 형식으로 만들어줘”를 다음 요청으로 예약할지 현재 업무에 반영할지 선택한다. 추가 정보가 필요한 업무는 질문·현재 단계·이미 만든 결과를 남기고 원래 업무에서 이어간다.

기존 스레드의 `needs-answer`, 원래 request ID, 정확한 워크룸 session ID, 입력 revision과 submission receipt를 재사용한다. **질문 화면·승인 대응과 재접속 기록은 이미 있는 기반**이다. 새 부분은 사용자에게 명확한 입력 방식과 구조화된 다음 단계·산출물 연결이다. CLI마다 진행 중 입력 지원이 다르므로 미지원 환경에서는 대기열로 표시하고 즉시 수정했다고 주장하지 않는다. 네이티브 승인 화면에 일반 답변을 자동 Enter로 바꾸지 않는다. [현재 입력·승인 계약](../community-workspace.md#실행과-기록-계약)

### F. 예약·상태 변화 뒤 이어가기 — 반복 업무 확장

예: “평일 오전 9시에 프로젝트별 실패 검사 정리”, “이 테스트 run이 끝나면 결과를 읽고 같은 업무에 정리”다. 새 업무를 예약하는 방식과 기존 업무의 다음 단계를 재개하는 방식을 구분한다.

현재 카카오 대직은 질문 응답 전용이며 재시작 뒤 OFF다. **일반 스케줄러·CI 완료 감지·원래 업무 자동 재개는 신규 개발 범위**다. 대직의 동의·호출 예산·중복 방지 패턴을 참고할 수 있다. [현재 대직](../cs-duty.md)

상태 감지는 가능한 한 AI 없이 처리한다. 같은 작업의 중첩 실행을 막고, 원래 프로젝트·기기·권한·실행 상태가 확인될 때만 승인된 후속 단계를 수행한다. 결과 미확정은 재실행 대신 원래 영수증을 조회한다. 이 제안 자체가 예약·자동화 활성화 요청은 아니다.

## 4. 우선순위와 생태계가 형성되는 경로

상위 후보의 현행 구현과 차이는 소스로 교차 확인했다.

| 후보 | 현재 기반 | 신규 계약 |
|---|---|---|
| 작업 맥락 묶음 | [target inventory](../../src/agentRuntimeTargetInventory.ts), [세션 activity](../../src/aiTerminalActivity.ts), [검사 report](../../src/testerAgentContract.ts) | 프로젝트·워크트리 상태를 같은 수집 결과로 묶고 불완전·오래됨을 표시. 기존 activity cursor는 프로젝트 전체 snapshot/delta가 아님 |
| 도구 실행 묶음 | [USE operation](../../src/serviceUseProtocol.ts), [검사 operation](../../src/testerAgentContract.ts), [Push 준비·실행](../../src/platformGithubPush.ts) | 공통 단계 목록·의존 관계·단계별 receipt·제한된 병렬 조회·부분 실패·미확정 복구 |
| 작업 팩 | [텍스트 규격 명령](../../src/promptLibrary.ts), 기존 SDK·기억·테스터 | 입력·허용 동작·사람 확인·검사 근거·호환 버전·검토 후 배포를 묶는 실행 규격 |

도구 실행 묶음이 여러 제품의 쓰기를 하나의 원자적 transaction으로 보장하는 것은 아니다. 완료된 단계와 아직 실행하지 않은 단계, 미확정 단계를 나누어 보존한다.

| 단계 | 직접 구현할 것 | 완료를 판단할 기준 |
|---|---|---|
| 1 | 작업 맥락 묶음 + 읽기 도구 실행 묶음 + 기존 업무 스레드의 결과 카드 | 같은 대상의 현재 상태와 검사 근거를 한곳에서 확인하고 오연결·누락·부분 실패를 표시 |
| 2 | 기존 규격 명령 기반 작업 팩 + 검토된 도구 조합 | 대표 절차 하나를 서로 다른 두 프로젝트에서 입력·권한·검사 설정을 바꿔 실행 |
| 3 | USE 도구 규격 일반화 + 개발 SDK·적합성 검사 | 성격이 다른 두 제품이 동일한 등록·권한·중복 요청·영수증 계약을 충족 |
| 4 | 수정/대기 UX·예약/재개 + 검토된 팩 카탈로그 | 지원 여부·권한 변경·중복·업데이트·실패·재시작을 명시적으로 처리 |

생태계의 순환은 **개발자가 도구 제공 → 팩 작성자가 절차 구성 → 사용자가 선택·실행 → 테스터가 결과 확인 → 검토된 개선을 다음 버전에 반영**이다. AgentsToZ가 도구 정의·대상 해석·권한·실행 결과·검증·배포 규격을 소유한다.

일반 고객이 개발 소스·Git·DEV 기억 없이 설치된 제품 기능을 연결하려면 고객용 설치 identity 계약이 추가로 필요하다. [현재 설치 한계](../dev-use-context.md#제품-설치와-현재-한계)

## 5. 판단 범위와 검증

이 기능들은 ego-lite·Aside 실행 환경 없이 설계할 수 있다. 자체 브라우저 엔진도 전제하지 않는다. 웹페이지 조작이 필요한 제품 기능을 나중에 넣는다면 별도 웹 실행 도구가 필요하지만, 위 생태계 기반의 첫 구현과는 분리할 수 있다.

자체 구현이 기존 권한을 넓히지는 않는다. DEV·USE·OPS 기억·실행 역할을 유지하고, 채널 연결이 다른 프로젝트·기기 도구 권한을 주지 않는다. 외부 전송·설치·배포처럼 별도 확인이 필요한 단계는 팩에 포함되어도 기존 실행 경계를 따른다.

효율 향상은 아직 가설이다. 대표 업무에서 완료율·반복 설명 횟수·사용자 개입·왕복 호출·전체 시간·토큰·결과 확인 시간을 비교한다. 기억과 결과를 더 많이 쌓는 것만으로 효율 향상을 주장하지 않는다.

이번 변경은 분석 문서다. 앱 구현·스케줄 생성·외부 제품 설치·테스트 실행은 하지 않았다. 실제 구현에서는 기존 프로젝트 tester·정상 프로필·페르소나 계약을 따르고 기존 후보와 새 여정을 비교한다.
