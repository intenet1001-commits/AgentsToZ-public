# 2026-11-03 후속 통합: 공통 등록·관리 역할·검사 범위

이 문서는 `aab3a2e7` 이후의 구현 범위다. 아래 변경을 포함한 새 릴리스의 전체 검증·설치·실기 성공을 뜻하지 않는다. 현재 설치본은 두 Mac과 iPad의 2124이며, 후속 소스와 설치본을 혼동하지 않는다.

## 11-03 기기 신뢰 선택과 실제 판정

3호의 사람 라벨 키보드·포인터·iPad 입력 실측에서 PID/state/type이 충돌했다. 진단은 `ambiguous`, `certifiesCalibration:false`이며 기존 Mac 조작 관문은 유지한다. 사용자는 이 결과와 SR-23의 범위 차이를 설명받고 **「기기 신뢰로 변경 · Mac 재인증 최소화」**를 명시적으로 선택했다. 새 구현은 [기기 신뢰 계약](../../design/community-desktop-trust-2026-11-03.md)을 따르며, 양쪽 데스크톱의 별도 명시적 승인·현재 서명된 권한에서만 새 모드를 사용한다. 기존 등록·기능 전체 선택을 자동 승격하지 않는다. 이 선택은 자동 Screen ON·D2 복원·일반 시작 RPC·Computer Use 대상 확대의 승인이 아니다.

직전 `3f509197`에서 정상 12개와 추가 3개, 전체 16개 페르소나의 고유 근거 75개는 통과했다. 별도 전수 `bun run verify`는 Bun 10,605 pass / 12 skip / 4 timeout fail / 후속 오류 2로 실패해 Rust 단계에 도달하지 못했다. 같은 소스·원래 시간 제한의 파일별 분리 실행은 10개·6개 모두 통과했지만, 원래 전수 실패를 통과로 대체하지 않는다. 새 기기 신뢰 구현을 합친 최종 소스의 전수 검사는 다른 무거운 검사와 겹치지 않게 실행한다. 이 과거 수치로 후속 commit의 통과를 주장하지 않는다.

Native 구성요소 `4cf97d79`는 Swift 76개·Control 66개, 타입 검사·portal·unsigned iPhoneOS 컴파일을 통과했다. Cloudflare `457851fd`는 실제 workerd를 포함한 15파일 117개와 타입 검사를 통과했고 기존 11개 골든을 보존했다. 통합 브랜치에는 이 변경과 공통 검사 필터를 반영했다. 독립 리뷰에서 trusted ON의 이전 시도가 늦게 실패해 새 연결을 닫는 문제를 발견해 수정·재검증 중이며, 이 구성요소 수치를 최종 통합 통과로 바꾸지 않는다.

외부 앱 effort 연결은 별도 작업이다. 사용자 요청대로 Orca의 Claude Code 창을 열었고 실제 창에서 협업 인계문을 받아 읽기 시작한 것을 확인했다. 아직 native 앱 자동 변경·실제 readback 완료는 아니다. Codex 앱의 명시적 도구 접근 거부는 다른 에이전트로 우회하지 않는다. 사용자는 Teams 멤버의 질문을 메인 챗에서 답하고 그 답만 상대 질문에 적용·제출·확인하는 공통 흐름도 요청했다. 현재 경로를 조사하며, 자유 인계문을 선택 질문의 답변 칸에 넣은 이번 입력 문제와 구분해 개선한다.

## 유지하는 사용자 요구

- 커뮤니티에서 기기별 한 번의 명시적 등록으로 사용할 기능을 함께 선택한다.
- 등록된 데스크톱은 평상시 연결마다 앱 생체 인증을 반복하지 않는다.
- 모바일은 생체 인증 한 번으로 등록된 여러 Mac과 허용한 기능을 사용한다. 마지막 실제 사용 후 60분이 유휴 제한이며 heartbeat·영상 수신은 이를 연장하지 않는다.
- 기능 전체 선택이 관리 권한 추가를 뜻하지 않는다. 새 기기 승인·관리 역할 확대·복구는 별도 관리 행위다.
- 사용자가 선택하는 화면 연결과 AI Computer Use는 구분한다. HANDOFF §2 SR-23, 입력 출처 검증, 기기 폐기·원격 차단, OS 권한 경계를 유지한다.

## 이번 변경

1. Main의 커뮤니티 화면에 기기 등록·기능 승인 입구를 둔다. 채팅 대상이 없어도 보이며, 기존 인자 없는 Viewer 열기 경로만 사용한다. 모바일 웹에 Mac 도구 입구를 노출하거나 화면 세션을 자동 시작하지 않는다. 다른 경로의 실행본·갱신 대기·불명확한 helper 상태는 기존 거절을 유지한다.
2. Viewer와 iOS에서 등록 대기 목록을 위쪽에 표시하고, 목록 실패·빈 목록·관리 역할 없음·요청 만료를 구분한다. 갱신 중 이름·IME·확인 선택을 보존한다.
3. 모바일 관리 역할 변경은 기본값 `변경하지 않음`과 구분한 선택이다. issuer·community·원래 기기 키·정책 digest·기존/새 역할·revision·일회 challenge에 결속한 새 관리 서명 도메인을 쓴다. 정상 기능 승인과 관리 승인 요청을 서로 바꿔 쓸 수 없다.
4. v2 등록 알림은 승인 권한이 없는 별도 서명 notice다. 실제 관리 권한과 현재 subscription을 다시 확인하며, 최대 4개 동시 전달과 Durable Object alarm으로 나머지를 계속 전달한다. 새 토큰을 이전 전달의 410 응답으로 지우지 않는다. 상태 조회·같은 요청 재전송은 새 알림을 만들지 않는다.
5. 불명확한 등록 요청은 원본 ID·hash·서명된 요청과 plan의 결과만 조회한다. 기존 키·정책은 보존한다. 응답이 늦게 도착할 수 있는 원본 요청의 60초 수락 구간이 닫히기 전에는 absence로 fence를 해제하지 않는다. 승인 결과 불명은 자동 재승인하지 않는다.
6. 인증서·신원 IPC를 기다리는 중 창을 닫거나 다른 선택을 하면 이전 검토가 부활하지 않도록 전체 준비 과정을 하나의 취소 세대에 묶는다. 별도 issuer/origin에서 받은 absence도 현재 coordinator를 해제할 수 없다.
7. 전수 클릭 검사는 localhost 웹뿐 아니라 프로젝트의 실제 데스크톱 앱도 대상으로 설정할 수 있다. 웹·native desktop·fixture·구형 불명 범위, OS, baseline, 현재 실행 영수증을 구분한다. native harness가 없으면 미설정이며, 실행 종료 코드 0이나 클릭 0만으로 통과하지 않는다. 기존 웹 desktop-size fixture를 실제 데스크톱 앱 검사로 표시하지 않는다.
8. 공통 등록만 한 수신 Mac의 안전 준비는 legacy 폰 등록 대신 현재 관리 모바일의 알림 구독과 실제 수신 Mac의 서명된 원격 중단 poll로 확인한다. 새로운 생체 인증 없이 승인된 기기 키로 구독하며 OS 알림 거부는 더 높은 관찰 순서의 제거 요청으로 반영한다. OS 상태 확인·서명·HTTP가 늦게 끝나도 이전 정책·계정·세션을 되살리지 않는다. 미확정 양의 요청 16개가 알림 철회를 막지 않도록 음의 관찰과 원문 증거 예산을 분리한다. 원문은 보존하며 전체 128개·256KiB 증거 예산까지 소진되면 제거 미확인·증거 포화를 명시한다. 무제한 복구나 철회 성공을 가장하지 않는다. 명령 결과는 원래 서명과 ID를 보존해 복구하며, 사용 중단·화면 끄기·해당 Mac의 접근 철회만 허용한다. 이 경로도 S-M3·Screen 켜짐·사람의 보류·OS 권한 관문을 유지한다. 실제 APNs 수신 확인이나 모든 통신의 이전 완료를 뜻하지 않는다.
9. 첫 영상 대기는 해당 원래 연결에서 20초로 제한한다. 유효한 영상 sample이 준비돼야 대기를 끝내며, 안내 메시지·빈 영상·delta만으로 제한 시간을 연장하지 않는다. 취소된 이전 연결의 timer가 새 연결을 닫지 않으며, 시간 초과로 자동 재연결하거나 생체 인증을 다시 시작하지 않는다.

## 5G 장애와 현재 경로 구분

11-03 사진의 `Cloudflare 사설망에서 Mac까지 연결하지 못했습니다. Mac 인증은 아직 시작하지 않았습니다`는 기존 QR 등록 항목의 사설 TCP 경로 실패다. 3호 주소는 핫스폿의 `172.20.10.4`에서 네트워크 이동 후 `192.168.102.41`로 다시 바뀌었다. 이전 주소 `192.168.219.138`도 현재 인터페이스에 없었다. 터널 Healthy만으로 저장 IP·허용 경로·수신 앱 준비가 증명되지 않는다.

해당 3호의 정확한 `/32`만 기존 소유자 TCP 52741 허용 규칙·나머지 접근 차단 규칙·사설 터널·iPad split include에 추가하고 저장 후 다시 읽었다. 사용자가 명시적으로 요청한 Appium 운영 점검에서 iPad 2124의 저장 주소가 `192.168.0.6`인 점과 One Agent가 연결됐지만 새 주소를 포함하지 않은 점을 직접 확인했다. 저장 주소를 `192.168.102.41`로 바꾸고 설정을 다시 열어 보존을 확인했으며, VPN을 재연결한 뒤 실제 포함 경로에 `192.168.102.41/32`가 반영된 것도 확인했다. 이후 사용자가 직접 화면 세션을 시작하고 **5G에서 화면 보기·클릭·스크롤 정상**, iPad에서 메시지 입력을 확인했다. 이 성공은 설치된 2124의 기존 QR 사설망 경로에 한정한다. 후속 공통 인증 소스의 실기 통과로 바꾸어 보고하지 않는다. 현재 주소는 네트워크 이동 후 바뀔 수 있다. 기존 등록이나 개인 키를 초기화하지 않았다.

Appium 점검은 설치 앱에 접근하지 않는 자동 프로젝트 검사와 별개인, 사용자가 지정한 실제 기기 설정 작업이었다. AI는 화면 세션·생체 인증을 시작하거나 원격 Mac에 입력하지 않았으며, 점검용 Appium·WDA·USB proxy만 종료하고 AgentsToZ의 Mac 목록을 남겼다. 원본 점검 영수증은 `~/Library/Caches/AgentsToZ/appium-ipad-inspect-20261103/inspection-repair.receipt.json`에 있다.

공통 등록 행은 별개로 내장된 outbound WSS relay와 protocol 6 E2EE를 사용한다. One Agent나 저장 IP가 필요하지 않지만, 양쪽의 실제 공통 승인·현재 사용 세션·상대 수신 허용·Screen 켜짐·알림 gate가 필요하다. 기존 QR 행을 자동으로 공통 신뢰로 승격하지 않는다.

`100.x` Tailscale 주소는 OS의 자기 호스트 경로가 있어도 현재 `ScreenPrivateNetworkRoute`가 RFC1918만 받으므로 2124 복구 주소로 쓰지 않는다. 이 사실을 Cloudflare WARP 기기 주소로 잘못 설명하지 않는다.

## 검증·출시 시 남은 관문

- 최종 통합 commit을 동결하고 정상 mobile-workroom 프로필, 테스터 변경 관련 검사, 전체 16개 페르소나와 `bun run verify`를 그 소스에서 실행한다. 기존 96개 검사 상한 안에서 argv와 coverage를 확장한다. 구성요소의 이전 검증을 새 통합 HEAD 통과로 보고하지 않는다.
- 실제 workerd와 APNs 대역의 완료 대기를 사용한다. 전달 시작 횟수를 완료로 간주하거나 전역 응답 모드를 전달 도중 바꾸는 fixture race를 재도입하지 않는다.
- 공개 소스 확인·공증 빌드·설치는 검증 후 기존 출하 가드로 한다. 새 설치본 전까지 Main 입구·알림·관리 역할 개선이 설치됐다고 말하지 않는다.
- 사람이 시작하는 Mac1↔Mac3 및 iPad 5G의 **새 공통 등록**·복수 Mac 전환·화면 연결·입력을 실제 확인해야 한다. 기존 QR 경로의 iPad 5G 성공과 구분한다. 현재 사용자의 iPad→Mac3 연결을 설치 교체로 끊지 말고 교체 직전에 유휴를 확인한다.
- **S-M3 실측은 입력 출처가 충돌해 ambiguous이며 기존 Mac 조작 gate는 꺼져 있다.** 명시적으로 승인하는 새 desktop trust 모드는 이 물리 출처 관문과 별도다. 기존 관문을 통과로 위조하거나 새 모드의 소스·fixture만으로 Mac 상호 실기 완료를 보고하지 않는다.
- 화면과 명령은 목적·프레임·예산이 구분되지만 현재 같은 relay DO 계층을 사용한다. 별도 WebRTC/TURN 미디어 경로와 성능 실측은 완료하지 않았다. 모든 통신이 Cloudflare로 전환됐다는 뜻도 아니다.

운영 상태와 원본 로그·실행 영수증은 canonical `.agentstoz/maintainer/manual/`에 보존한다. 저장 위치가 있다는 사실과 실기 성공을 구분한다.
