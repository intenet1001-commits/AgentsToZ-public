# Codex·ego-lite에서 시작하는 온보딩 — 사용자 합의, 2026-09-11

상태: 후속 설계 방향. 이 문서의 동선 전체를 구현·출시했다는 뜻이 아니다.
기존 PLAN의 ego 선택 보조 제안에 대해, 사용자는 브라우저 보조 여정의 선행 준비를 명확히 요청했다.

## 시작 동선

앱과 기존 localhost 화면에서 동일한 시작 도우미를 제공한다.
완전 신규 사용자는 설치 앱에서 시작하며 개발 서버를 직접 실행하도록 요구하지 않는다.

1. Codex 설치 확인 → 없으면 공식 설치 지원 → 사용자 로그인.
2. ego-lite 설치 확인 → 없으면 공식 설치 지원 → 브라우저 제어 연결 확인.
3. 온보딩 시작 → Codex가 지침과 앱에 저장된 진행 상태를 읽는다.
4. 선택한 GitHub·Supabase·Vercel·Google OAuth 과정을 실제 브라우저 화면에서 진행한다.
5. 계정 선택·가입 정보·비밀번호·추가 인증 등 필요한 순간에 사용자에게 제어를 넘긴다.
6. 사용자 완료 후 실제 결과를 검사하고 다음 단계로 진행한다.

첫 두 단계는 AI 없이 동작해야 한다. 브라우저 메뉴 조작은 Codex/ego가, 로컬 설치와 CLI 검사는
앱의 제한된 설치 도우미가 담당한다. 준비 도구 설치 자체가 또 다른 AI를 전제로 해서는 안 된다.

## 기존 경로를 개선할 범위

기존 개인 포털 마법사에는 Google OAuth 안내와 Playwright 보조 프롬프트 복사가 이미 있다.
이를 앱에서 연결되는 ego 보조, 실제 콜백 값 안내, 검증된 완료 조건과 재개 기록으로 발전시킨다.
현재 OAuth 단계의 다음 버튼과 완료 안내는 실제 성공을 자동 보증하지 않는다.
Codex/GitHub 대표 설치·인증 구현과 전체 Google/Supabase/Vercel 여정의 검증을 혼동하지 않는다.

Vercel을 유지하는 방향과 Google OAuth 설정 부담 개선을 먼저 검증한다.
프로젝트 조회까지 QR 등록을 필수화하는 제안은 채택하지 않았다. 기존 조회의 편의성을 유지하고
원격 제어의 승인 경계를 보존한다. Vercel 개인 포털 및 공통 모바일/gateway의 최종 제품 경계는
전체 신규 사용자 시험 이후 명시적으로 재검토하며 기존 개인 환경을 자동 전환하지 않는다.

## 재개와 신규 사용자 시험

진행 상태는 앱의 영수증에 저장하고 Codex 대화가 바뀌어도 결과부터 다시 확인한다.
프로젝트·OAuth client·배포를 불확실한 상태에서 중복 생성하지 않는다.
브라우저 클릭 성공, CLI 설치, 로그인 정보 존재, 실제 서비스 이용 성공은 각각 따로 판정한다.

신규 브라우저 시험 → 새 macOS 사용자 시험 → 개발 도구가 없는 깨끗한 환경의 설치 시험 순서다.
ego의 새 task space는 기존 로그인 상태를 이어받을 수 있으므로 빈 브라우저 상태의 증거가 아니다.
새 macOS 사용자도 공용 앱/전역 도구가 남을 수 있다. 비밀번호·토큰·쿠키는 기록/진단에 넣지 않는다.

다른 계정으로 이동하기 전 소스 커밋·앱 버전·설계 결정·미완료 항목·성공 기준과 시작 프롬프트를
인수인계 파일로 준비한다. 이 파일은 Supabase 연결 전에도 읽을 수 있어야 한다.
시험 앱의 설정/로그인/완료 기록은 비워 두고, 개발 인수인계 자료를 기존 앱 데이터로 가져오지 않는다.
