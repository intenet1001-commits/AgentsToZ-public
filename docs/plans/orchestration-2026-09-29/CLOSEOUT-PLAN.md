## 실행 순서와 통과 조건

### 1. E2E 검증 도구 보완 및 로컬 검증 — Sol high

- `e2e-orch.ts`의 고정 프로젝트 ID·절대 경로를 현재 설치 경로와 등록 대상 목록으로 확인한다.
- delivery는 현재 nonce가 입력 프롬프트에 존재하기만 해도 성공할 수 있다. 실제 새 응답과 턴 완료를 확인하고,
  단일/세 줄 입력이 각각 한 번 전달됐는지 판정한다. 에코만 있는 경우 실패하는 대표 회귀를 추가한다.
- names는 `OPEN-DONE`/`CALL-DONE`만으로 성공 처리하지 않는다. 프로젝트 화면 대상,
  담당자 세션의 프로젝트·AI 일치, 기존 세션 재사용과 불필요한 중복 생성 없음을 각각 확인한다.
- pairs는 최종 문구 외에 실제 워커 생성·응답·왕복 전달 및 종료 결과를 확인한다.
- RPC 시간 제한·프로세스 종료 처리·실패 시 nonzero 종료 코드를 마련하고,
  테스트가 생성한 세션 ID를 추적해 실패해도 정리한다. 기존 사용자 세션은 보존한다.
- 승인 화면의 문구만 보고 Enter/2를 보내는 처리는 작업·대상·선택지 확인을 포함하도록 제한한다.
  테스트 범위 밖 요청이나 뜻이 불명확한 승인은 자동 진행하지 않는다.
- 테스트 시작 전 `/api/project-tester/ensure`를 세션당 한 번 호출하고,
  `.agentstoz/MAINTAINER.md`의 quick profile → 관련 회귀 → `bun run verify`를 실행한다.
  API가 없으면 기존 도구로 진행하고 이를 기록한다. 단순 문서 수정에 별도 테스트를 만들지 않는다.

완료: 에코·잘못된 대상·RPC 실패가 성공으로 기록되지 않으며 현재 소스의 필수 검증이 0 fail.

### 2. 소스 Push와 macOS 빌드·설치 — Sol medium, 이상 시 high

- 계획·수정 검토 및 커밋 후 `origin/main`으로 Push하고 실제 원격 SHA와 clean 상태를 확인한다.
- `bun run tauri:build:dmg`를 실행한다. 래퍼가 버전을 증가시키므로 `update-version`을 먼저 실행하지 않는다.
  현재 기준 예상은 544지만 재시도나 다른 작업이 소비한 번호가 있으면 실제 번호 N을 사용한다.
- 빌드가 만드는 버전 커밋도 별도로 Push하고 소스 SHA·앱 버전·DMG 경로를 결과에 기록한다.
- DMG 안의 앱을 확인한 뒤 설치본 백업 → 앱 정상 종료 → staging/교체 → 실행을 단계별 확인한다.
  빌드/복사 실패 후 기존 설치본을 제거하거나, 이전 DMG를 이번 성공 산출물로 재사용하지 않는다.
- 설치 앱·실행 sidecar 버전, OPS GitHub 링크, 기존 승인과 연결된 새 경로의 Codex hook 상태,
  OPS binding/legacyRoots·repositoryKey·memoryId·기억 동기화 상태를 확인한다.
- 핸드오프의 로컬 DMG 설치와 일반 사용자용 Developer ID/공증 배포는 별도 경로다.
  이 계획만으로 공개 DMG 배포 완료를 주장하지 않는다.

완료: 설치된 N 버전에서 마지막 두 수정이 실제 적용되고 OPS 기억 정체성과 기존 기록 접근이 유지됨.

### 3. 설치 앱 실기 E2E — 초기 Sol high

- 설치된 MCP를 통해 `pairs` → `delivery` → `names` 순서로 실행한다.
  저장소 루트에서는 `E2E_RUN=live<N> bun docs/handoffs/2026-09-29-orchestration/e2e-orch.ts <mode>`를 사용한다.
- pairs: codex→codex, agy→claude, codex→agy, claude→hermes, hermes→codex, claude→codex 회신.
- delivery: Codex·Claude·agy·Hermes 각각 한 줄/세 줄, 입력 잔류·누락·중복 없음.
- names: Codex·agy OPS에서 바이브2 열기/담당자 호출의 실제 대상·세션 재사용 확인.
- 실패 시 원인에 해당하는 코드와 회귀를 수정하고 관련 검증부터 재실행한다.
  앱 코드가 바뀌면 새 버전 빌드·설치 후 실패했던 실기와 영향을 받는 흐름을 다시 확인한다.

완료: 각 사례에 실행 버전·대상·세션·응답·종료 증거가 있으며 실패/차단/미검증을 구분함.

### 4. TestFlight와 사용자 실측 — Sol medium

- 최종 통과한 제품 빌드 번호 N으로 포털 웹을 다시 번들링하고 iOS archive/export/upload를 진행한다.
- 핸드오프의 `ios-testflight-upload.md`는 이번 프로젝트 파일 검색에서 찾지 못했다.
  실행 전 기존 iOS 스크립트·기억의 API 키 기반 업로드 절차로 경로를 확정한다. 키 원문은 출력하지 않는다.
- bundle `com.intenet.agentstoz.mobile.testflight`와 팀·실제 내부 테스트 그룹 ID를 조회해 확인한다.
  처리 상태 VALID → 「개인 테스트」 그룹 포함 → 기기에서 해당 빌드 사용 가능 여부를 각각 기록한다.
- OpenAI/Gemini 각각 음성 「아젠투지 → 바이브2 담당자 불러」의 대상·AI·기록 범위를 실측한다.
- 다른 Mac에서 업데이트 후 자동 마이그레이션 및 열린 워크룸이 있을 때 보류/다음 실행 동작을 확인한다.
  접근 가능한 기기가 없으면 이 두 실기 항목은 사용자 확인 대기로 남긴다.

완료: 업로드 성공·테스터 제공·실기 사용 성공을 구분하며 실제 확인된 단계까지만 완료 표시.
