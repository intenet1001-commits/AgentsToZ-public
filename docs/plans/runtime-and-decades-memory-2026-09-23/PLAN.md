## 2. 장기기억 "수십 년" 검증 — 관찰 결과

### 2.1 지난 검토가 이미 해결한 것 (재발견 아님)

기억 항목 `5012d5929f245f17d7eb9925`에 기록된 기존 검증:

- 25,000 항목(≈68년치) 고정 데이터에서 recall **약 0.3초**
- 최초 Push(fsync 포함) **약 2.3초**
- 저널/피드백 동기화는 커밋 안전 sequence + memory별 advisory lock
- 로컬 절단·커서 소실·원격 되감기에서 **건너뛰지 않고 0부터 멱등 재생**
- 큐레이트 리비전은 memory당 **500개 상한**
- Private GitHub 아카이브 검증은 **O(total)** — 수십만 항목 전에 증분 전환 필요

**이번 실측은 위 결론과 모순되지 않는다.** recall 42~55 ms는 현재 177 항목
기준이고, 25,000 항목 0.3초와 같은 곡선 위에 있다.

### 2.2 이번에 새로 발견한 것

#### M-1 (높음) — 색인 `CORE.md`가 상한 없이 증가하며 매 세션 전량 로드된다

`src/projectMemoryDocument.ts:154` `renderMemoryIndex()`는 **모든 노트의 모든
항목 제목**을 출력한다. 노트 본문은 12,000 bytes로 제한·압축되지만(`:45`
`MEMORY_NOTE_BUDGET_BYTES`), 색인 자체에는 어떤 상한도 없다.

실측:

```
색인 현재 크기        12,746 bytes   (노트 예산 12,000을 이미 초과)
  머리말                 780 bytes
  목차                11,966 bytes
durable 항목             157개
항목당 목차 비용        76.2 bytes
프로젝트 연령            59일 (2026-07-26 시작)
관측 증가율            2.66 항목/일
```

현재 증가율이 유지될 때의 색인 크기 — **이 파일은 매 세션 전부 읽힌다**:

| 기간 | 항목 수 | 색인 크기 |
|---|---:|---:|
| 1년 | 1,128 | 85 KB |
| 5년 | 5,013 | 374 KB |
| 10년 | 9,869 | **735 KB** |
| 30년 | 29,295 | **2.1 MB** |

노트를 한 개만 열어 읽게 만든 설계의 이점이 색인에서 상쇄된다. 30년 후
"필요한 노트 하나만 읽으세요"라는 안내 자체가 2.1 MB다.

**회귀 부재 확인**: `tests/` 전체에서 `renderMemoryIndex` 결과에 **절대 크기
상한을 두는 단언은 없다**. `project-memory-decompose.test.ts:81`에 상대 단언
(`색인 < 원문/4`)이 있으나, 이는 분해 효과를 확인할 뿐 항목 수와 함께 색인이
무한히 커지는 것을 막지 못한다 — 원문도 같이 커지기 때문이다.

#### M-2 (중간) — 리비전 500개 상한이 실제 사용률에서 77일밖에 못 버틴다

실측 리비전 생성률 (2026-09-20 ~ 09-23 조밀 구간):

```
19개 리비전 / 2.91일 = 6.5 리비전/일  (이 기억 하나)
문서화된 상한: memory당 500개
→ 상한 도달까지 77일 (0.21년)
→ 상한 도달 후 보존 창은 최근 77일뿐
```

상한 자체는 "로컬 원본을 지우지 않는다"는 설계이므로 **데이터 유실은 아니다**.
그러나 "수십 년 이력"을 리비전에서 되찾을 수는 없고, 실제 이력 보존은 저널과
로컬 파일에만 의존한다. 이 구분이 사용자에게 보이지 않는다.

계정 전체로는 초기화된 기억 46개 × 6.5 = **약 300 리비전/일**이 된다.

#### M-3 (중간) — `ports-save-audit.jsonl`에 회수 로직이 전혀 없다

`api-server.ts:8537`이 저장마다 append하고, 코드 어디에도 자르기·회전·삭제가 없다.

```
현재       81,033줄 / 9.9 MB  (55일)
증가율     1,473줄/일
10년       5,377,645줄 / 0.64 GB
30년      16,132,934줄 / 1.92 GB
```

기억 원본이 아니라 감사 로그이므로 **유실 위험은 없다**. 다만 앱 데이터
81 MB 중 이미 9.9 MB를 차지하며 무한 증가한다.

#### M-4 (낮음, 정보) — `inSync:false`는 결함이 아니다

원격이 로컬보다 최신이다(원격 09-23 13:57, 로컬 09-22 23:44). 원인은 **다른
Mac("회사에서받은맥북")이 오늘 4개 리비전을 Push**했고 이 Mac이 아직 Pull하지
않은 것이다. 리비전 체인은 끊김이 없고 설계대로 동작 중이다.

최근 20리비전의 기기 분포: 최천성 MacBook Pro 14개, 회사에서받은맥북 6개.

## 4. 개선 계획

### 비목표

- 기억 본체 재작성. 세 계층 구조(로컬 원본 / Supabase 동기화 / GitHub 냉보관)는 유지한다
- 리비전 500 상한 변경. 상한 자체는 의도된 설계다
- 감사 로그 삭제. 회수는 상한 도입이지 이력 폐기가 아니다
- 이 계획에서의 코드 변경. 승인 전까지 실행하지 않는다

### P1 — 색인 크기 상한 (M-1)

**수용 기준**
1. 25,000 항목 데이터에서 색인 크기가 상한 이내
2. 상한 초과 시 **항목을 버리지 않고** 섹션 요약으로 접는다
3. 접힌 섹션의 항목도 recall로 찾을 수 있다 (FTS는 노트 본문 기준이므로 이미 성립 — **검증 필요**)
4. 기존 색인을 읽던 경로가 깨지지 않는다

**검증 형태**
- `renderMemoryIndex` 결과 바이트에 대한 새 단언 (현재 부재)
- 25,000 항목 고정 데이터 회귀 — 기존 recall 벤치마크와 같은 규모
- 접기 전후 recall 동일성 비교

**설계 선택지** (미결정, 승인 시 하나를 고른다)
- (a) 섹션당 항목 제목 N개 + "외 M개" — 단순, 오래된 항목이 색인에서 사라짐
- (b) 섹션 요약만 두고 항목 제목은 노트 안으로 — 색인 상수 크기, 탐색은 recall 의존
- (c) 최근 항목은 제목, 오래된 항목은 접기 — 절충, 구현 복잡

### P2 — 리비전 보존 창을 사용자에게 보이기 (M-2)

**수용 기준**
1. 리비전 화면이 "최근 N일 / 500개 상한"을 실제 값으로 표시
2. 상한에 가까워지면 로컬 원본과 저널이 진짜 이력임을 안내
3. 상한 동작 자체는 변경하지 않는다

**검증 형태**: 상한 도달 데이터에서 표시 문구 회귀

### P3 — 감사 로그 상한 (M-3)

**수용 기준**
1. 크기 또는 줄 수 상한 도입, 초과 시 회전
2. **저장 커밋 경로에 영향 없음** — 현재 코드는 append 실패를 삼키도록
   설계됐고(`api-server.ts:8546`) 이 성질을 유지한다
3. 회전이 진행 중인 저장을 막지 않는다

**검증 형태**: 상한 초과 데이터에서 회전 동작 + 저장 성공 유지 회귀

### P4 — 런타임 미관찰 항목 해소 (R-1, R-2)

**수용 기준**
1. 인벤토리 `complete:false`의 원인 항목 수와 사유를 조회로 확인
2. v492 설치 후 같은 측정 재실행
3. 4개 CLI 각각 워크룸에서 실제 기동·응답 확인

**주의**: 이것은 측정이지 수정이 아니다. 문제가 나오면 별도 판단한다.

### 아카이브 O(total) — 기존 결정 유지

기억에 이미 기록된 "수십만 항목 전에 증분 매니페스트로 전환"은 현재 규모
(177 항목)에서 시급하지 않다. **이 계획에서 다루지 않고 기존 결정을 유지**한다.

## 6. 이 계획이 증거로 삼지 않는 것

- quick 프로파일 통과는 **전체 verify 통과가 아니다**
- 리비전 체인 무결은 최근 **20개** 페이지에 대한 것이다
- 25,000 항목 수치는 **이전 세션의 기록**이며 이번에 재실행하지 않았다
- 색인 성장 예측은 **현재 증가율의 선형 외삽**이다. 실제 사용 패턴은 달라질 수 있다
- 이 문서는 준비된 계획이며 실행·검토·머지 증거가 아니다
