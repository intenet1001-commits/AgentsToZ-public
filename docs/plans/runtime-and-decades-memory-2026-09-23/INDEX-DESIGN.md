# 장기기억 색인 개선 설계 — 실측 기반

작성 2026-09-23 · 대상 `AgentsToZ_byCS` main `e764bdd` (v492)
상태: **설계 확정안 — 미승인, 코드 미변경**

이 문서는 앞선 `PLAN.md`의 M-1 항목을 실측으로 다시 검토한 결과다.
**앞 계획의 진단 일부가 틀렸음을 아래에 정정한다.**

---

## 0. 앞 계획의 정정

`PLAN.md`는 M-1을 "색인이 커져서 느려진다"는 **I/O 성능 문제**로 적었다.
실측 결과 이는 틀렸다.

| 30년 규모(29,295항목) 측정 | 값 | 판정 |
|---|---:|---|
| 전체 저장 (노트 2,443개 + 색인) | 169.5 ms | 무해 |
| 색인 디스크 읽기 | 0.66 ms | 무해 |
| curated recall | 110~129 ms | 무해 |

디스크는 전혀 병목이 아니다. **진짜 비용은 색인이 매 세션 모델
컨텍스트에 통째로 올라간다는 것**이다.

| 기간 | 항목 | 색인 | 추정 토큰 | 200K 컨텍스트 대비 |
|---|---:|---:|---:|---:|
| 현재 | 157 | 12 KB | 4,096 | 2.0% |
| 3년 | 1,128 | 84 KB | 28,672 | **14.3%** |
| 5년 | 5,013 | 376 KB | 128,341 | **64.2%** |
| 10년 | 9,869 | 742 KB | 253,269 | **126.6% — 초과** |
| 30년 | 29,295 | 2,225 KB | 759,467 | **379.7% — 초과** |

한계선은 30년이 아니라 **3년 무렵부터 체감, 10년에 구조적 불가능**이다.
질문에 대한 정확한 답: **지금 구조로는 수십 년을 버티지 못한다. 다만
유실 때문이 아니라 색인이 컨텍스트를 잠식하기 때문이다.**

(토큰 수는 3 chars/token 추정. 실제 토크나이저 측정은 하지 않았다.)

## 1. 근본 원인

`src/projectMemoryDocument.ts:154` `renderMemoryIndex()`는 **모든 항목의
제목**을 출력한다. 노트 본문은 `MEMORY_NOTE_BUDGET_BYTES = 12,000`으로
제한되지만(`:45`) 색인에는 상한이 없다.

설계 의도는 "색인만 읽고 필요한 노트 하나만 연다"였다. 그러나 색인이
항목 수에 **비례**하므로, 노트를 나눠 얻은 이득이 색인에서 상쇄된다.
30년 뒤에는 "노트 하나만 읽으세요"라는 안내문 자체가 2.2 MB다.

**회귀 부재**: `tests/` 전체에 `renderMemoryIndex` 출력의 **절대 크기 상한을
두는 단언이 없다**. `project-memory-decompose.test.ts:81`의 상대 단언
(`색인 < 원문/4`)은 항목 수에 비례한 증가를 막지 못한다. 이 성질은 테스트가
지켜주지 않으므로 조용히 악화된다.

## 2. 접기가 안전한가 — 선결 검증

색인에서 항목 제목을 빼려면, 뺀 뒤에도 그 항목을 찾을 수 있어야 한다.
**실제 기억으로 측정했다**:

```
실제 항목 134개
자기 제목으로 회수        134/134  (100%)
3개 키워드 부분 질의       40/40   (샘플 40)
```

오래된 항목도 1순위로 나왔다 (예: "notarytool screen lock" →
`Recurring Issues (continued 3)` 항목이 최상위).

**반례 검토**: 30년 합성 데이터에서는 오래된 항목이 상위 8위 밖으로
밀렸다(`rank -1`). 원인을 확인한 결과 **합성 데이터의 결함**이었다 —
5,859개 항목이 같은 문구를 공유해 생긴 동점이며, 상위 히트는 주제상
정확했다. 어휘를 다르게 해도 동일했다. 따라서 **이 실험은 30년 규모의
recall 정밀도를 판정하지 못한다.** 실제 기억에서 100%가 나왔다는 사실만
확정적이다.

→ 이 불확실성 때문에 **recall에만 의존하는 설계는 채택하지 않는다.**
   결정론적 탐색 경로를 함께 둔다.

---

## 3. 기각한 안

### 기각 (a) — 섹션당 제목 N개 + "외 M개"
오래된 항목이 색인에서 **영구히 사라진다**. recall 정밀도가 30년 규모에서
미검증인 상태에서 이는 되찾을 수 없는 항목을 만든다.

### 기각 (b) — family 요약만 (항목 제목 전부 제거)
색인은 1 KB로 상수가 되지만(측정 확인), 탐색이 **recall에만** 의존한다.
§2의 미검증 위험을 그대로 떠안는다.

또한 결정론적 대안인 "family 전체 읽기"가 성립하지 않는다:

```
30년: family 6개, 최대 family = 407노트 = 879 KB
```

한 주제로 좁혀도 879 KB를 읽어야 한다 — 대안이 못 된다.

### 기각 (c) — 최근 150항목만 제목 유지
12 KB 상수로 유계지만(측정 확인), 역시 오래된 항목의 결정론적 경로가 없다.
(b)와 같은 이유로 부족하다.

**세 안 모두 "색인을 줄인다"에만 답하고 "그래도 찾을 수 있다"에는 답하지
못한다.** 그래서 구조를 바꾼다.

## 4. 채택안 — 3계층 색인

각 계층이 독립적으로 유계이고, 위에서 아래로 결정론적으로 좁혀진다.

```
T0  CORE.md              매 세션 로드   family 목록 + 항목수 + 색인 파일 경로
T1  notes/_index-<family>.md  필요시     그 family의 노트 목록 (노트당 1행)
T2  notes/<note>.md           필요시     항목 제목 + 본문 (기존 12KB 상한)
     ─ 교차 경로: recall (FTS) — 빠른 길, 유일한 길이 아님
```

**측정한 크기** (프로토타입 실행):

| 기간 | 항목 | T0 (항상 로드) | T1 최대 family | T2 노트 |
|---|---:|---:|---:|---:|
| 현재 | 157 | 0.6 KB | 0.2 KB | 2.4 KB |
| 3년 | 1,128 | **0.6 KB** | 0.8 KB | 2.4 KB |
| 10년 | 9,869 | **0.6 KB** | 7.2 KB | 2.4 KB |
| 30년 | 29,295 | **0.6 KB** | 21.7 KB | 2.5 KB |

T0가 30년 내내 **0.6 KB 상수**다. 현재 12 KB보다도 작다.
최악의 탐색도 0.6 + 21.7 + 2.5 = **24.8 KB**로, 현재 색인 12 KB의 2배에
불과하며 30년 시점 현재안(2,225 KB)의 **1/90**이다.

### 왜 이 구조가 (b)와 다른가
(b)는 T0만 만들고 T1을 두지 않았다. T1(노트당 1행)이 있으면 recall이
실패해도 **family → 노트 목록 → 노트**로 결정론적으로 도달한다.
T1을 항목당이 아니라 **노트당** 1행으로 두는 것이 핵심이다 — 항목당이면
30년에 371 KB로 다시 터진다.

## 5. 수용 기준

1. **T0 상수성**: 157 / 1,128 / 9,869 / 29,295 항목에서 `CORE.md`가
   2 KB를 넘지 않는다. 회귀로 고정한다 (현재 부재).
2. **T1 유계**: 어떤 family 색인도 30년 규모에서 32 KB를 넘지 않는다.
3. **도달성**: 모든 항목이 T0→T1→T2 경로만으로 recall 없이 도달 가능.
   현재 기억 134개 전부로 검증.
4. **회수 동등성**: 개편 전후 recall 결과가 동일 (134/134 유지).
5. **무손실**: 항목 ID(`memory-entry-id`)와 본문이 한 글자도 변하지 않는다.
   개편은 **색인 렌더링만** 바꾸고 노트 내용은 건드리지 않는다.
6. **하위 호환**: 기존 `CORE.md`를 읽던 경로가 깨지지 않는다.
   AGENTS.md의 "인덱스 읽고 해당 노트만" 지침이 여전히 성립한다.

| 위험 | 대응 |

| T0가 너무 추상적이라 무엇이 있는지 감이 안 온다 | T0에 family별 항목 수와 최근 갱신일 표시 |

| 기존 25,000항목 벤치마크와의 연속성 | 개편 후 같은 벤치마크 재실행으로 회귀 없음 확인 |

## 7. 실행 순서

1. **회귀 먼저** — T0 상수성·T1 유계·도달성 테스트를 **구현 전에** 작성.
   현재 코드로 돌리면 T0 테스트가 실패해야 한다(문제 재현 확인).
2. `renderMemoryIndex` → T0 렌더러로 교체, T1 렌더러 신규.
3. 저장 경로에서 T1 파일 생성·갱신.
4. 회귀 통과 확인 + 실제 기억으로 134/134 재검증.
5. `essential-contracts` 프로파일 재실행.
6. AGENTS.md의 메모리 지침 문구를 3계층에 맞게 갱신.

전제: 이 순서는 **M-1만** 다룬다. `PLAN.md`의 M-2(리비전 보존창 표시),
M-3(감사 로그 상한), R-1/R-2(런타임 재측정)는 그대로 유효하며 별개다.

### 기존 작업과의 관계 — 착수 전 확인 필요

원격 브랜치 `codex/memory-scale-20260923`에 같은 날짜의 선행 작업이 있다

## 8. 증거 경계

- 30년 수치는 **합성 데이터** 프로토타입 측정이다. 실제 30년 사용 패턴이
  아니다.
- 토큰 수는 3 chars/token **추정**이며 실제 토크나이저로 세지 않았다.
- recall 100%는 **현재 134항목**에서의 결과다. 대규모 정밀도는 §2대로
  미검증이며, 그래서 결정론적 경로를 설계에 넣었다.
- 이 문서는 준비된 설계이며 구현·검토·머지 증거가 아니다.
- 프로토타입 코드는 `~/.hermes/cache/scratch/memscale/`에 있고 제품
  코드에 반영하지 않았다.
