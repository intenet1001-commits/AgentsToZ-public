# 개선 앱 빌드·기능 검증 실행 계획

2026-09-13 · 상태: **실행 중**. 최신 결과는 [TEST-RESULTS.md](TEST-RESULTS.md)를 따른다.

최신 요청은 서명창 해결을 반복하기보다 추가한 기능을 새 앱으로 빌드하고 검증하되,
먼저 테스트 계획을 작성하는 것이다. 이후 사용자의 실행 요청에 따라 검증을 시작했다.
이 계획은 [ACCEPTANCE.md](ACCEPTANCE.md)의 제품 전체 합격 기준을 실제 실행 순서로 좁힌다.
기존 결과는 [EXECUTION.md](EXECUTION.md), 미구현 범위는 [IMPLEMENTATION.md](IMPLEMENTATION.md)를 따른다.

## 1. 기준선과 완료의 의미

| 구분 | 현재 확인된 상태 | 이번 검증에서 할 일 |
|---|---|---|

| 설치 Mac | v463, 이번 온보딩 변경 미포함 | 기존 앱을 눌러 보고 새 기능을 검증했다고 보고하지 않는다 |

완료 판정은 **빌드 성공 → 새 앱 실행 확인 → 기능별 실제 결과 → 재시작·업데이트 회귀**다.
계획된 기능, fixture 통과, CLI 버전 출력만으로 실제 사용 가능을 판정하지 않는다.
현재 완성되지 않은 AI/MCP 왕복 확인, 소스 없는 포털 자동 배포, 신규 OAuth 전체 자동 설정,
두 OS 사용자 동시 endpoint 격리는 `미구현/개선 필요`로 기록한다.

## 2. 실행 환경과 데이터 보호

- 테스트 폴더 3개: 빈 폴더, 한글·공백 경로의 Git 프로젝트, 연결된 worktree. 운영 프로젝트는 실패 주입에 사용하지 않는다.
- UI 자동화는 fixture API·임시 SQLite·테스트 브라우저 프로필에서 시작한다. 예상 외 API/외부 쓰기는 실패시킨다.
- 실제 앱 조작은 전용 테스트 프로젝트에서 수행한다. 테스트 전후 등록 목록·UUID·memoryId·원격 승인 만료·설정의 변화를 대조한다.
- 실제 사용자 데이터는 삭제·초기화하지 않는다. 오래된 워크룸 정리는 테스트 세션만 대상으로 검증한다.
- native 앱은 Tauri가 정한 앱 데이터 경로를 사용한다. Bun의 `APP_DATA_DIR`만 바꿔 전체 native 앱이 격리됐다고 판단하지 않는다.
- 깨끗한 첫 실행은 별도 OS 테스트 계정/VM에서 확인한다. HOME 변경이나 같은 Mac의 새 계정만으로 개발 도구 없는 환경을 증명하지 않는다.
- 앱의 고정 포트 3001 때문에 두 계정 동시 실행은 별도 회귀 항목이다. 점유 중인 다른 사용자의 서버를 종료하지 않는다.
- 실제 로그인·키체인·MCP 제공자 권한처럼 도구가 접근할 수 없는 단계는 `사용자 조작 필요`로 남긴다. 같은 승인 요청을 반복 실행하지 않는다.
- Mac 재시동은 이번 계획에서 재요청하지 않는다. 이전 재시동 요청의 완료 여부는 실행 재개 시 먼저 확인한다.

## 3. 순서와 단계별 종료 조건

| 단계 | 실행 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| T0 기준선 고정 | 현재 변경/기존 결과 검토, 테스트 자원 지정, 실행 중 작업·버전·sidecar 상태 기록 | 대상 소스와 데이터 범위가 명확함 |
| T1 코드·UI 회귀 | 이번 변경의 집중 테스트, 온보딩 UI, 워크룸 입력/저장/승인 fixture | 0 fail. 실패 시 원인 수정 후 관련 검사부터 재실행 |
| T2 새 Mac 앱 빌드 | 최종 verify, 소스 정리·공개 snapshot 반영, 공식 소스 가드로 빌드 | 새 산출물 생성·버전/소스/자원 일치. 오래된 산출물 재사용 금지 |
| T3 Mac 실제 작업 | 새 앱에서 연결 센터→프로젝트→4종 CLI→저장→종료→재개 | 실제 입력/응답·저장 결과가 관측되고 데이터 회귀 없음 |
| T4 모바일·원격 | 연결된 실제 iPhone의 모델 확인, 로그인→목록→원격 입력→저장→재접속 | 실제 폰과 Mac의 동일 작업 결과 확인 |
| T5 안정성·새 사용자 | 반복/지연/연결 중단/업데이트·새 OS 사용자·포트 충돌 | 누적 오류·중복 작업·권한 손실·다른 계정 데이터 혼입 없음 |
| T6 배포 검증 | Mac Store 서명·sandbox·profile·업로드·TestFlight 설치 후 T3/T4 핵심 재검사 | 실제 배포 채널에서 통과. 로컬 앱 결과와 구분 |

최우선은 T0~T3이다. 서명창이 막혀도 T1과 소스·번들 검사는 진행 가능하다.
T4의 실기 조건이 없으면 가능한 자동 검사를 완료하고 실제 폰 항목을 대기 상태로 남긴다.
최종 배포 목적지는 기존 결정대로 TestFlight이며 Developer ID 배포로 임의 변경하지 않는다.

### 빌드·설치 규칙

1. 먼저 소스/프런트·sidecar의 테스트 빌드를 검사한다. 배포 서명 인증서를 사용하지 않는 로컬 검사를 먼저 진행한다.
2. 변경 파일만 검토·커밋하고 기존 private→public 배포 절차를 사용한다. 공개 저장소에는 정제된 snapshot만 반영한다.
3. 설치할 공식 앱은 clean worktree와 원격 기본 브랜치 HEAD가 일치한 소스로 빌드한다.
   `--allow-unpublished-source` 산출물은 로컬 분석용이며 운영 앱 설치·배포에 사용하지 않는다.
4. `bun run tauri:build`는 빌드 번호와 공통 출력 폴더를 변경한다. 빌드 병렬 실행을 피하고 산출물 시각·manifest·리소스를 대조한다.
5. 새 앱 설치는 기존 원격 작업·저장 진행 상태를 확인한 뒤 수행한다. bundle ID와 앱 데이터 경로를 보존한다.
6. 실행 후 UI 버전, Info.plist, 실제 프로세스 경로, 응답하는 sidecar의 버전/출처를 맞춘다.
   프런트만 최신이고 backend는 이전 버전이면 실패다.
7. 기존 v463을 복사한 서명 실험 파일은 이번 새 기능 테스트에서 제외한다.

4종 CLI 결과는 별도 행으로 기록한다: `설치 / 인증 / 시작 / 입력 / 응답 / context 관측 / 수동 저장 / 자동 저장 지원 / 종료`.
한 CLI의 성공을 다른 CLI로 확대하지 않는다. 비싼 컨텍스트 채우기를 위해 불필요한 AI 호출을 반복하지 않는다.
50/75/90 경계는 결정적 fixture로 검사하고, 실기는 작은 실제 저장 1회로 경로를 확인한다.
음성은 실제 제공자 음성 세션의 전사→동일 MCP 실행을 별도 확인한다. 텍스트 명령 통과를 음성 통과로 계산하지 않는다.

## 5. 기존 러너 사용 순서

아래는 실행할 명령이며 이번 계획 작성에서 실행하지 않았다. 실제 계정 호출은 자동 회귀와 분리한다.

```bash
# 이번 변경의 빠른 회귀
bun run typecheck
bun test --cwd tests --max-concurrency=1 onboarding-app-first.test.ts onboarding-supabase-status.test.ts onboarding-infrastructure.test.ts onboarding-tools-refresh.test.ts

# 새 App 번들 및 온보딩 fixture
bun run build
bun tests/onboarding-first-project-app-ui.mjs dist
bun tests/onboarding-preparation-ui.mjs
bun tests/onboarding-first-project-ui.mjs

# 최종 변경본 커밋 전 필수 전체 검사
bun run verify
```

워크룸 브라우저 회귀는 전용 Vite만 기동하고 다음 기존 러너를 재사용한다:
`workroom-input-lifecycle.e2e.mjs`, `workroom-session-footer.e2e.mjs`,
`workroom-usability.e2e.mjs`, `workroom-rendering.e2e.mjs`, `internet-workroom-approval.e2e.mjs`.
러너마다 origin 계약이 다르므로 실행 전 확인한다. footer는 현재 9000 고정이고 승인 러너는
`INTERNET_APPROVAL_TEST_ORIGIN`을 지원한다. 점유 포트를 빼앗지 않고 필요하면 테스트 러너에 origin 주입을 추가한다.
Vite는 `./node_modules/.bin/vite --host 127.0.0.1 --port <확인한 빈 포트> --strictPort`로 실행한다.
앱 데이터와 연결되는 `bun run start`를 fixture 서버 대신 켜지 않는다.

순수 회귀 재사용 대상은 `remote-control-mobile-terminal`, `remote-terminal-grant`,
`remote-control-relay-session-vault`, `codex-auto-remember-coordinator`, `workroom-close-evidence`,
`terminal-memory-queue`, `agentstoz-use-control`, `orchestration-mission-*` 테스트다.
`bun run verify`에서 이미 통과한 동일 소스는 관련 수정·실패·미해결 우려가 생길 때만 반복한다.
`bun run test:ios`는 native 정적/계약 검사이며 실제 iPhone 조작을 대체하지 않는다.
실제 기기가 연결되어 있으면 모델/OS/설치 빌드를 먼저 확인하고 이전에 쓰던 폰이라고 가정하지 않는다.

## 6. 성능·장시간 안정성

| 검사 | 횟수/측정 | 초기 목표 및 판정 |
|---|---|---|
| 앱 시작·연결 센터 | cold 5회/warm 10회, 중앙값·최댓값 | 클릭 피드백 200ms, 로컬 진단 3초, 전체 진단 15초 목표. 실패 원인도 표시 |
| 목록·원격 입력 | 목록 10회, 키 입력 30회, p50/p95·유실/중복 | 정상망 목록 3초 목표/10초 내 결과·오류. 입력 유실·중복 0건. 지연은 LAN/외부망 분리 측정 |
| 워크룸 수명 | 시작/종료 20회, 탭 전환 50회 | 고아 프로세스·리스너·타이머·진행 중 표시가 누적되지 않음 |
| 연결 복구 | 연결 단절/복귀 10회 | 권한·대상·미확정 입력이 보존되고 중복 실행 없음 |
| 저장 | 경계 fixture + 실제 저장/종료 경로 | 로컬 문서·receipt·백업 상태 일치, 중복 AI 호출 없음 |
| 장시간 실행 | 60분, 안정 후 2시간 확장 | RSS/CPU/프로세스/큐 길이의 idle 회복 확인. 두 배치를 비교해 지속 증가 시 실패 조사 |

수치는 측정 완료값이 아닌 초기 목표다. AI 첫 토큰 시간은 앱 dispatch 지연과 제공자 응답 시간을 나눠 기록한다.
30일 유지 약속은 시간 이동 fixture·짧은 실기·장기 경과 결과를 별도 표시한다.
성능을 맞추려고 실제 작업·미저장 기록을 삭제하거나 권한 검증을 생략하지 않는다.

## 7. 실패 처리와 인계 결과

- `통과 / 실패 / 미구현 / 환경 차단 / 미실행` 다섯 상태를 사용한다. 전체 체크 수로 완료를 꾸미지 않는다.
- 재현→원인→수정→관련 회귀→같은 native/mobile 동작 재시험을 한 묶음으로 기록한다.
- 데이터 손실, 잘못된 계정·프로젝트 접근, 중복 명령/저장, 잘못된 성공 표시는 배포 차단 항목이다.
- 기본 흐름이 막히는 로그인 후 빈 화면·키 입력 무반응·종료 전 저장 실패도 수정 후에 진행한다.
- 인증창 차단은 한 번 원인 확인 후 사용자 조작 필요로 기록하고 다른 독립 검사를 계속한다.

각 결과는 `시험 ID, 앱/소스/sidecar/iOS 버전, 환경, 조작, 기대값, 실제값, 상태,
증거 경로, 결함/수정 커밋, 재검사 결과`를 남긴다. 비밀·사용자 원본 데이터는 증거에서 제외한다.
마지막 보고는 새 앱 위치/버전, 기능별 통과표, 해결한 결함, 남은 차단 조건,
실기하지 못한 항목, TestFlight 배포 상태를 함께 제공한다.
