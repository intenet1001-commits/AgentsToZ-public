상태: **검증 계획. 아래 시험은 이번 계획 수립에서 실행하지 않았다.**
[PLAN.md](PLAN.md), [IMPLEMENTATION.md](IMPLEMENTATION.md), [HANDOFF.md](HANDOFF.md)를 기준으로 한다.
기존 v463의 일반 회귀 통과는 신규 온보딩 전체 여정 통과를 대신하지 않는다.

## 1. 사용자 유형별 실제 시험

| 시험 환경 | 무엇을 구분하는가 | 필수 성공 결과 |
|---|---|---|
| 기존 계정·기존 설정 | 기존 사용자 업데이트 회귀 | 프로젝트/기억/UUID/원격 승인/만료·진행 보존 |
| 같은 Mac의 새 OS 계정 | 사용자 저장 공간과 공유 실행 파일 | 별도 등록/Keychain/CLI 인증, 기존 계정 데이터 변경 없음 |
| 두 계정 빠른 사용자 전환 | 동시 sidecar·MCP·포트 | 다른 계정 서버 채택/종료 없음, 양쪽 정상 동작 또는 정확한 미지원 안내 |
| 개발 도구 없는 새 Mac/깨끗한 VM | 개발자 환경 의존성 제거 | 소스/Bun/Rust/Xcode 없이 앱 실행, 필요한 도구만 준비 |
| 기존 Supabase/Vercel 공간의 추가 기기 | 이사/기기 추가 | 기존 자원 재사용, 새 UUID 한 개, pending 재개 시 같은 UUID |
| 별도 소유 계정·빈 Supabase·새 포털 | 진짜 새로운 사용자 | 개발자 데이터 접근 없이 S0~S9 완료 |
| 서로 다른 두 고객 공간 | 공간 격리 | DB/인증/cache/relay 교차 접근 거부 |
| 실제 iPhone TestFlight + 외부망 | 배포 앱의 실제 동작 | Google 로그인·목록 자동 표시·원격 입력/응답·저장·재접속 |

새 OS 계정만으로 '아무것도 설치되지 않은 Mac'을 대신하지 않는다. HOME 임시 변경으로 Keychain 격리를 주장하지 않는다.
시험 자원은 전용 프로젝트/DB/폴더로 지정하며 사용자의 실제 장기기억을 실패/삭제 시험에 쓰지 않는다.
실제 계정 로그인/2FA/OS 계정 생성은 사람이 처리하는 실기 단계로 남기고 가짜 성공을 주입하지 않는다.

## 3. 조작 수와 체감 속도 측정

초보 사용자 최소 3명이 개발자 구두 설명 없이 대표 경로를 수행한다. 통계적 일반화가 아닌 출시 전 사용성 점검이다.
성공/중단 위치와 원인, 화면에서 소요한 시간, 사람의 선택·로그인·보안 입력 횟수, 복붙 횟수를 구분한다.

| 지표 | 제안 합격 기준 |
|---|---|
| 직접 개발 명령 작성·실행 | 기본 전체 경로에서 0회 |
| 수동 SQL/.env/설정 파일 편집 | 기본 전체 경로에서 0회 |
| AI 인계문 작성 | 앱 생성, 사용자 직접 작성 0회 |
| AI 인계문 복붙 | 정상 시작 1회, 이후 제공자 변경/대화 복구에 필요한 경우만 추가 |
| 인계문 외 비밀값 복붙 | 엄격한 목표 0회. 필요하면 개선형 성공으로 별도 표시하고 엄격 목표 미통과 |
| 이미 완료한 단계 재입력 | 0회. 인증 만료 등 실제 새 증거가 있을 때만 재인증 |
| 로그인/승인 후 목록 | 정상망에서 3초 이내 목표. 최대 10초 안에 결과 또는 원인·재시도 제공 |
| 클릭 반응 | 네트워크 작업 전 200ms 이내 진행 표시 목표 |
| 진단 첫 화면 | 로컬 3초/전체 15초 예산 목표, 지연 시 항목별 이전 결과와 검사 중 표시 |
| 자동 AI 비용 | 상태 조회·화면 열기로 발생 0회. 첫 실제 작업/사용자가 선택한 AI 도움만 호출 |

시간 수치는 설계 목표이며 측정 완료값이 아니다. 다운로드/서비스 계정 생성/2FA·Apple 심사 대기 시간을
빠른 내부 실행 시간으로 감추지 않는다. 실패율·재시도·사용자 대기 시간을 별도 기록한다.

## 4. 검증 실행 순서

1. 관련 순수 상태·DTO·receipt·진단 회귀를 실행한다. 신규 테스트는 실패 경계·실제 동작을 검증한다.
2. fixture API/격리 DB로 React UI의 재개·늦은 응답·실패·키보드 접근을 검증한다. 테스트가 사용자 계정을 쓰지 않게 한다.
3. 빌드된 실제 설치 앱에서 공식 installer/auth/browser 흐름을 실행하고 새 OS 계정의 Keychain/권한을 확인한다.
4. 전용 별도 서비스 공간에서 실제 Google 로그인·Vercel 배포·DB read/write를 확인한다.
5. 실제 iPhone TestFlight 앱을 외부 네트워크로 연결해 전체 원격 작업을 확인한다.
6. 업데이트/재부팅·두 OS 사용자 동시 실행·두 고객 공간 시험으로 회귀를 확인한다.
7. 코드 커밋 전 `bun run verify`와 변경 영역에 필요한 UI/native 검사를 통과한다. 문서만 작성하는 지금은 제품 전체 검사를 실행하지 않는다.

실기 증거에는 app/source/recipe 버전, 배포 채널, OS/CPU, 설치·인증 구분, 오류 코드, readback 결과만 기록한다.
개인 계정·프로젝트 ID·스크린샷 등 사적 자료는 공개 계획에 넣지 않는다.

## 5. 출시 판정

다음 판정은 분리한다.

- **계획 완료:** 네 문서의 순서·책임·검증·공식 근거가 연결되고 모순/누락된 링크가 없음.
- **개인 환경 재현 완료:** 독립 사용자 소유 서비스에서 S0~S9를 실제 통과. 앱만 실행하거나 기존 개인 계정 성공으로 대체하지 않음.
- **클릭·인계문만 완료:** 보안 입력 포함 조작 수 기준을 실제 충족. 예외가 남으면 그 항목을 명시.
- **Mac TestFlight 가능:** 필요한 호스트 기능이 배포 제약을 충족하고 실제 업로드·설치·동작까지 통과.
- **외부 사용자 배포 가능:** 외부 테스터용 그룹/초대 또는 공개 링크, 필요한 Beta App Review, 지원 OS·빌드가 준비됨.
- **공통 gateway 완료:** F1의 별도 결과. 개인 Vercel 구성을 완성한 것으로 공통 gateway 완료를 주장하지 않음.

Mac TestFlight에서 전체 호스트 기능이 불가능하면 해당 채널은 미통과로 남기고 Developer ID 설치본의 같은 온보딩으로
검증할 수 있다. 사용자가 요청한 TestFlight 경로 달성 여부를 바꿔 말하지 않는다.
심사 결과·서비스 장애는 앱 개선으로 보장할 수 없다. 진행 보존·정확한 상태·복구 안내는 앱이 보장해야 할 범위다.
