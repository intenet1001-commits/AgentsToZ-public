# Control 기본 제공 및 여러 Mac 자동 준비 계획

상태: 2026-09-14 구현 진행. 설계 목표와 실제 구현·검증은 [실행 기록](CONTROL-PROFILE-EXECUTION.md)으로 구분한다.

같은 날 사용자 요구로 [AgentsToZ 사용자 운영 프로필 설계](AGENTSTOZ-PROFILE-PLAN.md)를 상위 계약으로 추가했다. Control은 사용자 전체의 운영 프로필이며 폴더는 저장 어댑터다. 아래 준비 절차는 기존 Control 복원에 우선 적용하고, 신규 공개 사용자의 기본 저장은 프로젝트 폴더가 필요 없는 앱 데이터 영역으로 한다. `controlId` 명칭은 구현 시 `profileId`로 통일한다.

## 사용자에게 보장할 결과

- private byCS 업데이트: 소스 Pull 후 최신 앱/개발 서버를 실행하면 기존 사용자의 Control 저장소를 복원·등록하고 원래 기억으로 연결한다. 복원 버튼을 다시 찾아야 하는 구조를 없앤다.
- 공개 저장소 clone: 첫 실행부터 관제 화면과 준비 카드가 보이며, 본인의 기존 Control 복원 또는 신규 생성으로 이어진다.
- 배포 앱 설치: 저장소 checkout 없이 같은 준비 엔진이 작동한다. 모바일 앱은 연결된 Mac의 Control을 사용하며 휴대폰에 별도 Control 기억을 만들지 않는다.
- 폴더 준비, 기억 연결, CLI 연결, 첫 작업 성공을 별도로 표시한다. 폴더 존재만으로 오케스트레이션 준비 완료를 표시하지 않는다.

## 착수 시 확인한 빈틈

`src/controlCenterProject.ts`는 이름/폴더명으로 등록 항목을 찾는다. `src/App.tsx`의 복원은 일반 GitHub clone 폼을 열고, `/api/control-center/create`는 로컬 등록 조회 후 새 프로젝트를 만든다. 시작 시 기존 계보를 찾아 복원하는 공통 엔진은 없다. 이름만으로 동일한 Control을 판정하지 않도록 바꿔야 한다.

Git의 일반 `git pull`은 앱 코드 실행이나 설치 앱 교체를 보장하지 않는다. clone으로 사용자 Git hook이 자동 설치되는 것도 전제로 삼지 않는다. 따라서 완료 조건은 **Pull + 업데이트된 런타임 실행**이다. 앱의 업데이트 흐름은 이 두 단계를 묶고, 터미널 Pull 이용자는 다음 실행에서 자동 준비된다.

## 공통 Control 준비 엔진

신규 `controlCenterBootstrap` 도메인과 호스트 어댑터를 둔다. 개발 Bun API와 패키지 sidecar가 같은 엔진을 호출한다. 프론트엔드, MCP와 업데이트 스크립트는 이 엔진의 상태/진행 요청만 사용한다. 렌더링이나 상태 조회 자체는 생성 요청이 아니다.

상태는 checking → needs-account/root/choice → restoring 또는 creating → registering → restoring-memory → configuring-agents → ready/needs-attention으로 관리한다. 각 단계의 영수증·버전·마지막 오류를 계정 전용 앱 데이터에 저장한다. 재시작은 완료 증거를 검증해 중단 지점부터 이어가며 AI 미션을 자동 재실행하지 않는다.

별도의 계정/Control 단위 lease로 개발 서버와 설치 sidecar의 중복 준비를 막는다. 멱등 키는 사용자 주체와 controlId로 구성한다. 임시 clone 디렉터리에서 검증한 뒤 목적지를 no-replace 방식으로 확정한다. 기존 폴더는 origin, memoryId, Control 표식을 검증하고 등록만 보완한다. 같은 이름의 다른 폴더나 충돌·권한 오류에서 새 기억 생성으로 대체하지 않는다.

## 사용자 설정과 Mac 설정 분리

공유 Control 프로필에는 schemaVersion, controlId, 소유자 주체, GitHub repository node ID/URL, canonical memoryId, 사용자가 선택한 자동 복원 정책을 둔다. 소유자 주체는 검증된 로그인 계정/기존 신뢰 가능한 개인 설정을 기준으로 하며 표시 이름이나 이메일 문자열만으로 합치지 않는다. 공유 저장소는 기존 백엔드의 사용자 격리가 검증된 범위에서 사용하고, 제공되지 않는 배포에서는 사용자가 가져온 프로필로 연결한다.

Mac별 기록은 OS 사용자 영역의 설치 ID, 선택한 workspace root, 실제 폴더, 로컬 등록 ID, 준비 결과와 CLI 연결 상태다. 절대경로·토큰·인증정보는 공유 프로필에 넣지 않는다. 같은 Mac의 다른 OS 사용자는 별도 로컬 설정을 가지며, 같은 클라우드 사용자로 로그인하고 기존 Control을 선택한 경우에만 같은 기억으로 연결한다.

기존 Control의 `.agent-memory/config.json` 정체성을 보존한 채 사용자 운영 프로필의 기억 backend로 연결한다. 사용 범위는 사용자 전체지만 저장 형식을 억지로 바꾸지 않는다. 이 작업 때문에 별도의 서비스 USE-memory 저장소로 변환하거나 byCS 개발 기억과 합치지 않는다. 이름/폴더명이 아니라 profileId와 검증된 기억 바인딩으로 조회한다.

## 먼저 구현할 개인 byCS 경로

1. 이 사용자의 기존 Private Control 원격 저장소/기억 정체성을 검증하여 복원 프로필을 만든다. 사용자는 이번 요청으로 자기 다른 Mac에서의 자동 복원을 요청했다.
2. 개인 bootstrap 프로필은 private 전용 경로에 두고 public snapshot 제외 규칙 및 검사를 먼저 추가한다. 공개 저장소/공개 앱 리소스에는 이 프로필을 포함하지 않는다. 개인 프로필도 인증 토큰을 담지 않는다.
3. 다른 Mac의 byCS 최신 소스 실행 시 이 프로필을 읽는다. GitHub 접근 가능하고 사용 가능한 작업 루트가 하나이면 기존 Control을 자동 clone·등록한다.
4. 기본 위치는 사용자가 이미 선택한 작업 루트의 `AgentsToZ-Control`; private 소스 실행에서는 검증된 byCS checkout의 형제 폴더를 제안할 수 있다. 여러 루트/목적지 충돌이면 한 번만 선택받고 저장한다. 설치 앱에서 개발자 절대경로를 추정하지 않는다.
5. GitHub 로그인이 없으면 연결 안내를 표시하고, 로그인 완료 후 동일 준비 작업을 재개한다. Supabase가 연결되지 않으면 폴더/등록 결과를 유지하고 기억 백업 연결 필요로 표시한다. 원격 기억 미확인 상태에서 빈 기억을 Push하지 않는다.
6. 동일 memoryId와 프로젝트 등록을 다시 조회하고 Control 바로 열기를 활성화한다. 기존 파일은 덮어쓰지 않고 재실행해도 중복 등록하지 않는다.

## 공개 clone 및 배포 앱 경로

공통 엔진과 Control 템플릿은 공개 소스와 앱에 포함한다. 공개 신규 사용자에게 개인 byCS의 Control URL/기억은 전달하지 않는다.

첫 실행: 이미 연결된 계정에 Control 프로필이 있으면 복원 제안 후 선택한 자동 복원 정책을 적용한다. 계정이 없거나 신규이면 OS 사용자별 앱 데이터에 로컬 프로필을 준비하는 한 번의 시작 동작을 제공한다. 프로젝트 등록·작업 루트 선택은 관제 프로필 준비의 선행 조건이 아니다. 최초 로컬 사용에 Google/Supabase/Vercel 가입을 강제하지 않는다. 기존 Control 폴더 연결이나 GitHub 저장소 생성과 공개 범위 선택, 원격 백업 설정은 후속 단계이며 개인 운영 기억용 저장소는 Private를 권장한다. 다른 Mac 동기화 준비가 완료된 경우에만 동기화 가능으로 표시한다.

Mac 배포본은 파일 접근과 CLI 프로세스 실행이 실제 배포 권한에서 가능한지 별도 검증한다. TestFlight 빌드가 host 역할을 제공하지 못하는 경우 UI에 별도 서명된 Mac host 연결 단계를 제공하며 ready로 위장하지 않는다. 이 계획만으로 Mac TestFlight 배포 가능성이 확인된 것은 아니다.

## 관제와 에이전트 연결

Control 화면은 폴더 유무와 무관하게 기본 노출하되 준비 전에는 상태와 다음 동작을 제공한다. 준비 후 채팅/지원되는 음성 입력은 같은 MCP·미션·Workroom 경로로 진행한다. Codex/Claude/Hermes/agy의 설치, 인증, MCP 인식, 실제 실행 증거를 각각 조회한다. 없는 CLI 때문에 Control 폴더 준비를 취소하지 않는다.

사용자가 요청한 첫 테스트는 Control 회상 → 등록 프로젝트 ID 조회 → 선택 에이전트의 짧은 작업 → 응답/결과 확인 순서로 진행한다. 설치/복원만으로 유료 AI 호출이나 이전 미션 재개를 시작하지 않는다. 앱 자동 음성 호출 지원 여부와 Control 준비 완료는 별개다.

## 구현 순서와 완료 증거

P0: 사용자 프로필 계약, 개인 설정의 public 제외 검사, 공통 준비 엔진, private source 시작 연결. 최우선 수용 사례는 사용자의 다른 Mac에서 Pull + 최신 런타임 실행 후 기존 Control 자동 복원, 기존 memoryId 일치, 재실행 시 중복 없음이다.

P1: 공개 신규/기존 사용자 온보딩, 계정별 공유 프로필 연동, 설치 패키지 시작 연결, GitHub 인증 후 재개. 신규 OS 계정과 별도 사용자로 검증한다.

P2: MCP/CLI별 실동작 검증, 모바일에서 동일 Control 접근, 배포 앱 업데이트 후 설정 유지, 실제 배포 경로 테스트.

검증 행렬:

- private 추가 Mac: 로그인 있음/없음, 루트 하나/여럿, 폴더 없음/미등록/이미 등록.
- public 신규 사용자: 개인 운영자 식별자 없음, 로컬 시작 가능, 자신의 Private 저장소 연동.
- public 기존 사용자: 원래 기억 복원, 다른 사용자 프로필 접근 불가.
- 반복/동시 실행: 한 폴더·한 등록, lease 중단 복구, 일시 네트워크 오류에서 새 ID 생성 없음.
- 실패: 잘못된 origin, memoryId 충돌, 쓰기 불가, clone 중 종료, 백업 미연결/실패에 대한 정확한 상태.
- 앱: 소스 Pull만 했을 때 구버전 실행 감지/안내, 업데이트된 패키지 첫 실행과 재실행, 모바일 동일 Control 표시.
- 오케스트레이션: 폴더 성공과 첫 AI 응답 성공을 분리해 실제 사용자 요청으로 확인.

기존 생성/clone/기억 Pull 계약과 공개 출하 검사, `bun run verify`, 격리된 실제 UI 테스트를 유지한다. 소스 테스트로 다른 Mac/TestFlight 설치 실증을 대신하지 않는다.
