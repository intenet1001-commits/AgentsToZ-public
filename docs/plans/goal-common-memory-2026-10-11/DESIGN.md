# 목표별 클라우드 공통기억 설계

상태: 아래 목표 구조를 앱·MCP·SDK에 구현하고 검증 중이다. 실제 구현 범위와 운영 적용·검사 결과는 EXECUTION.md를 따른다. 이 설계에 기재한 미래 자동화가 모두 구현됐다는 뜻은 아니다.

## 목표와 범위

기존 장기기억 여러 개를 선택해 목표별 공통기억을 만든다. 같은 장기기억은 여러 공통기억에 동시에 참여한다. 공통기억에는 각 목표와 적용 조건에 맞는 지식만 포함하고, 원본 갱신과 실제 적용 결과를 근거로 계속 관리한다.

사용자 사례:

| 원본 장기기억 | 공통기억 | 선별할 지식의 예 |
|---|---|---|
| A, B | 운전게임 | 조작·물리·게임 성능·검증에 해당하는 항목 |
| B, C | 아이폰 네이티브 앱 | iOS 생명주기·입력·권한·실기기 검증에 해당하는 항목 |

B의 모든 내용이 두 공통기억에 들어가지는 않는다. B의 한 항목이 두 목표에 모두 적합하면 양쪽에 참여할 수 있으며, 목표별 설명·적용 조건·검증 결과는 각각 유지한다.

OPS 운영기억, 프로젝트 DEV 기억, USE 서비스기억과 목표별 공통기억은 서로 다른 개념이다. OPS의 단일 프로필을 클라우드에 등록하는 방식으로 이 요구를 구현하지 않는다.

## 기존 장기기억과의 관계

| 기존 기능 | 공통기억에서의 사용 |
|---|---|
| `memoryId` | 원본 선택·접근 확인·계보 해석의 기준. 폴더·단말 ID로 대체하지 않음 |
| `entryId`, `contentVersionHash` | 항목의 동일성과 내용 변경을 따로 추적 |
| 기억 리비전·head CAS | 원본 스냅샷 검증과 공통기억 게시의 경쟁 감지에 재사용 |
| 기억 alias·merge 계보 | 원본 합병 뒤 대표 ID를 해석. 공통기억 생성은 merge RPC를 호출하지 않음 |
| curated / journal / feedback | 선별의 기본은 curated 항목. journal은 검토 근거, feedback은 검증 보조 근거 |
| 로컬 기억·Pull/Push | 원본 파일은 기존 정책대로 유지. 클라우드에 동기화된 리비전만 공통기억 처리의 확정 입력 |
| 기억 보관·휴지통 | 과거 출처는 보존하되 자동 신규 회상·갱신에서는 제외하고 상태를 표시 |
| 기존 저장 승인 | 기존 범위의 동의를 재사용해 원본을 쓰거나 새 AI 호출을 허용하지 않음 |

공통기억은 원본 장기기억을 교체하거나 원본에 역으로 쓰지 않는다. 공통기억에서 발견한 개선을 원본에도 반영하려면 별도 제안과 해당 원본의 기존 저장 절차를 거친다.

## 공통기억의 초기 계약

이름만으로 관련성을 판정하지 않는다. 초기 설정은 다음 내용을 하나의 버전으로 확정한다.

1. **목표**: 어떤 결과를 돕는 기억인지 구체적인 문장으로 작성한다.
2. **포함 범위와 제외 범위**: 필요한 주제, 플랫폼, 작업 단계, 사용할 수 없는 조건을 작성한다.
3. **원본 선택**: 기존 `memoryId`를 선택한다. 선택 가능한 원본인지 현재 권한·휴지통·계보를 다시 확인한다.
4. **적용 예시**: 포함될 사례와 제외될 사례를 최소 하나씩 작성한다.
5. **검증 기준**: 적용 성공을 어떤 관찰·테스트·사용자 확인으로 판단할지 작성한다.
6. **운영 정책**: 원본 변경 시 후보 생성 방식, 게시 승인 방식, AI 제공자·예산·점검 조건을 선택한다.

목표·범위가 바뀌면 `goalVersion`을 올린다. 이전 목표에서 검증된 지식은 새 목표에서 자동으로 검증 완료가 되지 않는다. 새 목표로 재검토할 항목과 기존 게시본을 구분한다.

기본 정책은 원본 변경 감지는 토큰 없이 수행하고, 신규·의미 변경·충돌 후보는 검토 후 게시하는 것이다. 자동 AI 선별과 자동 게시의 허용 범위는 각각 명시적으로 설정한다. 공급자·모델은 기존 설정을 임의로 고르지 않는다.

## 데이터 모델

정체성과 정의는 동일한 Supabase 연결에 공유한다. 단말에는 실행 큐·로컬 사본·접속 상태만 둔다. 단말 `device_id`는 실행 근거일 수 있으나 공통기억의 소유 키가 아니다. 클라우드 연결 URL·권한이 달라지면 동일한 이름을 근거로 다른 클라우드의 공통기억에 합류하지 않는다.

| 개체 | 주요 필드와 계약 |
|---|---|
| `common_memory` | `groupId`, 표시명, 상태, `goalVersion`, 목표·포함·제외·정책, `configRevision`, `publishedRevisionId` |
| `common_memory_source` | `(groupId, sourceMemoryId)` N:N 연결, 원래 선택한 ID와 현재 canonical ID, 원본별 처리 위치 |
| `common_memory_item` | 안정적인 `itemId`, 규칙·이유·적용 조건·예외·주제, 현재 상태. 원본 항목 ID와 별개 |
| `common_memory_evidence` | `itemId`, 원본 `memoryId/entryId/revisionId/contentVersionHash`, 검증된 발췌·발췌 hash, 출처의 역할 |
| `common_memory_revision` | 게시된 항목 집합, 목표 버전, 처리한 원본 스냅샷, parent, 작성·승인 근거. 게시본은 불변 |
| `common_memory_review` | 후보·관련성 이유·충돌·보류 이유·검토 결과, 기준 목표/원본/게시 리비전 |
| `common_memory_application` | 실제 작업에서 선택한 게시 리비전·항목·적용 조건, 작업/테스트 근거와 관찰 결과 |
| `common_memory_job` | 변경 처리·점검의 idempotency 키, 상태, 입력 hash, 실행 lease, 재시도 근거 |

파생 본문은 전용 `common_memory_revision`에 저장한다. 원본 프로젝트의 리비전 테이블에 공통기억 행을 넣으면 구버전 장기기억 목록·계보·합병이 파생 기억을 원본 프로젝트로 오인할 수 있으므로, 그 테이블과 원본 ID는 유지한다. 원본 읽기는 기존 장기기억 어댑터를 재사용하고, 파생 본문의 hash·크기·불변 리비전·head CAS는 기존 계약과 같은 검증 규칙을 사용한다. 공통기억의 목표·연결·출처·평가 관계도 전용 메타데이터로 둔다. 본문을 기존 레저와 새 레저 양쪽에 중복 저장하지 않는다.

원본의 오래된 전체 리비전이 보존 정책에 따라 정리돼도 증거가 사라지지 않도록, 공통기억은 사용한 항목의 검증된 발췌와 hash를 자체 보존한다. 기존 전체 리비전 보존 기간을 무제한으로 늘려 해결하지 않는다. 원본 최신 상태와 과거 적용의 근거는 별도로 표시한다.

## 선별과 정리

단순 키워드 일치나 원본 간 문장 교집합만으로 공통지식을 확정하지 않는다. 후보마다 다음 판단을 남긴다.

- 목표의 어느 부분에 도움이 되는지와 포함/제외 규칙에 대한 근거.
- 적용 가능한 플랫폼·상황·버전·예외.
- 직접 확인한 출처와 원본 내용 버전.
- 원본 진술, 목표에 맞게 적용한 해석, 여러 원본에서 확인된 규칙의 구분.
- 모순, 오래된 근거, 확인되지 않은 추론.

한 원본의 항목도 목표에 적합하면 포함할 수 있다. 원본 두 개에 같은 문장이 있다는 이유만으로 검증 수준을 높이지 않으며, 복제된 기억 두 개를 독립 근거로 계산하지 않는다.

동일 규칙은 하나의 공통 항목에 여러 출처를 연결한다. 서로 다른 적용 조건은 조건별 규칙으로 둔다. 충돌은 후보나 보류 상태로 남기고, 최근 날짜나 AI 점수만으로 한쪽을 삭제하지 않는다. 최종 항목은 **규칙 → 이유 → 적용 조건 → 예외 → 근거 → 검증 상태**를 갖는다.

## 계속 갱신하는 흐름

```mermaid
flowchart LR
  A[원본 갱신·동기화] --> B[변경 항목 감지]
  B --> C[각 목표별 관련성·조건·충돌 검토]
  C --> D[추가·수정·보류 후보]
  D --> E[검토·CAS 게시]
  E --> F[작업별 관련 항목 회상]
  F --> G[실제 적용·결과 근거]
  G --> H[누락·오적용·충돌 개선]
  H --> D
```

1. 원본 head/hash 변화와 `entryId/contentVersionHash` 차이를 토큰 없이 확인한다.
2. 그 원본에 연결된 공통기억에 각각 독립적인 검토 작업을 만든다. B의 변경이 운전게임과 아이폰 앱에 같은 결론을 강제하지 않는다.
3. 변경된 항목과 그 항목에 의존하는 파생 항목을 재평가한다. 변경되지 않은 전체 기억을 매번 AI로 다시 읽지 않는다.
4. 신규·수정·충돌·삭제 근거·적용 조건 변경을 별도로 후보화한다. 원본에서 사라졌다고 공통기억의 과거 항목을 즉시 지우지 않는다.
5. 검토 후 게시 직전에 목표·멤버십·원본 head·기존 게시 head를 다시 확인한다. 바뀌었으면 후보를 재검토 상태로 돌린다.
6. 게시와 처리 위치 전진은 같은 트랜잭션으로 기록한다. 실패한 작업의 cursor를 완료로 전진시키지 않는다.
7. 사용 중인 작업은 선택한 불변 게시 리비전을 유지한다. 이후 갱신이 이미 시작한 작업의 기억을 조용히 바꾸지 않는다.

AI 판단 결과가 없거나, 연결이 실패하거나, 입력 예산을 초과하면 후보를 보류한다. 빈 결과를 “관련 내용 없음”으로 기록하지 않는다. 미래 형식을 읽지 못하면 처리 위치를 멈춘다. 큐는 그룹별·클라우드별로 제한하고, 재시도는 동일한 입력·작업 ID에 결속한다. 변경 감지 주기 자체는 AI 호출 권한이 아니다.

## 적용 점검과 개선

회상됐다는 사실은 적용 성공이 아니다. 확인할 세 단계를 나눈다.

| 단계 | 질문 | 근거 |
|---|---|---|
| 선별 품질 | 목표에 맞는 규칙을 고르고 관련 없는 내용을 제외했는가? | 초기 포함/제외 사례, 누락·혼입 검토 |
| 적용 정확성 | 실제 작업 조건에 맞는 규칙을 사용했는가? | 사용한 항목·조건·작업 결과, 미적용·오적용 이유 |
| 결과 유효성 | 적용으로 기대한 결과가 확인됐는가? | 관련 테스트·관찰·사용자 확인. 성공을 기억 하나의 효과로 단정하지 않음 |

`검증됨`, `관찰됨`, `관련 테스트 없음`, `판단 보류`를 구분한다. 테스트 이름만 등록하거나, 회상 횟수만 늘리거나, AI가 자기 답변에 동의한 것은 검증 근거가 아니다.

실패·혼입·누락·충돌·목표 변경을 개선 후보로 연결한다. 재현 가능한 오적용은 조건 수정과 회귀 사례로 남긴다. 유효한 기존 규칙은 폐기 대신 적용 조건 조정이나 superseded 상태로 바꾸고 이전 게시본은 복구 가능하게 둔다.

자동 점검은 목표 변경, 의존하는 원본 항목 변경, 실제 적용 실패 같은 명확한 사건을 우선한다. 사용자가 설정한 정기 점검은 변경 감지만 반복할 수 있으며, 근거 없이 같은 기억 전체를 반복 평가하거나 이미 끝난 AI 작업을 재실행하지 않는다.

## 사용자 흐름

1. 클라우드 장기기억 목록에서 여러 원본 선택 → 공통기억 만들기.
2. 이름·목표·포함/제외·검증 사례·갱신 정책 작성.
3. 원본별 선별 결과·통합 결과·출처·충돌을 확인하고 첫 게시.
4. 공통기억 화면에서 원본 연결, 게시 내용, 변경 후보, 적용 점검 결과 관리.
5. 작업에서 공통기억을 선택하면 해당 목표·작업 조건에 맞는 bounded 기억만 사용.
6. 작업 결과에서 적용 여부·실패/누락 근거를 기록하고 개선 후보 확인.

공통기억을 선택한 작업만 해당 기억을 적용한다. B가 어느 그룹의 원본이라고 해서 B의 모든 작업에 모든 그룹의 기억을 주입하지 않는다. 서로 다른 그룹을 함께 선택한 경우에도 충돌과 적용 범위를 표시한다. AI 연결·실행 성공·로컬 저장·클라우드 게시 상태는 각각 확인한다.

## 호환성과 확장성의 구현 순서

| 단계 | 결과 | 통과 조건 |
|---|---|---|
| 1. 데이터·API 계약 | 그룹·N:N 원본 연결·목표 버전·불변 게시·출처 구조 | 기존 ID/파일/alias를 변경하지 않고 A+B, B+C가 동시에 존재 |
| 2. 초기 설정과 관리 | 클라우드 목록 선택·목표 설정·후보 검토·게시·편집·보관 | 단말 두 곳에서 같은 그룹/내용 조회, 실패를 빈 목록으로 표시하지 않음 |
| 3. 변경 반영 | 원본 변경 감지·항목별 후보·재검토·게시 CAS | B의 변경이 두 목표에 독립적으로 처리, 중복 실행·cursor 누락 없음 |
| 4. 작업 적용 | 명시적으로 선택한 그룹·목표·조건·게시본에 결속한 회상 | 다른 그룹 혼입 없음, 시작한 작업의 리비전 유지, 토큰 예산 준수 |
| 5. 적용 점검·개선 | 실제 결과 근거·오적용 회귀 사례·조건 개선·복구 | 회상과 적용/검증 구분, 자동 자기확증 없음, 원본 역쓰기 없음 |

새 기능의 구버전 호환 범위는 원본 기억 읽기·저장 유지다. 구버전 단말이 새 그룹을 지원한다고 표시하지 않는다. DB 변경은 버전 migration과 앱 설치 SQL 정본에 함께 반영하고, 미적용 상태는 명확한 기능 미준비 상태로 처리한다. 웹은 기존 인증·멤버십을 사용하고, 서버 비밀키를 프론트엔드에 보내지 않는다. 그룹 정의·게시·검토·점검 근거의 권한은 동일한 클라우드 경계를 따르며, 단말 실행 lease와 별개다.

## 필수 수용 검사

- A+B 운전게임과 B+C 아이폰 앱을 함께 만들고 B의 소속·원본 ID가 유지된다.
- B의 게임 관련 변경은 운전게임 후보로만 반영된다. B의 iOS 관련 변경은 아이폰 후보로만 반영된다. 두 목표에 적합한 변경은 각기 다른 조건과 근거를 갖는다.
- 한 원본의 유효한 지식은 포함할 수 있고, 복제된 두 원본을 독립 검증으로 계산하지 않는다.
- 원본 항목 변경·목표 변경·원본 연결 변경·동시 게시가 오래된 검토 결과를 게시하지 못한다.
- 원본 alias 합병·휴지통·원격 리비전 정리 후에도 출처와 과거 적용 근거를 읽을 수 있다.
- 클라우드 연결 실패·접근 거부·미적용 migration·부분 스캔이 “그룹 없음/변경 없음/점검 완료”로 표시되지 않는다.
- 실제 적용되지 않은 항목이 회상만으로 검증됨이 되지 않는다. 테스트 없는 결과와 실패 원인 미확정은 판단 보류다.
- 첫 게시·후속 업데이트·편집·보관·이전 게시 복구가 다른 단말에서도 일관된다.
- 자동 후보 생성·AI 호출·게시 정책의 경계를 지키고, 재시작·중복 요청·큰 기억에서 작업을 잃지 않는다.
- 일반 장기기억·OPS·USE·워크룸의 기존 저장·승인·백업 회귀가 유지된다.

## 현재 코드 근거

- `src/projectMemoryRecall.ts`: 안정적 항목 ID, 내용 버전 hash, 조건부 feedback와 회상.
- `project-memory-server.ts`: 로컬 기억 원본, 리비전 Pull/Push, head CAS, 원본 계보 해석.
- `src/projectMemoryMerge.ts`, `src/schemaSql.ts`: 기존 계보 합병과 단일 기억 연결. N:N 공통기억 생성에서 합병 호출을 재사용하면 안 된다.
- `src/PortalMemoryDirectory.tsx`: 클라우드 장기기억 목록·계보·기기·합병·보관 관리의 현재 진입점.
- `src/controlProfileStore.ts`, `src/serviceMemory.ts`: OPS/USE 정체성. 목표별 공통기억의 소유 키로 사용하지 않는다.
- `docs/resource-management.md`: dispatcher 예산·workspace lease·영속 작업·원본 보존 계약.

## SDK와 새 프로젝트의 연결

공통기억 목표의 `sdkModules`는 SDK 카탈로그의 안정적인 모듈 키를 참조한다. 프로젝트 생성에서 “무엇을 만들까요?”를 입력하고 목표별 공통기억 후보·조건·관련 SDK를 확인한 뒤 선택한다. MCP는 같은 계약으로 후보를 제시하고 대화에서 선택을 받는다. 선택한 `groupId/revisionId/goalVersion`을 생성 직전 다시 검증한다. 추천 뒤 게시본이 바뀌면 재선택을 요구한다.

현재 등록된 `SDK` 프로젝트와 GitHub 저장소, 고정 `memoryId`를 그대로 사용한다. 다른 Mac은 같은 저장소를 Clone/Pull하고 이 Mac의 경로·도구로 모듈을 준비한다. 저장소의 `.agentstoz/sdk-project.json`에는 상대 경로·모듈·목표·준비 규칙만 둔다. 기존 플랫폼 SDK와 새 공통기억 SDK의 코드 버전, 목표별 공통기억 게시 버전, 프로젝트 원본 기억을 각각 관리한다.
