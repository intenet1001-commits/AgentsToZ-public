# 커뮤니티 업무 스레드

커뮤니티는 아젠투지 기기별 채널에서 등록 프로젝트들을 `@`로 호출하고, 각 프로젝트의 실제 워크룸으로
업무를 실행하는 화면이다. 기존 운영 프로필 단체방은 **아젠투지 단톡방**으로 표시한다.
일반 단톡방 메시지는 AI에 자동 입력하지 않는다. 새로운 AI 실행 엔진이나 CS-CEO 미션을 만들지 않는다.

## 사용 흐름

1. Mac 메인 창 왼쪽의 **대화 세션 → 커뮤니티 · 업무 스레드**, 휴대폰 홈의 같은 버튼 또는 원격 작업의
   **더 보기 → 커뮤니티**를 연다.
2. `#아젠투지 1호`처럼 실행 기기를 고른다. 프로젝트 선택 상자나 입력칸의 `@` 후보에서
   정확한 등록 프로젝트/워크트리를 선택한다. 입력칸의 `@` 후보 또는 **프로젝트 추가**로 같은 기기의 프로젝트를 최대 8개까지 호출한다. 추가 호출은 기존 대상을 바꾸지 않으며 호출 칩에서 취소할 수 있다. 기준 프로젝트는 위 목록에서 바꾼다. `#기기명`은 채널, `@프로젝트명`은 실행 대상, 본문의 `#프로젝트명`은 참고이며 실행을 추가하지 않는다. 같은 이름의 다른 기기로 자동 추정하지 않는다.
3. AI와 업무를 선택해 **업무 맡기기**를 누르면 모든 프로젝트의 권한·폴더·진행 중 업무를 검사한 뒤 공동 스레드와 프로젝트별 실행 의도를 한 transaction으로 저장한다. 호출한 프로젝트마다 별도의 워크룸 세션을 연다. 결과는 `@프로젝트` 이름을 붙여 같은 업무 스레드에 모인다. 프로젝트별 스레드 목록에서 이전 업무를 찾는다.
4. 공동 스레드에서는 **답변할 프로젝트**를 선택해 그 워크룸에만 답하거나, 프로젝트별 **워크룸 열기**에서 입력한다. 최초 업무는 모든 호출 대상에 전달하며 후속 답변은 선택한 대상 한 곳으로 보낸다. 워크룸의 전체 요청
   입력칸에서 제출한 답변도 같은 스레드에 기록한다. 화면 이동과 재조회는 실행을 재전송하지 않는다.
5. 업무 결과와 프로젝트 기억 저장을 별도로 확인한다. 스레드의 **세션 기억하기**는 기존
   `workroom.save` dispatcher·권한·영수증을 사용한다. 자동 저장은 기존 opt-in 설정을 따른다.

프로젝트 입력만 선택됐던 휴대폰 진입도 수정했다. 실행 중인 세션이 있으면 해당 세션을 열고,
없으면 새 작업 화면을 연다. 다른 커뮤니티 기기를 보고 있어도 연결된 Mac의 프로젝트 진입은
그 Mac으로 돌아온다. 프로젝트 보기만 열었다고 유료 AI 요청을 시작하지 않는다.

## 실행과 기록 계약

- 단일 업무는 등록 target ID·폴더 지문·작성 주체·정확한 워크룸 session ID에 결속한다. 공동 업무는 그 결속을 프로젝트별 자식 기록에 보존하고, 암호화된 부모 기록에 참가자와 공통 이벤트 순서를 유지한다. 자식 기록 변경과 부모의 질문·결과 반영은 같은 SQLite transaction이다. 같은 프로젝트의 ‘가장 최근 세션’을 재사용하지 않는다.
  디렉터리 교체·연결 권한 변경은 실행 직전에도 확인한다.
- `starting`, `running`, `needs-answer`, `completed`, `failed`, `unknown`, `closed`를 구분한다.
  접수·창 열림·CLI 종료를 업무 완료로 판단하지 않는다. 완료는 연결 워크룸 AI의 결과 게시다.
- AI는 `agentstoz_use_publish_workroom_thread`로 진행·질문·결과를 게시한다. 이 도구는
  호출자의 워크룸을 호스트에서 찾으며 thread ID·대상·경로·명령을 받지 않는다.
  기존 OPS MCP 인증과 프로세스/워크룸 caller binding을 사용한다. caller 힌트 자체는 별도 보안 경계가 아니다.
- Claude/Codex의 정확한 대화 완료 기록에 최종 공개 답변이 있으면 같은 업무 스레드에도 남긴다.
  먼저 도구로 게시한 결과와 본문이 다르면 두 기록을 보존한다. 같은 요청·프로젝트의 동일 본문만
  중복을 막으며, 긴 답변의 연속 조각도 원문 전체로 비교한다. 다른 프로젝트의 같은 답변은 각각 남긴다.
- CLI의 신뢰·승인 대기 화면은 기존 headless 화면 분류가 안정됐을 때 **관찰한 질문 화면**으로
  기록한다. 해당 승인·메뉴 선택은 연결 워크룸의 실제 선택지에서 답한다. 스레드의 일반 문장을
  메뉴의 Enter로 번역하거나 자동 승인하지 않는다. 원본 터미널의 모든 재그리기·개별 키 입력을 채팅 발언으로
  추정하지 않으며, 구조화된 게시와 전체 요청 입력이 대화 기록의 기준이다.
- 사용자의 업무/답변 request ID는 불변이다. 최초 업무는 기존 전체 요청 launch receipt,
  답변은 submission receipt와 input revision으로 PTY 쓰기를 보호한다. 양쪽의 동시 답변은
  thread revision과 실제 input revision을 모두 통과해야 한다.
- 워크룸 입력의 스레드 기록 의도를 PTY 쓰기 전에 저장하고, 실제 쓰기 후 전달 상태를 확정한다.
  기록의 복제는 CLI에 다시 입력하지 않는다. 응답 유실·부분 쓰기는 `unknown`으로 보존한다.
- 접수 전에 확실하게 거절한 경우만 별도 `refusal` DTO로 돌려 초안을 유지한 채 편집하게 한다.
  전송 결과가 불확실하면 원래 ID의 **전송 결과 확인**을 사용하며 새 ID로 자동 실행하지 않는다.
- 새 커뮤니티에서 같은 checkout의 미완료·미확정 업무를 동시에 시작하지 않는다. 완료된 스레드의 후속 답변도
  그 checkout을 다시 예약한다. 다른 업무가 이미 사용하면 기존 스레드나 별도 워크트리를 선택한다.
- 확인이 필요한 스레드는 사용자가 워크룸을 확인한 뒤 **스레드 종료 표시**할 수 있다.
  실제 CLI를 종료하거나 작업 완료·기억 저장 성공을 만들어 내지 않는다.
  앱 재시작 전의 미완료 워크룸도 조회 시 결과 확인 상태로 바꾸며, 확인 없이 checkout을 재사용하지 않는다.

## 종료된 워크룸과 긴 대화

창 닫기는 보기만 닫으며 실행 중인 CLI는 유지한다. 실제 CLI 종료를 호스트가 관찰했고 모든 사용자
전송이 확정됐으면 후속 글을 접수한 뒤 원래 저장 대화로 다시 연다. 기존 history의 provider 결속,
계정·프로젝트 지문, 단일 실행 lease와 resume 영수증을 사용한다. 저장 대화가 없거나 모호하면
새 대화로 추정하지 않고 요청을 보존한다. 지원 범위는 기존 history와 같은 Mac의 Claude/Codex다.
앱 강제 종료·미확정 전송은 관찰된 정상 종료와 구분하며 자동 재전송하지 않는다.

설치 Mac에서 기존 자동 기억 저장을 켠 프로젝트의 Community 워크룸은 70% 체크포인트를 사용한다.
기존 15초 유지보수 tick과 동일 dispatcher를 쓰고, 해당 실행에는 legacy 50/75/90% 저장을 중복 적용하지 않는다.
화면 하단 수치나 스레드 길이로 판단하지 않는다. 정확한 provider 대화의 사용률 관찰과 현재 입력 revision의
실제 transcript 턴 완료가 모두 필요하다. 실행 중·승인 대기·추가 입력은 세션 교체를 막는다.

저장 intent와 고정 요청 ID를 먼저 기록한다. 로컬 저장 영수증·입력 revision·프로젝트 활동을
기존 `memoryPolicy=saved` 종료 가드로 확인한 뒤 CLI를 종료한다. 백업 결과는 별도로 표시한다.
V2의 일부 구간만 저장되었거나 복구/추가 저장이 남으면 종료하지 않는다. 실패·미확정 저장은 같은
세션에서 자동 재실행하지 않는다. Mac에서 저장/복구 상태를 확인하고 수동으로 이어갈 수 있다.

다음 신규 글이 오면 같은 CLI 계정의 새 컨텍스트를 열고 프로젝트 기억과 기존 스레드를 읽도록
인계한다. 새 워크룸만 `agentstoz_use_read_workroom_thread`로 자기 스레드를 페이지 조회할 수 있다.
호출자가 thread ID·경로·계정을 지정하지 않는다. 과거 요청을 다시 수행하라는 지시로 취급하지 않으며,
원문은 기존 암호화 저장소에 보존한다. 이전 session ID는 계보로 남고 이전 세션의 늦은 입력/게시를 차단한다.
CLI가 로그인·신뢰 승인을 기다리면 신규 글을 보존하고 자동 입력하지 않는다.

Mac과 원격 워크룸의 숫자 키는 한 번의 실제 키 입력을 보낸다. Codex의 일부 메뉴는 숫자 자체로
확정되므로 Enter를 자동 추가하지 않는다. 기본 1·2·3과 **더보기 → 4~9·0**을 제공하며,
필요한 경우 기존 Enter 키로 확정한다. 숫자 버튼은 휴대폰 키보드를 강제로 열지 않는다.
입력이 잠겼거나 전송에 실패하면 이유를 표시하며 자동 재시도하지 않는다.
실제 A 프로젝트의 Codex 0.163.0 `/hooks` 화면처럼 숫자 선택이 없는 목록은 방향키·Enter·Esc 안내를
표시하며, 숫자를 `trust all` 승인으로 바꾸지 않는다.

## 권한과 보존

새 workspace 동작은 `workroom.threads.*`, 기능 표시는 `workroom-threads-v1`이다.
기존 encrypted relay와 community 제어 경로를 재사용하며 새 클라우드 테이블이나 공개 서버는 없다. 로컬 SQLite에는 해시된 참가자 색인만 추가한다. 최초 공동 업무 접수 시 메타 버전을 2로 바꾸어 이전 앱이 새 기록을 쓰지 못하게 하며, 기존 단일 업무와 암호화 키는 유지한다. 새 화면은 조회 시 `requireMultiProject` 계약으로 구형 호스트를 확인하므로 지원하지 않는 호스트에 실행 요청부터 보내지 않는다.
휴대폰 요청은 공동 업무에 참가한 모든 프로젝트의 기존 grant를 다시 검사한다. 표시용 control ID는 호스트에서 runtime target ID로 해석하고 응답에서 다시 그 연결의 control ID로 되돌린다. 다른 참가자의 권한이 없으면 공동 기록을 노출하지 않는다. 승인된 프로젝트의 업무 스레드는 작성 기기와 관계없이 Mac·모바일에서 함께 조회하고 답변한다. 공동 업무의 내부 참가자 기록은 직접 조회·답변하지 못하며 항상 모든 참가자의 권한을 확인하는 공유 스레드를 이용한다.
업무 스레드 공유는 원본 워크룸 대화 기록의 `history.read`·`history.resume` 권한과 별개이며, 이 권한을 자동 부여하거나 프로젝트 허용 범위를 늘리지 않는다. 생성 시 기록한 owner와 요청 영수증은 그대로 보존한다. Mac 로컬 사용자는 해당 Mac의 업무를 보며, 다른 community endpoint의 기록 소유는 인증된 발신 endpoint로 분리한다. 기존 `workroom.status/save`의 owner 계약은 유지한다.

본문은 앱 데이터의 `workroom-threads.v1.sqlite`에 AES-256-GCM으로 암호화한다. 기존
메타데이터 전용 Workroom history DB에 대화 본문을 넣지 않는다. 전용 Keychain/DPAPI 키,
0600 파일, 소유 파일 잠금, FULL 동기화 SQLite transaction을 사용한다. 키 유실·불일치 때
새 키로 기존 기록을 덮어쓰지 않는다. UI의 sessionStorage에는 미확정 요청 ID만 저장한다.

입력/게시 6,000 UTF-8 bytes(기호·줄바꿈의 JSON 확장 뒤 6,100 bytes도 적용), 스레드당 512개 이벤트·512 KiB, 호스트 1,000개 스레드·100 MiB,
미완료/미확정 업무 32개를 상한으로 한다. 목록은 최근 20개 이하와 6,500-byte 예산,
단일 업무 본문은 20개 이하와 같은 예산으로 페이지화한다. 공동 업무 본문은 JSON 확장 기준 1,200-byte 조각으로 원문을 손실 없이 나누고 참가자 영수증을 포함해 7,800-byte 예산으로 페이지화한다. 전체 8,500-byte wire 한도는 유지한다.
원본이나 미완료 업무를 자동 삭제해 예산을 맞추지 않는다. 화면 폴링은 열린 스레드만 8초,
기억 상태는 15초이며 숨김·종료 때 멈춘다. CLI 자체의 기존 최대 12개 상한도 유지한다.

## 검증

- `community-threads`: 실제 암호화 SQLite, 실제 terminal submission 서비스와 합성 PTY.
  중복 접수·양쪽 답변·권한·폴더 지문·응답 유실·키 유실·재시작·질문 화면·종료 상태. 복수 프로젝트의 동시 접수·각기 다른 워크룸·공동 질문/결과·선택 답변·일부 시작 실패·휴대폰 ID 매핑·긴 메시지 페이지 보존을 포함한다.
- `community-threads-screen`: 실제 React + 위 저장소/서비스, 합성 CLI. Chromium/WebKit에서
  채널·타이핑 멘션·질문·답변·워크룸 연결·초안·기억 저장·44px 터치 영역을 조작한다.
- `phone-workroom-entry-screen`: 같은 두 엔진에서 세션 없음/있음, 다른 프로젝트 전환,
  목록 조회 실패와 새 AI를 자동 실행하지 않는 진입을 검사한다. 수정 전 HEAD는 빈 세션에서 실패한다.
