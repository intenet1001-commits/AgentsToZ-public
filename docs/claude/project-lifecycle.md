## 유휴/오래됨 판정 — 활동 기준은 한 벌뿐

`lastActivityFor(id)` = **max(앱 방문 `lastVisits`, git 커밋 `gitActivity`)** 하나만 쓴다.
행에 찍히는 날짜·정렬·섹션 카운트·유휴 소그룹·정리 검토 라벨이 **전부** 이 값을 봐야 한다.

- ⚠️ **소그룹만 `lastVisits`를 보던 버그가 있었다.** 앱에서 연 적은 없지만 커밋은 최근인
  프로젝트가 행에는 "4일 전"으로 뜨면서 동시에 "오래됨(30일+/기록 없음)"으로 분류됐고,
  그대로 정리 검토의 **삭제 후보**에 올랐다. 실측(2026-08-14) 97개 중 7개가 이 상태였다
  (Test0809·인증·airflow·mobiletest·myjob1 등, git 4~14일 전). 며칠 전 커밋한 프로젝트를
  지우라고 권하고 있었던 셈이다.
- `useMemo` deps에 **`gitActivity`를 반드시 넣는다** — 빠지면 커밋 후에도 옛 분류가 남는다.
- 정리 검토 라벨 문구는 "N일 전 **활동**"이다. "방문"이라고 쓰면 git 커밋을 세지 않는
  것처럼 읽히고, 실제로 그 문구였을 때 기준이 갈라져 있었다.
- **오래됨 기준 일수는 설정값**이다(`portmanager-stale-days`, 기본 30, 기기별 localStorage).
  1~3650 밖의 값은 기본값으로 되돌린다 — 0이면 전부 "오래됨"이 되어 정리 검토가 통째로
  위험해진다. `IDLE_RECENT_MS`(7일)는 고정이다.

## 정리 검토 행 — 지우기 전에 폴더와 장기기억을 보여준다 (2026-10-04)

행마다 「폴더 열기」와 **폴더·장기기억 상태**를 적는다(`src/cleanupFolderStatus.ts`가 판정 정본).
107개 목록에서 무엇을 지우는지 알 방법이 없었고, 연결된 폴더가 이미 사라진 행도 멀쩡한 행과 같아 보였다.

- 상태는 셋이다: 있음 / 없음 / **알 수 없음**. ⚠️ **확인하지 못한 것을 「없음」으로 단정하지 않는다** —
  조회 전, 조회 실패, 경로 없는 프로젝트는 모두 「알 수 없음」이고 그때 「폴더 열기」는 비활성이다.
- 조회는 `POST /api/folder-memory-status`이고 **폴더마다 stat 두 번**이다(폴더 존재 +
  `.agent-memory/config.json`). ⚠️ **`detectProjectMemory`를 쓰지 말 것** — 폴더마다 git을 여러 번
  띄워 107개면 수백 spawn이다. 모달을 열 때 한 번만 쓸고 폴링하지 않는다.
- 그래서 **링크된 워크트리처럼 기억이 주 체크아웃에 있는 경우는 「없음」으로 보인다.** 표시 전용
  값이며 삭제 경로의 근거가 아니다 — `cleanupProject`는 여전히 자기 경로로 보관을 시도한다.
- 삭제 확인 문구도 이 상태를 따라 실제로 보관될 것을 말한다(연동/없음/폴더 없음/알 수 없음).

## 포트 삭제 — 로컬만 지우면 원격 행이 영영 남는다

삭제 표면은 **정리 검토와 카드/상세 두 곳**이고, 둘 다 `cleanupProject` 하나를 쓴다
(보관 → 원격 삭제 → 로컬 삭제). 각각에 「로컬만 삭제」와 「Supabase 포트 정보까지 삭제」를
나란히 둔다 — 한쪽만 원격 정리를 하면 나머지 경로가 조용히 고아를 만든다.

- **로컬만 지우면 그 원격 행은 회수 불가**가 된다. id가 로컬에서 사라져 다음 push의
  stale-delete 대상에도 들지 못하기 때문이다. 실측 150행 중 138행이 그 상태였다.
- 정리 검토의 **「Supabase 잔여 정리」**(`cleanup-orphans`)가 유일한 회수 경로다.
  버튼을 눌러야 조회한다 — 모달을 열 때마다 원격을 때리지 않는다.
- ⚠️ **"내 로컬 목록에 없다"는 쓰레기라는 뜻이 아니다.** 다른 기기가 소유한 행은 그
  기기에서 쓰이고 있다. 그래서 소유자별로 갈라 분류하고, 회수 가능한 것
  (내 기기 소유인데 로컬에 없음 / `device_id` 없음 / 등록되지 않은 기기)만 기본 대상으로
  제시한다. 다른 기기 소유는 기기명과 개수를 밝히고 `cleanup-orphan-delete-other`라는
  **다른 testid**로 분리해 실수 클릭과 구분한다.
## 장기기억 아카이브 — 지워도 노하우는 남긴다

프로젝트를 정리하면 `.agent-memory/`도 함께 사라진다. 거기 적힌 것은 그 프로젝트만의
사실이 아니라 다음 프로젝트에서도 쓰이는 지식이다. 그것이 함께 사라지면 **사용자가 안 쓰는
프로젝트 지우기를 두려워하게 되고, 정리 검토 자체가 작동하지 않는다.**

| | |
|---|---|
| 보관 위치 | `~/Library/Application Support/com.portmanager.portmanager/memory-archive/` — 본문 `.md` + 메타 `.json` |
| 파일명 | `YYYY-MM-DD-<이름>-<프로젝트코드>.md` |
| 대시보드 | 헤더 아카이브 아이콘(`memory-archive-toggle`) → 검색·본문 보기·전체 복사 |
| 엔드포인트 | `POST /api/memory-archive` (보관) · `GET /api/memory-archive[?file=]` (목록·본문) |

- **정리 순서는 보관 → 원격 삭제 → 로컬 삭제**(`cleanupProject`, App.tsx). 로컬을 먼저 지우면
  `folderPath`를 잃어 **기억을 보관할 수 없다.**
- **보관 실패는 삭제를 막지 않는다**(복사일 뿐이므로). 반대로 **원격 삭제가 실패하면 로컬도
  남긴다** — 로컬만 지우면 id를 잃어 그 원격 행은 어떤 push로도 회수할 수 없게 된다.
- 원격 삭제는 **id 기준**이라 `device_id`와 무관하다. 실측(2026-08-13) 150행 중 138행이 현재
  기기 소유가 아니어서 stale-delete 범위 밖이었다 — 그 잔류를 정리하는 유일한 경로다.
- 문서는 반드시 `readMemoryDocument`로 읽는다. 분해된 기억을 `readFileSync`로 읽으면 색인만
  보관되고 본문을 잃는다.
- ⚠️ **아카이브에는 삭제 기능을 두지 않는다.** "지워도 노하우는 남기려고" 만든 곳에 삭제를
  두면 같은 실수를 한 단계 뒤로 미루는 것뿐이다. 정말 지우려면 Finder에서 폴더를 연다.
