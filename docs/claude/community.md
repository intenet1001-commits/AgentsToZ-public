## 기기 간 대화 — 커뮤니티가 기본이다 (2026-10-04)

「누가 누구를 부른다」를 버리고 **각자 단체방에 입장**하는 모델로 바꿨다. 쌍 단위는 기기 3대면 3쌍,
4대면 6쌍으로 늘고 매번 상대를 골라야 한다. 커뮤니티는 입장 한 번이 끝이고 **나가지 않는 한 계속**이라
만료 개념도 없다. 판정은 화면은 `src/agentDialogueCommunity.ts`, 엔진은 `community-*` RPC 한 곳이다.

- **프로필당 단체방 하나.** `portmgr_agent_dialogue_rooms.kind='community'`이고 `profile_id`에
  부분 유니크 인덱스가 걸려 둘이 될 수 없다. **초대가 없다** — 같은 운영 프로필의 활성 endpoint면
  누구나 입장할 수 있고, 그 입장이 곧 동의다. 프로필·기기 키·endpoint 상태 검사는 그대로다.
- ⚠️ **커뮤니티는 만료·유휴 종료 대상이 아니다**(`prune`이 `kind='room'`만 닫는다). 그래서 본문은
  방이 닫혀서가 아니라 **30일 나이로** 지운다. 메시지 상한도 2,000이 아니라 20,000이다.
- `read`가 `join_after_seq`부터 읽으므로 **입장 전에 지나간 대화는 보이지 않는다.** 화면이 그렇게 말한다.
- **들어와 있으면 AI가 그 방에서 승인 없이 말한다**(`send`·`read`·`wait`). ⚠️ 그런데 **나가기와 종료는
  AI 연결에 대해 하드 거절**이다(`AGENT_DIALOGUE_COMMUNITY_UI_ONLY`). 승인 게이트로는 부족하다 —
  정당한 커뮤니티 `send`가 그 MCP 연결에 방 grant를 남기고(호스트가 send/wait 뒤 grant를 되살린다)
  그 grant가 `close`를 그대로 통과시켜 **한 AI가 전원을 쫓아낼 수** 있었다. 테스트가 이 경로를 지킨다.
- **입장·나가기는 앱에서만.** MCP `community-join`은 언제나 앱 승인을 받는다(`agentstoz_use_enter_community`).
  읽기 전용 `community-status`는 승인이 필요 없다.
- 쌍 단위 페어링은 **특정 상대와만 따로 쓰는 보조 경로**로 남긴다(화면 제목 「1:1 연결 · 30일」).
- 검증: `tests/agent-dialogue-sql.test.ts`(3대 입장 → 한 번 보내 수신 2명 · 재입장 멱등 · 나가면 1명 ·
  prune에 살아남음), `tests/agent-dialogue-host.test.ts`(실제 호스트로 입장 → 승인 없는 send/wait ·
  AI의 입장은 승인 요구 · close/leave 거절), `tests/agent-dialogue-community.test.ts`(화면 판정).
- ⚠️ **정본 SQL은 「새 DB」와 「옛 DB 업그레이드」 둘 다에서 돌아야 한다.** `kind`를 `create table if not exists`
  안에만 넣었더니 10-03 rooms 테이블이 있는 라이브 DB에서 컬럼이 생기지 않아 바로 다음 인덱스가
  `column "kind" does not exist`로 실패했다(새 DB만 쓰던 테스트는 통과). 기존 테이블에 컬럼을 더할 때는
  `alter table … add column if not exists`를 함께 둔다 — 테스트가 10-03부터 차례로 올리는 경로를 돈다.
- **라이브 적용 완료(2026-10-05, Supabase MCP)**: 수정된 `20261004030000`을 한 트랜잭션으로 적용하고 이력에
  `20261004020000`·`20261004030000`을 함께 기록했다(커뮤니티 SQL이 페어링 SQL의 상위집합이라 결과가 같다).
  함수 본문 md5가 로컬 PGlite 재현과 일치했고(주석 속 `«` 4곳만 MCP JSON 전송에서 실제 «»로 바뀜),
  가짜 기기 2대로 입장→전송→수신을 확인한 뒤 의도적 예외로 롤백해 잔여 0건을 확인했다.

### 커뮤니티 기기 제어 — 워크룸 「기기」 선택 (2026-10-05)

커뮤니티에 입장한 다른 Mac의 워크룸을 이 Mac 화면에서 그대로 쓴다. 워크룸 툴바에 「기기」 줄이 생기고
(다른 기기가 하나도 없으면 줄 자체가 없다 — 예전 화면 그대로) 고르면 **그 Mac에서** 터미널이 뜬다.
화면은 휴대폰 원격 워크룸과 같은 `AiTerminalPanel remote`이고 통로만 다르다(`src/WorkroomDeviceSwitch.tsx`).

- **권한 근거는 커뮤니티 입장 하나다.** 사용자가 「입장 = 제어 허용」을 골랐다(승인·6자리 코드 없음). 그래서 DB가
  매 요청마다 **보내는 쪽과 받는 쪽이 모두 같은 프로필 커뮤니티의 joined 멤버이고 활성 endpoint인지**를 다시 본다.
  나가거나 대화를 끄면 이미 줄 서 있던 요청도 실행되지 않는다. 같은 기기는 자기 자신을 지정할 수 없다.
- ⚠️ **휴대폰 릴레이를 재사용하지 않은 이유**: 릴레이의 컨트롤러 RPC는 Google 로그인 사용자 JWT(`auth.uid()`)를 요구하고
  호스트당 소유자 한 명에 묶인다. Mac 사이드카는 service_role만 있어서 컨트롤러가 될 수 없다. 대신 이미 기기 인증이 된
  대화 RPC(`portmgr_agent_dialogue_call`)에 **제어 우편함**(`portmgr_agent_dialogue_controls`, `control-send/inbox/respond/result`)을 더했다.
- **우편함이지 기록이 아니다**: 답하면 요청 본문을 비우고, 답은 보낸 쪽이 읽는 그 문장에서 지우며, 10분 넘은 행은 지운다.
  2분 넘은 요청은 실행하지 않는다(보낸 쪽은 이미 포기했다). 터미널 글은 **평문으로** DB를 지난다 — service_role만 읽는다
  (사용자가 종단간 암호화 대신 고름. 다음 단계 후보).
- **우회 없이 연 Codex가 「훅 신뢰」 메뉴에서 멈추지 않게 한다**(`src/codexHookTrust.ts`, 2026-10-07 3호 실측). Codex는 처음 보는 훅마다
  「Review hooks / Trust all / Continue without trusting」을 묻고 답을 `~/.codex/config.toml`의 `[hooks.state."<경로>:…"] trusted_hash`에
  기억한다. 다른 Mac에서 연 워크룸은 우회가 없어서 AgentsToZ 활동 훅이 있는 프로젝트마다 한 번씩 멈췄다. Codex의 공식 플래그
  `--dangerously-bypass-hook-trust`(「훅 출처를 이미 검증한 자동화용」)를 **실행할 훅 전부가 AgentsToZ가 쓴 활동 훅과 바이트 단위로 같을 때만**
  준다 — 사용자 수준 `hooks.json`, 플러그인 훅, config.toml의 훅 표, 프로젝트 파일 안의 다른 명령 중 하나라도 있으면 Codex가 원래대로 묻는다.
  활동 훅 명령의 정본은 `src/projectMemoryActivityHook.ts` 하나다(생성기와 검사기가 같은 문자열을 만든다). 플래그를 모르는 옛 Codex에는 주지 않는다
  (`codex --help`를 실행 파일마다 한 번 확인).
  ⚠️ **AgentsToZ가 프로젝트 `.codex/hooks.json`에 새 훅을 더하면 검사기(`OUR_EVENTS`)에도 함께 넣는다.** 5ead6c0c가 사전 압축 복구 훅
  (`PreCompact`·`Stop`, 정본 `src/projectMemoryRecoveryHook.ts`)을 더하면서 이 표를 빠뜨려, 새 장기기억 버전의 프로젝트마다 우회 없는 Codex가
  「Hooks need review — 3 hooks are new or changed」에서 다시 멈췄다(2026-10-31 3호 Testforcsagents1 실측). 같은 때 3호→1호 OPS 요청이
  1호에서 「승인·확인 필요」(`awaitingAnswer`)로 멈췄다 — 받는 OPS도 우회 없이 시작하므로 이 메뉴가 그대로 막는다.
  사용자 수준 훅이 있는 기기(3호는 config.toml에 codebase-memory-mcp의 `SessionStart`·`SubagentStart`, 1호는 `~/.codex/hooks.json`)에서는
  고친 뒤에도 의도대로 Codex가 묻는다 — 그 기기에서 사람이 한 번 「Trust all」을 골라야 훅이 다시 바뀔 때까지 묻지 않는다.
- **다른 Mac에서 넘어온 OPS 작업의 워커는 넘겨받기에 필요한 아젠투지 도구 15개만 묻지 않는다**(`src/opsWorkerToolApproval.ts`,
  2026-10-31 사용자가 고름). 우회 없이 시작한 받는 쪽 CLI가 아젠투지 도구를 부를 때마다 「Allow the agentstoz_use MCP server to run tool
  …?」(Claude는 「Do you want to proceed?」)를 물어, 3호→1호 작업이 「승인·확인 필요」에서 멈췄다. 허용은 **그 실행의 인자에만** 있다 —
  Codex는 도구마다 `-c mcp_servers.agentstoz_use.tools.<도구>.approval_mode="approve"`, Claude는 `--allowedTools mcp__agentstoz_use__<도구>,…`.
  사용자 설정 파일에는 아무것도 쓰지 않는다. 3호 실측(Codex 0.166·Claude 2.1.314): 목록의 도구는 바로 실행되고 목록 밖 도구는 그대로 물었다.
  서버 전체 키(`default_tools_approval_mode`)는 쓰지 않는다. 목록 밖에 둔 것: 키 입력(신뢰·권한 화면에 답한다), 다른 기기로 넘기기,
  컴퓨터 유즈, 공용 셸, 프로젝트·저장소 만들기, 기억 쓰기, 메시지, 팀, 제품 USE. 셸 명령·파일 편집·다른 MCP 서버도 그대로 묻는다.
  켜는 길은 OPS 호스트의 시작 하나뿐이다(`perform`의 호스트 전용 옵션 `opsWorker` — 원격 authority·우회·제한 실행·재개에는 거절,
  「다시 시작」은 물려받지 않는다). Hermes·agy는 바꾸지 않았다. 검증: `tests/ops-worker-tool-approval.test.ts`.
- **다른 Mac으로는 권한 우회·다시 시작이 가지 않는다**(`agentDialogueControl.ts`가 거절 — 입장은 제어 허용이지 「묻지 않고 실행」
  허용이 아니다). 그래서 다른 기기를 모는 패널은 `bypassUnavailable`(`COMMUNITY_BYPASS_UNAVAILABLE`, `workroomDeviceLabel.ts`)로
  **우회 없이 시작**하고 토글이 「이 기기에서는 꺼짐」과 이유를 말한다. 기기 `@` 전달도 같다. 이것이 없던 동안 저장된 「켜짐」이
  그대로 실려 3호 → 1호 시작이 매번 「다른 기기에서는 권한 우회나 다시 시작으로…」로 거절됐다(2026-10-07).
  저장된 선택은 그대로라 이 Mac으로 돌아오면 다시 켜진다. 검증: `tests/workroom-device-bypass.e2e.mjs`.
- **받는 Mac이 할 수 있는 것은 워크룸뿐이다**(`src/agentDialogueControl.ts`): 터미널 `list/start/read/input/resize/close`,
  `workroom.*` 동작, 프로젝트 목록. 공용 셸(`shell.*`)·그 밖의 로컬 API는 닿지 않는다. 실행은 그 Mac 자신의 워크룸과 같은
  경로라서 그쪽 화면에도 세션이 보인다.
- **폴링**: 받는 Mac은 커뮤니티에 있을 때만 우편함을 읽고, 최근 90초 안에 제어받았으면 0.6초, 아니면 3초 간격이다
  (멤버십은 1분 캐시 — 입장하지 않은 Mac은 분당 1회). 보내는 쪽은 답이 올 때까지 최대 20초 기다리고, 넘으면
  「실행됐는지는 알 수 없다」고 말한다(거절이 아니다).
- 앱 경로는 전용 Tauri 커맨드 `agent_dialogue_control_request` → `/api/agent-dialogue/control`(요청 64KB·읽기 30초).
  관리 경로(4KB·10초)는 넓히지 않았고, 일반 관리 요청 함수로는 이 경로를 부를 수 없다(Rust 테스트).
- 검증: `tests/agent-dialogue-sql.test.ts`(멤버만·나가면 즉시 중단·남의 답 불가·2분/10분), `tests/agent-dialogue-host.test.ts`
  (두 Mac 호스트가 한 DB로 실제 왕복·외부 기기 불가·응답 없음), `tests/agent-dialogue-control.test.ts`(셸 거절).
- 마이그레이션 `20261005010000_agent_dialogue_control.sql`(= 정본 SQL 전체).
- ⚠️ **기기 목록(`controlDevices`)은 멤버십 캐시를 건너뛰지 않는다.** `fresh=true`로 부르면 바로 뒤의
  `community-status`와 **같은 인자로 두 번** 부르고, 입장하지 않은 Mac은 공개 엔드포인트 **전부**를 매
  호출 순회한다(실측 101개 공개 → 15초마다 101 RPC). 이 경로는 워크룸이 15초마다 부르고 팝아웃 창마다
  늘어난다. 입장·나가기가 캐시를 비우므로(`uiCommunity`) 판정이 늙지 않는다.
  `tests/agent-dialogue-host.test.ts`가 호출당 `community-status` **1회**를 고정한다.

### 원격 워크룸은 휴대폰에서 더 작은 글자로 시작한다 (VOC 2026-10-05, 아이폰 17 Pro)

원격 「읽기 보기」는 호스트의 100칸 줄을 **폰 너비에서 다시 접는다**. 시작 크기가 16px이라 한 줄에
20자 남짓이 들어가 모든 줄이 서너 번 접혔고, 그것이 「화면이 깨진다」로 읽혔다. 판정은
`remoteWorkroomFontFloor`(`src/workroomTerminalView.ts`) 한 곳 — **≤640px면 12px, 그 밖은 16px**로
시작한다. 실측(402px·WebKit): 같은 줄이 16px에서 3줄, 12px에서 2줄.
- 이것은 **시작값**일 뿐이다. A−는 여전히 10까지, A+는 24까지 가고 고른 값은 기기별로 저장된다
  (`Math.max(floor, 저장값)`이라 저장값이 더 크면 그대로 쓴다).
- ⚠️ **줄바꿈 CSS는 건드리지 않았다.** `overflow-wrap:anywhere`를 `break-word`로 바꿔 봤지만 실측에서
  **차이가 없었다**(WebKit이 `-`·`/`를 break opportunity로 똑같이 끊는다). 같은 시도를 다시 하지 말 것 —
  낱말이 쪼개져 보이는 원인은 줄바꿈 규칙이 아니라 한 줄에 들어가는 글자 수다.
- 원격 화면은 **PTY 크기를 바꾸지 않는다**(CLAUDE.md의 원격 워크룸 규칙) — 글자 크기는 보는 쪽 사정이다.

### 맥의 커뮤니티 대화창 — 「기기」 줄 아래 접힌 한 줄 (2026-10-05)

폰에만 대화창(`RemoteCommunityPanel`)이 있어서 맥에서는 **입장·멤버 확인과 기기 제어만** 되고 주고받는
일은 AI에게 시켜야 했다. 같은 일을 맥 화면에서 직접 하도록 `src/CommunityChatPanel.tsx`를 워크룸의
「기기」 줄 **바로 아래**에 둔다(메인 창과 전용 창 모두). 다른 호를 생각하는 자리가 거기다.

- **접혀 있으면 한 줄이다**(「아젠투지 단톡방 · 함께 있는 대상 N개 · 읽지 않음 N개」 — 응답 없는 기기가 있으면 「· 응답 없음 N개」가 붙는다). 워크룸은 이 앱에서 가장
  빽빽한 화면이라 읽을 것이 없을 때 자리를 차지하면 안 된다. 펼치면 그 자리에서 읽고 답한다.
- ⚠️ **접힌 동안은 아무 것도 두드리지 않는다.** 읽지 않음 개수는 워크룸이 이미 15초마다 하는 기기 조회의
  **덤**이다 — `controlDevices()`가 어차피 부르는 `community-status`의 `unread`를 함께 싣는다(RPC 추가 0).
  메시지 조회는 **펼친 뒤에만** 12초 주기이고, 접으면 타이머가 사라지고 커서는 남아 이어 읽는다.
- 서버는 휴대폰과 **같은 스냅샷 함수**(`communityMobile`)를 쓰고 **같은 모양**(`remoteCommunityState`)으로
  내보낸다. 그래서 화면도 휴대폰의 `normalizeRemoteCommunityState`·`mergeRemoteCommunityMessages`를 그대로
  쓴다 — 정규화기가 모르는 키를 통째로 거절하므로 서버가 키를 늘리면 맥 화면이 먼저 깨진다(의도).
- 관리 경로에 더한 동작은 `community-read`·`community-send` 둘이다. 입장하지 않은 Mac은
  `AGENT_DIALOGUE_COMMUNITY_OUTSIDE`로 거절되고 화면이 「「기기 간 대화」(아젠투지 설정 옆)에서 입장하세요」를 말한다.
  **나가기·종료는 여전히 「기기 간 대화」에서만** 한다(AI 연결에는 하드 거절).
- ⚠️ **보내기에는 읽기 커서(`afterSeq`)를 함께 싣는다.** 호스트는 **커서를 준 `send`에만** 메시지를
  돌려준다(`agentDialogueHost`의 `cursorGiven`) — 빼먹으면 방금 보낸 내 말이 다음 폴링(12초)까지
  화면에 없다. 커서는 **앞으로만** 간다(뒤로 가면 본 줄을 다시 받고, 0이면 가장 오래된 줄이 온다).
- ⚠️ **초안은 보낸 뒤에만 비운다.** 먼저 비우면 실패했을 때 쓰던 글이 사라진다(`onSend`가 성공 여부를 돌려준다).
- 길이는 **글자가 아니라 바이트**다(한글 1자=3바이트). 서버는 `normalizeRemoteCommunityText`로 거르고
  (제어문자·빈 글·2,000바이트), 화면은 80%를 넘으면 바이트 수를 보여 준다. `maxLength`로 글자를 막지 말 것.
- ⚠️ **한 번에 싣는 메시지는 5건인데 커서를 읽은 끝까지 밀면 못 실은 줄이 영영 사라진다.** 그래서
  `remoteCommunityState`가 커서를 **실제로 실은 마지막 줄**까지만 전진시킨다(와이어에 새 키를 더하지
  않는다 — 휴대폰 정규화기가 모르는 키를 통째로 거절하기 때문).
- **맥은 휴대폰의 릴레이 예산을 쓰지 않는다.** 5건·240자는 릴레이 평문(11,000바이트)에서 나온 숫자이고
  맥은 자기 사이드카와 loopback으로 말한다(응답 상한 1MiB). 그래서 한도를 인자로 받고 맥 경로만
  `LOCAL_COMMUNITY_MESSAGE_LIMIT`(40)·`LOCAL_COMMUNITY_TEXT_LIMIT`(4,000)을 쓴다. **기본값은 휴대폰
  값 그대로**라 명시하지 않은 호출자는 전과 같다. ⚠️ 보내는 쪽과 **검사기도 같은 한도**로 읽어야 한다
  — 서버가 맥 한도로 내보내고 화면이 기본값으로 검사하면 상태가 통째로 거절된다.
- ⚠️ **커뮤니티의 보내기·읽기는 RPC 이름이 `send`·`read`다.** 그래서 「유휴로 거절됐다」를 동작 이름으로
  판정할 수 없었고, 그때 적용되지 않았던 `20261005020000_agent_dialogue_community_idle.sql` 때문에 원시 코드
  `AGENT_DIALOGUE_ROOM_INACTIVE`가 화면에 그대로 떴다. 이제 호스트의 `rpc()`가 **설명용 라벨**을 따로
  받아(`community-send`·`community-read`, 와이어로 가지 않는다) 그 파일 이름을 말한다. 일반 1:1 방의
  유휴 거절은 **그대로 둔다** — 그 방은 정말 2시간 규칙을 받는다.
- ⚠️ **입력칸은 떼어 memo하고, 조합 중에는 읽기를 쉰다**(VOC 2026-10-05 「타이핑이 잘 안 된다」). 초안은
  `CommunityCompose` 안에서만 살아서 바깥 상태가 바뀌어도 값이 내려오지 않고, `compositionstart`~`end`
  동안에는 폴링이 목록을 갈아끼우지 않는다. 인라인 람다를 넘기면 memo가 깨져 떼어 놓은 의미가 사라진다.
  휴대폰 `RemoteCommunityPanel`도 같은 조합 가드를 쓴다.
  (근거의 한계: Chromium 하네스에서 **조합 중 재렌더로 글자가 깨지는 것은 재현되지 않았다** — 그래서 이
  두 겹은 원인 확정이 아니라 앱 쪽에서 그럴 수 있는 길을 없앤 것이다.)
- 검증: `tests/workroom-community-chat.e2e.mjs`(접힌 줄이 아무 요청도 보내지 않음 · 펼치면 한 번 읽음 ·
  보내기 본문·requestId · 조합 중 읽기 중단과 초안 보존 · 접으면 폴링 중단),
  `tests/agent-dialogue-host.test.ts`(`controlDevices` 키 고정).

### 빈 「새 작업」 칸은 항상 접힌다 (2026-10-05)

처음엔 **실행 중 세션이 있을 때만** 접었는데, 그러면 세션이 0개인 화면 — 다른 아젠투지를 막 고른
직후가 정확히 그렇다 — 에서는 한 화면짜리 빈 입력칸과 `0 / 24,000바이트`가 늘 먼저 보였다.
이제 `composerFoldable`은 항상 참이고, 터미널만 열려면 「새 터미널」로 충분하다.
⚠️ **지우는 것이 아니라 접는 것이다** — 첫 요청을 담아 새 세션을 여는 유일한 길이므로 「새 작업 요청
작성」 버튼과 넘겨받은 초안(`entry`)이 그 길을 연다. 「새 작업 새 창으로」 줄은 **이어서 열 세션이 있을
때만** 그 자리를 쓴다(세션이 없으면 그 버튼은 할 일이 없다).

### 「새 작업 새 창으로」에는 AI 선택이 함께 있어야 한다 (VOC 2026-10-05)

전용 창에서는 실행 칸(프로젝트·AI)이 접혀 있고 이 버튼이 **그 펼치기 버튼 자리**를 쓴다. 그래서 버튼이
`agent`를 따라가기만 하면 네 CLI 중 무엇으로 열리는지 **바꿀 길이 없었다**. 이제 그 줄에 AI 선택(`select`,
`workroom-new-window-agent`)과 「프로젝트·요청까지 고르기」(= 접힌 칸 펼치기)를 함께 둔다. 두 칸은 같은
`agent` 상태를 쓴다 — 서로 다른 값을 들고 있으면 어느 쪽이 열릴지 알 수 없다(e2e가 같은 값을 확인한다).

### 커뮤니티 차원의 `@`·`#` — 기호 앞의 기기 이름 (2026-10-05)

입력칸에서 `@`·`#` 바로 앞에 **기기 이름**을 적으면 그 아젠투지의 프로젝트가 후보가 된다
(「아젠투지2호 @블로그」). 이름이 없으면 예전 그대로 이 화면이 몰고 있는 기기의 목록이다.
판정은 `src/workroomCommunityMention.ts` 한 곳이고, Mac(메인·팝아웃)과 휴대폰 포털이 같은 함수를 쓴다.

- **기기 이름은 꼬리만 적어도 된다**(`2호` → `아젠투지2호`). 공백·가운뎃점·대시는 무시하고
  뒤에서 최대 세 단어까지 본다(「아젠투지 2호 @」). ⚠️ **모호하면 아무 기기도 고르지 않는다** —
  두 기기에 걸리는 이름으로 다른 Mac에 일을 보내지 않는다(fail-closed).
- **전달은 기존 절차를 그대로 돈다.** `deliverWorkroomRoute`에 그 기기의 세션 목록과 그 기기의 요청
  함수를 넘기므로, 화면 읽기(질문·승인 화면이면 입력하지 않음)·첫 요청으로 담기·준비 뒤 입력이 모두 같다.
  새 입력은 `crossDevice`뿐이다: 플랜을 `source:null`로 세워 **다른 기기의 세션이 「현재 대화」로 읽히지
  않게** 하고, 핸드오프에 `보낸 기기:` 줄을 더한다. 대화상자·미리보기·영수증이 어느 기기인지 말하도록
  `target.label`에 「<기기> · <프로젝트>」를 넣는다.
- **받는 곳을 고르면 그 기기의 세션 목록을 한 번 읽는다**(`list`). 그래야 「전달/새로 열기」와 받는 AI
  기본값을 정직하게 말한다. 목록이 오기 전에 보내면 거절하고 기다리라고 한다.
- ⚠️ **`#` 참고 폴더는 받는 쪽 호스트만 풀 수 있다.** 그래서 참고는 **기기별로** 기억하고
  (`CommunityReferenceChip`), 전달할 때 **받는 기기와 같은 기기의 것만** `references`로 넘긴다. 다른
  기기의 참고는 글 안의 `#아젠투지2호/블로그` 이름으로만 가고, 영수증이 그 사실을 적는다.
- **프로젝트 목록은 쓸 때 한 번 받는다**(`requestProjects`). 커뮤니티에 있는 기기마다 미리 긁으면
  쓰지도 않을 왕복이 생긴다(2026-10-05 감사의 교훈). Mac은 한 번에 전체 목록을, 휴대폰은 한 장 20개씩
  최대 다섯 장(100개)까지 모으고 남은 것이 있으면 후보 목록이 그 사실을 말한다.
- ⚠️ **요청 함수(`requester`)는 기기마다 한 번만 만든다.** `createTerminalRequester`가 순서를 지키는
  대기열을 들고 있어서 렌더마다 새로 만들면 같은 기기로 가는 요청들이 서로의 순서를 모르고, 패널의
  effect가 매 렌더 다시 돌아 `list`를 끝없이 보낸다. 패널은 ref로 읽어 이 함정을 한 겹 더 막는다.
- 다른 기기를 몰고 있을 때는 **이 Mac**이 `@` 대상이 된다(`local` 줄). 지금 몰고 있는 기기는 목록에서
  빠진다 — 그 기기의 프로젝트는 그냥 `@프로젝트`다.
- 검증: `tests/workroom-community-mention.test.ts`(이름 꼬리·모호함 거절·후보 출처·토큰·참고 분배),
  `tests/workroom-route-delivery.test.ts`의 「다른 아젠투지」 묶음(같은 targetId·같은 AI여도 「현재 대화」가
  아님, 새 세션의 첫 요청에 `보낸 기기`).

### ⚠️ 커뮤니티는 유휴 2시간 규칙에서도 빠져야 한다

**라이브 적용·기록 완료 (2026-10-06, 사용자 승인).** 그런데 실측에서 드러난 것은 **DDL이 이미 라이브에
있었고 이력에만 없었다**는 것이다 — 라이브의 `portmgr_agent_dialogue_call`·`_community_members` 본문 md5가
정본 `AGENT_DIALOGUE_SQL`을 PGlite로 재현한 값과 **바이트 단위로 같았다**(`2c241d76…`, `c854166a…`).
앱의 스키마 경로(`MIGRATION_SQL`이 `AGENT_DIALOGUE_SQL`을 품는다)가 먼저 적용했을 가능성이 크다.
그래서 적용은 사실상 무작동이었고 실제 변화는 `supabase_migrations.schema_migrations`의 한 줄이다.
⚠️ **「이력에 없음」을 「라이브에 없음」으로 읽지 말 것** — 판정은 이력이 아니라 **함수 본문 md5와 스키마**로
한다(이 저장소는 정본 SQL을 PGlite로 재현할 수 있으니 비교가 가능하다). 반대로 이력만 보고 「적용됐다」고
읽는 것도 같은 오류다.
그 수정이 지금 필요했던 것은 실측으로 확인됐다: 라이브 커뮤니티가 `state=active`·`expires_at` 2126년인데
**1,294분(약 21.5시간) 유휴**였고, 옛 가드라면 그 방의 모든 발송이 거절되는 상태였다.

보존 패스(`prune`)에서만 면제했더니, **방 조작 가드의 2시간 유휴 검사**가 조용한 커뮤니티의 모든
`send`를 `AGENT_DIALOGUE_ROOM_INACTIVE`로 거절했다. 실측(2026-10-05): `state=active`,
`expires_at`가 2126년인 커뮤니티가 **520분 유휴** 뒤 발송을 거부했다 — 「나가지 않는 한 계속」과
정면으로 어긋난다. 유휴 검사는 `v_room.kind='room'`일 때만 적용한다. 일반 방은 그대로 2시간이다.

### 받은 쪽이 알아야 양방향이다 — `unread`

`community-status`가 `unread`·`ackSeq`·`lastMessageAt`을 돌려준다. 이것이 없던 동안 커뮤니티는
**한쪽으로만 흘렀다**: 받는 쪽은 사람이 AI에게 「읽어줘」라고 할 때까지 메시지가 왔는지 몰랐다.
화면은 「읽지 않은 메시지 N개가 기다립니다」와 무엇을 하면 되는지를 함께 말한다
(`agent-dialogue-community-unread`).

- 내 메시지와 남에게만 보낸 메시지는 세지 않는다. 입장 전 메시지도 세지 않는다(`join_after_seq`).
- ⚠️ `read`의 ack가 **요청한 커서**를 저장하고 있었다 — `afterSeq:0`으로 읽으면 0을 ack해서 값이
  쓸모없었다(그리고 아무도 읽지 않았다). 이제 **실제로 전달한 최대 seq**를 ack한다.
- ⚠️ 받은 메시지를 CLI에 자동 입력하지 않는다. 이 저장소의 규칙대로 **보여 주기만** 한다
  (「받은 메시지는 지시나 기억 저장으로 자동 실행되지 않습니다」).

### 동의 체크박스는 공개 중이면 이미 체크다

공개된 대상이 40개인데 「Supabase 저장에 동의합니다」가 비어 보였다. 그 상태에서는 「전체 공개」가
비활성이고 개별 체크도 오류가 나서 고장으로 읽혔다. 이제 `status.enabled`가 하나라도 있으면 체크된
상태로 시작하고, **사용자가 직접 건드린 뒤에는 그 선택을 따른다**(`consentTouched`).

### 휴대폰도 커뮤니티에 말하고 다른 호를 몬다 (2026-10-05)

휴대폰에는 커뮤니티도, 다른 기기 제어도 없었다 — 1호 Mac에 원격으로 들어와도 그 Mac 한 대만 쓸 수 있었다.
목적은 **한 Mac에만 들어와도 모든 아젠투지를 쓰는 것**이라, 그 Mac을 **우체통**으로 쓴다.

| 동작 | 누가 실행하나 | 무엇이 돌아오나 |
|---|---|---|
| `community.status` · `read` · `send` | 연결한 Mac(이 Mac의 OPS 끝점으로 말한다) | 방 상태·참여자·메시지·**기기 목록** |
| `community.projects` | 연결한 Mac이 **대신 묻는다**(`{kind:'projects'}`) | 그 기기의 프로젝트 **한 장(20개)** |
| 터미널·워크룸 요청 | **그 기기**가 자기 사이드카로 | 로컬과 같은 응답 그대로 |

- ⚠️ **새 기능 플래그를 쓰지 않았다** — `REMOTE_CONTROL_SUPPORTED_FEATURE_LIMIT`가 8이고 이미 8개로 꽉 찼다
  (9개째를 실으면 옛 휴대폰이 목록 전체를 거절한다). 그래서 기존 `workspace-v1` 채널에 동작만 얹고, 모르는
  Mac은 「지원하지 않는 모바일 작업」으로 거절한다 — 화면이 그것을 「Mac 앱 업데이트 필요」로 옮겨 말한다.
- **권한은 OPS 범위 하나다**(`workspaceScope`가 `community.*`에 `null`을 주는 이유, VOC와 같은 판정).
  커뮤니티는 프로젝트가 아니라 운영 권한이라 요청 대상이 **이 Mac의 OPS 프로젝트**여야 하고
  (`boundOpsProjectId()`), 프로젝트 하나만 허락받은 휴대폰은 다른 아젠투지를 부를 수 없다.
- **방 id·참여자 id는 호스트가 정한다**(`AgentDialogueHost.communityMobile`). 휴대폰은 커서(`afterSeq`)와 글만
  준다. **입장·나가기는 Mac 화면에만 있다** — 휴대폰 화면에 그 버튼을 만들지 말 것.
- 휴대폰에 나가는 payload에는 `endpointId`·`participantId`·`deviceId`가 **없다**. 기기를 지목하는 손잡이는
  endpointId에서 결정적으로 유도한 16자리 **불투명 참조**(`src/communityDeviceRef.ts`)이고, 되돌릴 때는
  **그때의 커뮤니티 목록을 다시 읽어** 맞춘다 — 표를 저장하지 않으니 나간 기기의 참조는 자동으로 아무 것도
  가리키지 않는다(fail-closed). 기기 한 대에 한 줄이라는 판정은 `communityDeviceRows` 한 곳이고, Mac 화면의
  「기기」 목록(`controlDevices`)도 같은 것을 쓴다.
- ⚠️ **기기 참조는 봉투에만 싣는다**(`RemoteTerminalRequest.device`). 요청 안에 넣으면 실행하는 Mac의 엄격한
  키 검사가 거절하거나(좋은 경우) 조용히 무시돼 **다른 기기로 가야 할 일이 이 Mac에서 실행된다**(나쁜 경우).
  전달 전에 반드시 벗겨낸다. 참조를 모르는 옛 Mac은 이 키 때문에 봉투를 거절한다 — 그것이 업데이트 안내가 된다.
- **기기 선택은 탭이다**(`ai-terminal-device-tab`, Mac·휴대폰 같은 모양). 드롭다운은 두 번 눌러야 하고 어느 호가
  있는지 가려졌다(VOC 2026-10-05). 기기가 하나도 없으면 줄 자체가 없어 예전 화면과 같다.
- **답하지 않는 기기는 탭이 그렇게 말한다(2026-10-31, Mac 화면만).** 엔드포인트는 10분마다 heartbeat를 보내고
  (`AGENT_DIALOGUE_HEARTBEAT_MS`, api-server의 유지 타이머), `lastSeenAt`이 그 세 배(30분)보다 오래되면 탭에
  「응답 없음 · 마지막 N분/시간/일 전」이 붙고 대화창 접힌 줄에 「· 응답 없음 N개」가 붙는다(`src/communityDeviceLiveness.ts`).
  **고를 수는 있다** — 잠든 Mac이 깨어나 답할 수 있고, 요청 영수증이 결과를 말한다. 고르면 「실행됐는지 모른 채 끝날 수
  있다」는 한 줄이 뜬다. `lastSeenAt`을 모르면 응답 없음이라 하지 않는다. 휴대폰 DTO에는 키를 더하지 않았다.
- **기기를 고른 직후에는 프로젝트 목록이 올 때까지 패널을 돌리지 않는다**(`visible=false`). 사용자가 기다리는 첫
  번째가 그 목록인데, 패널이 먼저 1초마다 `list`·`read`를 보내면 목록 요청이 뒤로 밀렸다. 첫 요청은 상대 Mac의
  유휴 폴링(3초) 틈에 떨어지기 쉬우므로 **한 번만** 자동으로 다시 묻는다(그 뒤 실패는 그대로 보여 준다).
- ⚠️ **답하지 않는 Mac 하나가 휴대폰의 릴레이 대기열을 채우면 원인이 가려진다**(2026-10-05 아이폰 17 실기).
  기기를 고르면 프로젝트 목록이 비고 「대기 중인 원격 입력이 많습니다」만 떴다 — 그것은 릴레이 대기열
  32개 상한 문구이고, 진짜 원인은 전달 한 건이 상대 Mac을 기다리는 20초 동안 워크룸 화면의 배경 조회가
  그 뒤에 계속 줄을 선 것이다(릴레이는 요청을 하나씩 처리한다). 두 겹으로 막는다:
  ① 휴대폰이 거친 전달의 마감은 `AGENT_DIALOGUE_CONTROL_MOBILE_TIMEOUT_MS`(8초)로 짧게 — 깨어 있는 Mac은
  유휴 폴링 3초 + 왕복이라 충분하고, 답하지 않으면 「상대 기기가 제때 답하지 않았습니다」라는 **진짜 이유**가
  나온다. ② 화면은 전달 요청을 동시 2개까지만 보낸다(`createCommunityForwardGate`) — 넘치면 쌓지 않고
  거절하고 배경 조회는 다음 주기에 다시 온다. `community.projects`는 이 Mac에게 묻는 것이라 문을 거치지 않는다.
- ⚠️ **보낸 직후의 읽기는 「보낸 줄 앞」에서 시작한다** — 방금 쓴 메시지의 seq가 보내기 전의 `next_seq`이고
  `read`는 `seq>afterSeq`만 주므로, 커서가 끝에 있으면(화면은 항상 끝까지 따라잡는다) **자기 말이 빠진다**.
  그리고 응답의 메시지는 **커서 뒤의 새 것뿐**이라 화면이 그대로 덮어쓰면 따라잡은 뒤의 폴링 한 번에 목록이
  비어 「사라졌다」가 된다 — 합치는 규칙은 `mergeRemoteCommunityMessages` 한 곳이다. 커서를 주지 않은 `send`는
  읽지 않는다(0부터 읽으면 가장 오래된 7건이 돌아온다).
- **응답 크기**: 커뮤니티 상태는 6,000바이트에서 **오래된 메시지부터 떨어뜨린다**(한글은 글자당 3바이트 —
  개수 상한만으로는 못 지킨다). 프로젝트 목록은 한 장 20개다. 터미널 응답은 **로컬과 같은 경로**로 가므로
  워크스페이스 8,500바이트 상한에 걸리지 않는다 — 그래서 터미널을 워크스페이스 동작으로 감싸지 말 것.
- **멱등**: 휴대폰 봉투의 `requestId`(uuid가 아닐 수 있다)에서 `stableRequestUuid`로 결정적 uuid를 만들어
  대화 DB의 멱등 키로 쓴다. 재시도가 두 번 보내지 않는다.
- 화면: 휴대폰 포털은 「원격 작업 → 커뮤니티」(`remote-community-toggle`, `src/RemoteCommunityPanel.tsx`)와
  워크룸의 「기기」 줄(`remote-workroom-device-switch`)이고, LAN QR 페이지는 워크룸의 `#terminal-device`다.
  커뮤니티 칸은 **연결 → 기능 확인 → 업데이트 필요** 순으로 말한다(2026-10-16 감사): Mac이 없거나 끊기면 `remote-community-offline`, 기능을 아직
  모르면(`supportedFeatures === null` → `available={null}`) `remote-community-checking`, 기능 목록을 받았는데 `workspace-v1`이 없을 때만
  「Mac 앱 업데이트 필요」. 보낸 뒤 문구는 「방에 남겼습니다」다 — 어느 AI에게도 저절로 가지 않는다(`REMOTE_COMMUNITY_SENT_NOTICE`).
  ⚠️ LAN 페이지에서 `terminalReady`에 **이 기기의** 목록이 들어오면 기기 선택을 되돌린다 — 프로젝트 카드의
  「워크룸」처럼 목록을 다시 채우는 길이 여러 개라서, 그 경로가 남의 목록 위에 이 기기 프로젝트를 얹으면
  어디로 보내는지 알 수 없게 된다. 커뮤니티 **조회**는 연결한 Mac에게 묻는 것이라 그 동안만 참조를 비운다.
- 검증: `tests/community-mobile.test.ts`(PGlite로 두 호스트를 띄워 상태·읽기·ack·재시도·전달·탈퇴까지,
  그리고 OPS 범위가 없을 때 전달이 거절되는지), `tests/remote-community.test.ts`,
  `tests/mobile-workspace.test.ts`, `tests/remote-control-mobile-page.test.ts`.

## 기기 간 대화 — 30일 상호 페어링과 자동 입장 (2026-10-04)

1호에서 3호 OPS로 실제 통신 테스트를 돌렸는데 **3호가 끝까지 입장하지 않아** 방에 보낸 사람만 남았다
(방 `4e8d97f7…`, 이벤트는 `joined`·`message` 둘 다 1호 것). 승인이 아니라 **입장을 호출하는 주체가 없다**는
것이 막힘의 실체였다. 그래서 방마다 수락하는 모델 위에 **쌍 단위 30일 페어링**을 올렸다.

- **페어링은 쌍에 하나다**: `portmgr_agent_dialogue_pairings`가 `(low_endpoint_id, high_endpoint_id)`
  정렬쌍으로 한 행을 쓴다. 「상호」가 두 쪽의 의견이 아니라 사실이 되고, 30일은 **두 번째 수락 시점부터**
  센다(한쪽만 요청한 페어링은 늙지 않는다). 1·2·3호는 쌍마다 한 번씩 = 3쌍이다.
- **페어링이 없애는 것은 상대 승인뿐이다.** `pair`·`pair-revoke`는 **언제나 앱 승인을 받는다** — 30일을
  허락하는 순간이 바로 그 승인이므로 이전 승인으로 건너뛸 수 없다. 페어링된 쌍에 대해서만 `create`·
  `invite`·`join`이 승인 없이 지나가고, 그때 방 grant가 30분 대신 **그 페어링의 남은 기간**(최대 30일)을
  받는다. grant는 계속 **MCP 인스턴스별**이다 — 아무 CLI가 붙어 바로 보내는 길을 열지 않는다.
- **자동 입장이 핵심이다**(`autoJoinPairedInvitations`, **20초 주기**). 페어링이 활성인 상대의 초대만
  사람 없이 `join`하고 틱당 최대 `AUTO_JOIN_PER_TICK`(8)개다. 이것이 없으면 페어링은 승인 피로만 줄이고
  오늘의 침묵은 그대로다. ⚠️ **보존 틱(`maintenance`, 10분)에 얹지 말 것** — 대화를 10분 기다리게 된다.
- ⚠️ **엔드포인트별로 폴링하지 말 것.** 한 Mac이 101개를 공개한 것이 실측이라 엔드포인트마다
  `pairings`+`invitations`를 돌면 틱당 200 RPC다. 그래서 `device-pairings`·`device-invitations` 두
  **기기 단위** 읽기를 쓴다(활성 페어링이 없으면 두 번째는 건너뛰고 답을 60초 캐시한다 — 페어링 없는 Mac은
  분당 1 RPC). 회귀는 `tests/agent-dialogue-host.test.ts`가 잡는다(실제 PGlite + 실제 호스트로 페어링 →
  승인 없는 방 개설 → 상대 `autoJoinPairedInvitations()`가 1건 입장, 두 번째 호출은 0건 → 수신 1명 확인,
  페어링 없는 기기는 0건).
- ⚠️ **페어링은 그 정확한 endpoint 쌍에만 적용된다.** 공개를 끄면(`disable`) endpoint가 폐기되고 다시
  켜면 **새 `endpointId`**가 발급되므로 페어링도 끊긴다. 같은 `memoryId`·같은 이름은 근거가 아니다.
  해지는 어느 쪽에서나 즉시이고, 다시 요청하면 **새 행**이 된다(폐기된 행을 되살리지 않는다).
- 화면은 「아젠투지 설정 → 기기 간 연결 · 30일」이다. 판정은 `src/agentDialoguePairingRows.ts` 한 곳이고
  상태가 다섯이다: 연결됨 / 상대 수락 대기 / **상대가 요청함(수락하면 연결)** / 기간 만료 / 연결 없음.
  앱에서 누르는 클릭이 승인이므로 `uiPair`는 pending을 만들지 않는다(`enable`·`disable`과 같은 성격).

### `peers`가 100개에서 잘려 다른 기기가 사라졌다

`peers` RPC가 `order by (ops 먼저), last_seen_at desc limit 100`이었다. 1호가 101개를 공개한 뒤 **3호의
프로젝트가 38개 → 3개**로 줄었고(2026-10-04 실측), heartbeat 순서로 정렬되니 호출마다 목록이 달라졌다.

- 지금은 **기기별 순위를 먼저 본다**: 기기 안에서 `row_number()`로 순위를 매기고 그 순위를 전역 정렬의
  첫 키로 써서, 전체 상한(500)이 **라운드로빈**이 된다 — 어느 기기의 1순위가 다른 기기의 2순위보다 먼저다.
  한 기기가 600개를 공개해도 조용한 기기의 대상은 전부 들어온다(테스트가 그 수치로 고정한다).
- ⚠️ **상한을 그냥 없애지 말 것** — 엔드포인트가 수천이면 수백 KB가 MCP 응답으로 나간다. 더 좁혀야 하면
  `deviceId`·검색 인자를 더하는 쪽이 맞다.
- 마이그레이션 `20261004020000_agent_dialogue_pairings.sql`은 **정본 SQL 전체**다(전부
  `create table if not exists`/`create or replace`라 멱등). 그래서 테스트가 파일 == `AGENT_DIALOGUE_SQL`을
  그대로 비교했다(지금은 그 역할이 `20261004030000`으로 넘어갔다). 라이브 DB에는 2026-10-05에 적용됐다(위 커뮤니티 절).
