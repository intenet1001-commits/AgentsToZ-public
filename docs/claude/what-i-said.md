# 내가 한 말(What I Said)

## 개인 프로필과의 경계

사람이 확인한 선호는 [내 프로필](../user-profile.md)의 전용 로컬 정본 하나에 둔다. What I Said의
프로젝트별 암호화 DB나 OPS 운영 기억에 섞지 않는다. 첫 구현은 직접 작성·확인·수정·사용 중지이며
원문 자동 분석·복사·AI 추론 저장을 하지 않는다. 장기기억과 원문 화면의 이동만 연결한다.
`recall_user_profile`의 활성 선호와 `recall_user_memory`의 과거 지시는 다른 근거이고 현재 지시가 우선한다.
개인 계정 바인딩을 검증하기 전에는 service-role 연결이나 OPS profileId를 사람의 정체성으로 사용하지 않는다.

> CLAUDE.md에서 옮긴 상세 노트다(2026-10-24, 원문 그대로 · 제목 수준만 한 단계 올림). 이 영역의 코드를 고치기 전에 읽는다.
> 새 결정·함정은 이 파일에 적고, CLAUDE.md에는 색인 한 줄(필요하면 절대 규칙 한 줄)만 더한다. 「위/아래 절」이라는 말은 옮기기 전 CLAUDE.md 안의 위치를 가리킬 수 있다 — 색인에서 찾을 것.

## What I Said — 비싼 것은 검색이 아니라 프로젝트 열거였다

`registeredWhatISaidProjects()`가 memoryId마다 `resolveRegisteredProjectMemory`를 부르고, 그 안에서
**등록된 모든 후보 경로마다** `detectProjectMemory`(git 2회 spawn)를 돌린다. 실측 138행/95별칭/41
lineage 기기에서 **한 번의 호출이 3,908회 spawn**이었고, `Bun.spawnSync`는 양보하지 않으므로 단일
스레드 API 서버 전체가 그동안 멎었다.

| 경로 | 개선 전 | 개선 후 |
|---|---|---|
| 「모든 프로젝트」 라이브러리 | **51.9s** | 2.2s(cold) / 0.8s(warm) |
| 외부 앱 feed(서명 요청) | **50.2s**(90s `idleTimeout`에 소켓 끊김) | 1.49s / 0.10s |

- 해결은 열거를 **identity 전용 비동기 캐시**로 바꾼 것이다(`src/projectMemoryIdentityCache.ts` —
  async git·동시 4개·in-flight 공유·TTL). What-I-Said는 60초, 장기기억 resolve 계열
  (`resolve-project`·`open/refresh-resolved`·`dispatch-worker`·`project-route`·`thread/*`·`memory-ids`)은
  `registeredProjectMemoryRootResolver`로 **5초**다. 음수 결과도 캐시해야 한다
  (95개 별칭 중 41개만 초기화돼 있어, 실패를 캐시 안 하면 절반밖에 못 줄인다).
  resolve 계열은 열거만 캐시하고 **골라낸 루트 하나에는 전체 detect를 다시 돈다**(쓰기 게이트는 신선한 판정).
  메모리를 만드는 경로는 `initializeProjectMemory` 래퍼가 두 캐시를 함께 비운다.
- ⚠️ **`detectProjectMemory`(전체 detect)를 전역으로 캐시하지 말 것** — 「세션 기억하기 필요」 배지가
  이 결과를 폴링하므로 배지가 늦어진다. `/api/project-memory/detect`는 여전히 캐시하지 않는다.
  유일한 예외는 프로젝트 패널의 `/api/project-memory/panel-status`(`scope: 'local'`) 스냅샷이고,
  지연을 **묶어 둔** 형태다: 2초 안은 공유, 60초까지는 이전 답을 `stale: true`로 즉시 주고 백그라운드에서
  한 번 다시 detect, 패널은 stale을 받으면 1.5초 뒤 한 번 더 읽는다(`src/projectMemoryPanelStatus.ts`).
- ⚠️ 파괴적 경로(`survivingRegisteredWhatISaidLineage` 등 소스 해지 범위 검사)는 **캐시를 쓰지 않는다** —
  신선한 `detectProjectMemoryIdentitySync`/`detectProjectMemory`만 쓴다.
- What-I-Said 해석 캐시는 별도로 5초다(`WHAT_I_SAID_PROJECT_RESOLUTION_CACHE_MS`); 감지 메모 60초는
  `WHAT_I_SAID_MEMORY_DETECT_TTL_MS`다.
- ⚠️ 사용자는 "검색 때문에 느린 것 같다"고 지목했지만 **검색은 원인이 아니었다**(입력은 서버 작업
  0회, 제출 때만 조회). 지목된 곳이 아니라 측정된 곳을 고칠 것.
- `configure-all`은 preflight와 apply가 각각 열거해 **두 번** 쓸었다. preflight가 목록을 돌려주고
  apply가 그것을 받는다(`options.projects`) — reconcile 경로는 preflight가 없으므로 optional 유지.

## What I Said — 원격은 기다리지 않는다 (로컬 먼저 · 차단기 · 적재 게이트)

라이브러리는 매 요청 Supabase 왕복(범위 순회·제외 목록·목록 RPC, 각 8초 타임아웃)을 먼저 기다렸고,
15초 순환 수집은 새로 담은 것이 없어도 매번 원격 적재(제외 목록·커서·정리 RPC)를 했다. 장애 중에는
둘 다 쉬지 않고 두드렸다. 상태 기계의 정본은 `src/whatISaidRemoteThrottle.ts` 한 곳이다.

- **목록은 로컬 먼저.** 패널이 `source: 'local'`로 이 Mac 기록 한 페이지를 바로 그리고, 이어서
  `source: 'remote'`로 공유 기록을 읽어 교체한다(`loadWhatISaidLibraryLocalFirst`). 응답의
  `localFirst: true`가 있을 때만 두 번째 요청을 한다 — 옛 sidecar는 `source`를 무시하고 원격 우선으로
  답하므로 두 번 물으면 느린 왕복만 두 배가 된다. 기본값 `auto`(외부 호출자·프롬프트 가이드)는 예전처럼
  원격 우선이다. 「더 불러오기」는 **지금 보이는 목록의 출처**로 이어 읽는다(커서 형식이 다르다) —
  그 출처는 ref(`listSourceRef`)에 둔다. state로 두면 `loadPrompts`가 바뀌어 목록 전체를 다시 읽는다.
- **차단기**(`WhatISaidRemoteBreaker`, 15초에서 두 배씩 최대 10분)를 목록·`remote/status`·순환 적재가
  **함께** 본다. 열려 있으면 `auto`는 원격을 부르지 않고 로컬로 답하며 `remoteDegraded`/`remoteRetryAt`을
  싣고, `remote`는 즉시 503 `WHAT_I_SAID_REMOTE_DEGRADED`다. 사용자가 누른 「동기화」만 차단기를 무시한다.
  ⚠️ **차단기는 원격 실패만 연다.** 적재 중 로컬 저장소 읽기·복호화·레닥션 실패(`WhatISaidLocalPushError`
  → `localFailure`)로 열면, 저장소 하나의 문제가 라이브러리 전체를 「Supabase가 응답하지 않는다」로
  거짓 보고한다. 연결 대상(URL·키)이 바뀌면 차단·캐시·게이트를 모두 비운다(`noteWhatISaidRemoteTarget`).
- 원격 새로고침 중에는 「더 불러오기」를 **숨긴다.** 로컬 커서로 이어 읽으면 요청 번호가 바뀌어 원격
  새로고침이 버려지고, 다른 기기 기록이 빠진 목록이 안내 없이 남는다.
- **제외 목록·클라우드 범위는 60초 캐시**다. 이 기기의 제외·삭제·새 장기기억 적재가 무효화한다. 다른 Mac의
  제외는 최대 60초 늦게 보이지만, 목록 RPC와 적재 트리거가 **DB에서** 제외를 강제하므로 그 사이에도
  제외된 행이 보이거나 올라가지 않는다. 실패는 캐시하지 않는다(적재의 fail-closed 유지).
- **순환 적재 게이트**: 새로 저장한 행이 없고 로컬 최대 seq(`probeWhatISaidMaxSeqReadOnly`, 키·쓰기 잠금
  없이 읽는다)가 마지막으로 올린 지점을 넘지 않았으면 원격 적재를 시작하지 않는다. 한 시간에 한 번은
  확인하고, 실패하면 기억을 지워 다음 기회에 다시 올린다. 만료 정리 RPC도 한 시간에 한 번이다.
  적재가 페이지 상한(200×200행)에서 멈추면(`complete: false`) "여기까지 올렸다"로 기록하지 않는다 —
  기록하면 남은 분이 확인 주기(1시간)까지 멈춘다.
- ⚠️ **원격 검색 인덱스는 마이그레이션만 있고 적용되지 않았다**
  (`20260925020000_what_i_said_trigram_search.sql`) — **그 뒤 적용됐다(2026-10-06 실측: `pg_trgm` 설치됨,
  `portmgr_what_i_said_prompts_body_trgm_idx` 존재).** 적용 전에는 `position()`이 인덱스를 못 써서 검색마다 전 본문을
  NFKC 정규화했다. 같은 식 `lower(normalize(body, NFKC))`에 pg_trgm GIN을 걸고 RPC를 이스케이프한 LIKE로
  바꾼다 — 식이 한 글자라도 다르면 인덱스를 못 쓴다. 인덱스 생성은 표를 쓰기 잠그므로 한가할 때 적용할 것.

## 전체 저장은 "앞으로"의 정책이다 — 과거는 명시적으로만 담는다

`applyWhatISaidGlobalCapturePolicy`는 프로젝트마다 저장소를 만들 뿐 **가져오지 않는다.** 실측 41개
저장소 중 74건이 든 1개만 비어 있지 않았고, 나머지 40개는 "아직 수집된 프롬프트가 없습니다"로 떠서
기능이 고장 난 것처럼 읽혔다.

- 빈 상태는 **셋**이다: 필터 결과 없음 / 아직 수집 전 / 정말 없음. 둘로 뭉치면 방금 켠 사용자가
  고장으로 읽는다. 라이브러리 제목 옆의 저장 건수(`what-i-said-stored-count`)가 그것을 자명하게 한다.
- 과거로 거슬러 담는 것은 **`backfill: true`뿐**이고 사용자 확인을 받는다. 켠 순간이 곧 동의 시점이라,
  정책 토글의 부수효과로 과거 대화를 담으면 안 된다.
- ⚠️ **backfill은 시간 하한만 낮춰서는 동작하지 않는다.** 파일마다 일반 수집 커서가 EOF에 있을 수
  있으므로 명시적 `backfill`은 별도의 내구성 커서로 처음에는 0바이트부터 읽고, 예산 소진이나 중단 뒤
  사용자가 다시 요청하면 그 위치에서 이어 읽는다. 일반 수집이 이 커서를 이어 읽어 동의 전 기록을
  가져와서는 안 된다. 파일 교체·덮어쓰기는 일반 수집과 공유하는 이벤트 세대를 갱신하며, 저장은
  라인별 안정 event id로 중복을 막는다. 한 요청의 예산이 소진되면 완료로 보고하지 않는다.
- 명시 동의 요청은 프로세스 안에서만 예산 단위로 최대 32회 이어가고, 15초 경과는 실행 경계에서
  협조적으로 검사한다. 파일 열거·개별 파일 I/O·DB 작업은 중간에 중단하지 않으므로 엄격한 시간 상한은
  아니다. 공유 연결을 구성한 호스트는 각 회차 앞에서 캐시를 우회해 공유 정책을 확인하며 연결 실패 시
  중단한다. 공유 연결을 전혀 구성하지 않은 로컬 전용 호스트는 로컬 동의를 사용한다. 로컬 동의 시각이나
  보존 기간이 바뀌면 중단한다. 한도에 도달하거나 오류가 나면 미완료를 표시하며 새 동의 요청으로
  이어간다. 프로세스 재시작 뒤 자동 수집은 동의 전 범위를 재개하지 않는다. 보존 기간이 바뀐 뒤의
  명시 요청은 기간 변경 전에 만료로 건너뛴 행을 다시 판정한다.
- 작은 예산으로 여러 번 재개할 때 앞 파일만 반복하지 않도록 Claude·Codex의 백필 전용 순회 위치와
  완료 범위를 각각 보관한다. 파일 목록이나 보존 기간이 바뀌면 순회 완료 범위는 다시 계산하되 시작
  위치는 유지한다. 각 파일은 방문 순간의 크기와 내용을 기준으로 읽는다. 완료 직전 목록·크기·수정
  시각 등을 회차 시작 때와 다시 비교하고 달라졌으면 해당 순회를 미완료로 표시하며 다음 회차에 다시
  확인한다. 계속 바뀌는 파일이 있어도 다른 파일은 순환해 읽는다. 다른 프로젝트로 확인된 Codex 파일은
  본문의 append 대신 파일 정체성과 소유권 헤더를 비교하므로 단순 append가 완료를 막지 않는다. 헤더가
  불완전하거나 256KiB보다 길어 소유권을 판단하지 못하면 전체 메타데이터를 보수적으로 비교한다. 헤더
  확인에 쓴 바이트도 기존 수집 예산에 포함되며 구성·검증의 누적 해시와 페이지 위치를 보관해 여러
  요청에 걸쳐 이어간다. 한 헤더·앵커·행 자체가 선택한 예산에 들어가지 않으면 예산 부족으로 중단한다
  (Claude 파일도 Codex와 같이 보고한다).
  최종 검증은 여러 회차로 나뉘어도 이어간다. ⚠️ 2026-10-28 이전에는 검증을 읽기 뒤 남은 예산으로 시작해
  넘치면 「검증 불확실」로 멈추고 다음 요청이 0바이트를 읽고 기준선부터 다시 시작했다 — Codex 첫 줄 헤더
  합계가 예산의 절반쯤을 넘으면(이 Mac 실측 257개·5.2MiB, 기본 8MiB) 완료에 영영 닿지 못했다. 지금 규칙:
  ① 같은 요청의 다음 회차(`backfillContinuation`, 러너의 `pass > 0`)는 저장된 검증 위치에서 무조건 이어간다 —
  한 요청 안(15초)의 여러 회차는 느린 한 페이지와 같다. ② 새 요청은 이미 검사한 파일들의 전체 메타데이터
  사슬(dev·ino·크기·수정·생성 시각, lstat만, 예산 없음)이 검사 당시와 같을 때만 이어가고, 다르면 **같은
  기준선**에 대해 첫 파일부터 다시 검증한다(읽기를 반복하지 않는다). 검증 완료(`d`) 상태도 같은 규칙으로
  새 요청에서 다시 확인한다. 기준선과 다르면 순회를 다시 시작한다. 그래서 수집기는 더 이상 검증 불확실을
  보고하지 않고(필드와 소비자는 남겨 둔다), 한 요청 안의 검증 창은 최대 요청 시간만큼 넓다 — 그 사이 이미
  검사한 파일에 오래된 날짜로 덧붙거나 덮어쓴 내용은 아래와 같이 다음 명시 요청에 의존한다. 메타데이터 확인은 단일 시점 원자적
  스냅샷이 아니며 확인 직후 추가된 내용이나 크기·시각을 보존한 덮어쓰기는 다음 수집에 의존한다.
  기존 일반 수집의 발견 커서는 공유하지 않는다.
- **한 요청의 시간 한도 (2026-10-28).** 데스크톱 패널은 관리 프록시(`src-tauri/src/lib.rs`의 읽기 타임아웃
  35초)를 거쳐 `/sync`를 부른다. 여러 장기기억을 순서대로 15초 + 업로드씩 돌리면 그 한도를 넘어 패널이 전송
  실패만 받았다. 이제 `/sync`의 장기기억들은 **하나의 20초 기한**을 나눠 쓴다(`runWhatISaidSyncBatch`,
  `src/whatISaidExplicitBackfill.ts`): 수집은 기한 4초 전까지, 업로드는 기한까지(페이지 사이에서 멈추고 원격
  커서부터 이어 올린다), 다음 장기기억은 수집 시간이 3초 이상 남을 때만 시작한다. 첫 장기기억은 항상 돈다.
  시작하지 못한 장기기억은 `WHAT_I_SAID_SYNC_DEFERRED` 항목과 응답의 `continuation.memoryIds`로 돌려주고,
  패널은 **시작하지 못한 것만** 같은 확인 안에서 이어 보낸다(`syncWhatISaidAcrossRequests`). 끝나지 않은
  가져오기는 자동으로 다시 보내지 않는다 — 사용자가 다시 요청한다. 요청 연결이 끊겨 첫 회차 전에 멈춘
  장기기억을 「저장을 먼저 켜세요」로 잘못 보고하지 않는다.
  **업로드의 대기도 기한에서 끝난다**(검토 2026-10-28로 바로잡음). 예전에는 업로드 직전에 기한을 한 번만 봤고,
  그 뒤 같은 장기기억의 변경 큐(제한 없음)와 전역 `what-i-said-remote.lock`(약 30초)을 기다렸다. 앞 요청이
  기한에 걸려 남긴 밀린 분을 백그라운드 업로드(기한 없음, 최대 200페이지)가 잠금을 쥐고 올리는 동안 다음
  장기기억의 업로드가 그 잠금을 기다리면 응답이 35초를 넘었다. 지금은 `pushWhatISaidRemoteBefore`가 큐 대기
  (`WhatISaidRemoteMutationLock.run`의 `waitUntil`)와 잠금 대기(`whatISaidRemoteFileLockAttempts`)를 기한에서
  끝내고, 기한이 지나면 원격 커서를 읽기 전에 멈추며(`notStarted`), 한 시간에 한 번 하는 정리 RPC도 부르지
  않는다. 시작하지 못한 업로드는 결과를 기록하지 않는다 — 게이트가 밀린 분으로 계속 본다. 기한 없는 백그라운드
  업로드와 삭제는 예전처럼 약 30초 기다린다. ⚠️ 엄격한 상한은 아직 아니다: 기한 전에 시작한 수집 회차 하나와
  이미 시작한 원격 호출(정책·제외 목록 읽기는 보통 캐시, 커서 읽기, 첫 페이지 — 각각 8초 제한)은 끊지 않는다.
  남은 15초가 그 꼬리의 여유이고, Supabase가 멈춘 듯 느리면 넘을 수 있다(그때 패널은 전송 실패를 본다).
  끊으려면 중단 가능한 원격 클라이언트가 필요하다.
- `/capture`의 명시 가져오기도 같은 기한을 쓰고, 회차마다 업로드하지 않는다(예전에는 최대 32회, 기한 밖).
  요청 끝에 게이트·차단기를 거친 업로드 한 번만 한다. 끝나지 않으면 `success:false`와 함께 이유 코드를 준다.
  두 경로의 코드(`whatISaidBackfillOutcome`): `WHAT_I_SAID_CAPTURE_DISABLED`·`WHAT_I_SAID_VERIFICATION_UNCERTAIN`·
  `WHAT_I_SAID_SCAN_BUDGET_TOO_SMALL`·`WHAT_I_SAID_BACKFILL_UNREADABLE`·`WHAT_I_SAID_BACKFILL_INCOMPLETE`. `/sync`
  항목은 업로드 실패를 `remoteError`로 따로 싣고(가져오기가 완료면 코드 `WHAT_I_SAID_REMOTE_PUSH_FAILED`), 기한에
  걸린 업로드는 `uploadIncomplete`다. 패널은 코드를 자기 문구(한·영)로 바꾸고 서버의 한국어 문장을 영어 화면에
  내보내지 않으며, 「다시 요청하면 이어서 진행합니다」는 이어갈 수 있는 항목이 있을 때 **한 번만** 붙인다.
  `uploadIncomplete`는 「업로드가 끝나지 않았다, 다시 동기화하면 이어 올린다」는 주장이다(검토 2026-10-28).
  시작한 업로드가 페이지 사이에서 멈췄으면 올릴 대상임이 확인된 것이라 그대로 싣는다. 시작하지 못한 업로드는
  기한이 지나 네트워크 없이 판단하므로 `whatISaidUnstartedUploadPending`
  (`src/whatISaidRemotePolicy.ts`)이 **올릴 대상임을 알 때만** 싣는다: 이 Mac에 원격 대상(Supabase 주소·키)과
  기기 ID가 있고, 캐시된 제외 목록(`WhatISaidTtlCache.peek`, 60초)이 이 장기기억을 빼지 않았고, 게이트가 밀린
  행을 배제하지 못할 때다. 제외 목록이 캐시에 없으면 주장하지 않는다 — 제외된 장기기억은 영영 올리지 않는다.
  ⚠️ Supabase를 전혀 설정하지 않은 Mac에서 명시 동기화가 클라우드 제외 목록부터 읽다 실패해 **매번**
  `WHAT_I_SAID_REMOTE_PUSH_FAILED`(`WHAT_I_SAID_EXCLUSIONS_UNAVAILABLE`)로 보였다. 지금은 제외 목록을 읽기 전에
  `whatISaidLocalOnlyConfiguration()`이면 `no-credentials`로 건너뛴다. 일부만 설정한 Mac은 그대로 실패로 보인다.
- 「지금 수집」은 전체 저장이 켜져 있어도 **누를 수 있는 것이 맞다.** 전역 정책은 앞으로의 세션 저장을
  다루고, 지금 이 순간의 대화를 담는 길은 이 버튼뿐이다. 설명은 버튼 **위**에 둔다 — 아래 두면
  모순으로 읽힌다(VOC 2026-08-31).

## 미처리 업무 조회 — 날짜 범위 기록은 「행을 읽어야」 찾는다 (2026-10-27)

- **저장 순번 정렬(2026-10-29):** `SELECT CAST(seq AS TEXT) AS seq`의 `ORDER BY seq`는 SQLite에서 문자열 별칭을 정렬한다. 자릿수가 다른 순번은 숫자 순서와 달라 페이지가 누락되거나 history가 `changed-or-out-of-order`로 멈췄다. 응답 순번은 문자열로 유지하고, 정렬은 `ORDER BY what_i_said_events.seq`로 정수 원본 컬럼을 지정한다. 최신/오래된 순서 목록·feed·구형 키 검증 순회에 같은 규칙을 적용한다. 105개 암호화 행의 양방향 페이지/feed 회귀와 실제 MCP의 human 기록 끝까지 조회로 검증한다.

- 여러 페이지의 수집 상태는 커서와 함께 누적한다. 앞 페이지에 읽을 수 없는 항목이나 수집 상태 미확인이 있으면 뒤 페이지와 마지막 최신 행 확인이 정상이어도 완전 검색으로 표시하지 않는다. `tests/user-memory-recall.test.ts`의 교차 페이지 재개 회귀로 확인한다.

`agentstoz-unfinished-work` 스킬(`src/unfinishedWorkSkill.ts`)이 `agentstoz_use_list_user_memory_history`로
기간 안의 사용자 요청을 읽는다(`src/userMemoryHistoryServer.ts`). 저장 순서(seq 내림차순)는 시간 순서가 아니다
— 과거 대화 backfill이 오래된 행에 새 seq를 준다(실측: 이 Mac의 AgentsToZ_byCS 기록 974행 중 역전 60곳).
그래서 시각으로 건너뛸 수 없고, 범위를 찾으려면 행을 읽어야 한다.

- **1.63(첫 판)은 호출당 5행만 읽었다.** 스킬 상한 10페이지로는 최신 50행(그날 약 3시간)밖에 못 봤고,
  7일 범위를 끝까지 보려면 197번 호출해야 했다. 1.64부터 한 호출이 목록을 최대 8번(100행씩, 400행·2.5초)
  읽고, 범위 안 결과만 최대 20개·12KiB까지 돌려준다. 다음 결과가 예산에 안 들어가면 **그 행 앞에서 멈추고**
  커서는 마지막으로 소비한 seq다 — 다음 호출이 그 행부터 읽으므로 빠짐도 중복도 없다.
- **출처 필터 `origin: "human"`.** 실측 7일 573행 중 402행이 출처 `unknown`이었고, 그 대부분이 Codex
  **하위 에이전트 세션의 지시문**이었다(수집된 Codex 전사 중 디스크에 남은 115개 중 107개가
  `session_meta.source.subagent`). 사람 출처만 보면 7일 171건을 11번 호출로 끝까지 읽는다(메타데이터만으로 재생, 원문 미복호화).
  걸러낸 행은 `traversal.filtered`로 센다 — 출처 증거가 없을 뿐 사용자 요청일 수 있어 「없음」으로 말하지 않는다.
  2026-10-28 재실측(이 프로젝트 정확한 루트, 최근 7일, 본문 미출력): Codex 하위 에이전트 중 **승인 검토자**
  (`source.subagent.other = "guardian"`, 89세션)의 사용자 메시지 397개가 **전부** delivery `unknown`이었다 — `unknown`
  402행의 거의 전부다. `thread_spawn`(38세션)은 사용자 메시지가 0개 추출됐고, 본 대화(8세션)는 `user-message` 138·
  `unknown` 8이었다. 즉 하위 에이전트 지시문은 `human`이 되지 않는다(사람 패스는 오염되지 않는다). 대신 `filtered`를
  부풀리고 `all` 패스를 승인 검토문으로 채운다 — 그래서 스킬은 `all` 패스에서 승인 판정 요청·하위 에이전트 지시문을
  사용자 요청으로 세지 않고 제외 수를 밝힌다. 근본 해결은 수집기 소유 판정에서 `session_meta.payload.source.subagent`를
  빼는 것이다(수집 대상 파일은 `!modifiedWithinScanWindow` 때문에 언제나 헤더를 다시 읽으므로 분류 캐시 버전은 올릴 필요가
  없다). 이미 저장된 행은 보존 기간까지 남는다. 수집기는 다른 작업 소유·편집 중이라 이 브랜치에서는 고치지 않았다.
- **커서가 누적 통계와 위치를 들고 다닌다**(HMAC 서명, 프로세스 키라 재시작하면 만료). 앞 페이지의 잘림·건너뜀·
  순서 이상도 끝 페이지의 `complete`를 거짓으로 만든다. seq가 거꾸로 가거나 커서가 전진하지 않으면 커서를
  내지 않고 `changed-or-out-of-order`로 멈춘다(무한 반복 방지).
- ⚠️ **조회 도중 수집된 행.** seq는 AUTOINCREMENT라 새 행(backfill로 들어온 옛 날짜 프롬프트 포함)은 언제나
  이미 읽은 행보다 위에 생기고, 커서는 아래로만 간다. 첫 판은 그 행을 못 본 채 `complete: true`를 낼 수
  있었다(독립 검토가 재현). 지금은 한 구간을 다 읽으면 맨 위를 1행 확인하고, 읽은 최고 seq보다 새 행이 있으면
  그 seq를 하한으로 한 **다음 구간**을 읽는다. 완료는 「마지막 확인 시점까지」의 판정이다.
- **확인 때 본 최상단 행을 그 구간에서 못 읽었을 때**는 맨 위를 다시 1행 확인한다. 그 행이 사라졌으면(삭제)
  이어서 끝내거나 더 새 행으로 다음 구간을 읽고, 아직 목록에 있는데 못 읽었으면 `changed-or-out-of-order`로
  멈춘다. 첫 판정은 삭제만으로도 멈춰 기간 전체를 다시 읽게 했다(2차 독립 검토의 퍼즈에서 시드당 2회).
  그래도 멈추면 스킬은 그 기간을 처음부터 한 번 다시 읽는다.
- **보존·소스 변경 감지(2026-10-29).** 설정 revision과 소스 scope를 커서에 결속한다. 보존 기간을
  A→B→A로 바꿔도 revision이 달라져 `changed-or-out-of-order`로 재시작을 요구한다. 목록 읽기 전후의 revision도
  비교한다. 읽는 속도보다 빨리 수집되면 새 구간이 계속 생길 수 있으며, 호출마다 전진하고 `more-pages`를 남긴다.
  스킬은 12페이지/15초 배치를 유지하며 사용자가 끝까지 조회를 요청하면 다음 유한 배치로 계속한다.
- `complete`는 `incomplete` 사유 목록이 비었을 때만 참이다(`USER_MEMORY_HISTORY_INCOMPLETE_REASONS`).
  v7 이전 저장소에는 영속 수집 근거가 없어 `collection-unknown`이 남는다. 이는 누락의 증명이 아니다.
  v7 수집기는 시작 시 이전 receipt를 무효화하고, 최종 cursor CAS까지 끝난 결과만 정책 epoch·시도 ID·소스 scope와
  함께 저장한다. 중단·예산 초과·읽기 실패·보류 기록은 완료가 아니다. 재시작은 정상 receipt를 지우지 않는다.
  읽기 전용 probe는 DB·키를 만들거나 마이그레이션하지 않는다. v6→v7은 정상 저장소 작업 때 원본 행을 유지하며
  완료를 추정하지 않고 시작한다. 구버전은 새 schema를 거절하므로 데이터의 역마이그레이션은 하지 않는다.
- 이어 읽을 때 `origin`을 생략하면 커서의 것을 쓴다(다른 값을 주면 거절). 형식이 깨진 커서와 만료·위조·다른 조건의
  커서는 모두 `USER_MEMORY_CURSOR_EXPIRED`, 잘못된 기간은 `USER_MEMORY_RANGE_INVALID` — 스킬은 앞의 것만
  기간 처음부터 한 번 다시 읽는다(커서 없이 멈춘 `changed-or-out-of-order`도 같다).

## 날짜 범위 조회의 긴 본문과 수집 근거 (2026-10-29)

- MCP 1.69 / unfinished-work 스킬 v4는 2KiB JSON 이스케이프 예산을 **잘림이 없는 조각**으로 사용한다.
  긴 요청은 같은 id와 `textPart {offset,nextOffset,totalChars,sha256}`로 이어진다. offset은 UTF-16 문자열 인덱스이고
  sha256은 완성 본문의 UTF-8 해시다. 끝 조각까지 순서대로 합친 뒤 요청을 세고 중복 제거한다.
  `traversal.returned`는 완성된 요청 수이며 조각 수가 아니다. `excerptTruncated:false`가 중간 조각의 완성을 뜻하지 않는다.
- 기존 400행·목록8회·20개 hit/조각·hit JSON 12KiB·2.5초 제한을 유지한다. 커서는 본문 대신 행 해시와 offset만
  담는다. 조각을 전부 내보낼 때까지 seq를 소비하지 않고, 다음 호출은 그 seq를 직접 다시 읽는다. 중간에 신규 수집이
  생겨도 조각의 행을 놓치지 않으며, 같은 행의 본문·출처·시각 변경이나 삭제는 완료를 막는다.
- 64KiB 최대 요청, JSON 제어문자, 한글·이모지 복원, 조각 중 변경·삭제, 정책 변경, 다른 프로세스의 receipt 읽기와
  실제 API/MCP 재시작을 각각 `user-memory-history-body`, `what-i-said-collection-receipt`, `control-profile-api` 회귀로 검사한다.
- 명시적인 로컬 재수집은 관리 capability 경로 `/api/what-i-said/capture`의 `localOnly:true`로 원격 push 없이 실행할 수 있다.
  기존 수집 동의 이후 범위를 유지하고 backfill을 암묵적으로 켜지 않는다. MCP의 읽기 경로는 수집을 실행하지 않는다.
- `complete:true`는 해당 기기에 이미 수집된 Claude/Codex 기록 순회와 유효한 수집 근거에 관한 판정이다. 다른 기기·
  미동의 기간·Hermes/agy까지 모든 대화를 수집했다는 뜻은 아니며 `coverage.historical`은 계속 unknown이다.
  receipt는 **가장 최근 수집 실행**의 근거다. 과거 보류 영수증은 지우거나 재분류하지 않고 `coverage.historicalWithheld`로
  누적 수를 공개한다. 잘못된 형식·크기 초과 전사 줄의 수이며, 전부 사람의 요청이거나 현재 조회 기간의 누락이라는 뜻은 아니다.
  스킬은 이 값이 있으면 함께 밝히며 `complete:true`를 과거 수집 전체의 보장으로 설명하지 않는다.

## 기간 종료와 수집 영수증 (2026-10-29)

- 저장 행 순회가 끝나고 마지막 수집이 성공했더라도, 영수증의 `scannedThrough`가 조회 종료보다 이르면 그 이후의 수집은 확인되지 않는다. 이때 `complete:false`, `collection-outdated`, `coverage.endBoundary:unconfirmed`를 반환한다. 이는 누락된 요청이 있다는 뜻이 아니다. 종료와 같거나 이후인 유효한 영수증만 종료 경계를 확인하며, 누락·잘못된 시각과 구형 호스트의 미제공은 `collection-unknown`이다.
- 순회 중 확인한 이전 페이지의 경계 미확인은 서명된 커서에 보존한다. 나중 페이지에서 영수증이 새로워져도 그 순회는 완료로 바꾸지 않는다. 통상 수집이 뒤에 완료되면 사용자가 원할 때 전체 기간을 다시 조회하며, 조회가 수집을 자동 실행하거나 옛 보류 기록을 지우지는 않는다.
- MCP 1.70·스킬 v5는 구형 호스트가 `complete:true`를 반환해도 `scannedThrough`가 없거나 종료보다 이전이면 범위의 마지막 부분을 미확인으로 보고한다. `endBoundary:confirmed`도 마지막 경계의 증거이며 다른 기기나 과거 모든 대화의 수집 보장은 아니다.
- **조회 도중 삭제·만료(2026-10-29).** 수집 revision은 정책 epoch·기존 `index_epoch`·소스 scope를 함께 해시한다. 삭제·purge와 같은 SQLite 트랜잭션에서 `index_epoch`가 바뀌므로, 다음 페이지나 목록 읽기 전후에 바뀌면 현재 페이지의 미전달 결과를 버리고 `changed-or-out-of-order`로 중단한다. 새 수집 행은 epoch를 바꾸지 않아 기존 최상단 재탐색을 유지한다. feed 설정 등 무관한 `index_epoch` 회전도 보수적으로 중단할 수 있다.
- probe는 설정·만료 경계·영수증을 한 읽기 전용 SQLite 스냅샷에서 확인한 뒤 트랜잭션 종료 후 epoch·영수증을 다시 본다. API는 실제 목록 읽기 전후 두 probe 중 **가장 이른 유효 행 만료 시각**을 보존하고, 이력 커서는 관찰한 최솟값을 서명해 유지한다. 만료 시각이 조회 중 지나면 해당 페이지의 미전달 본문을 폐기하고 `retention-expired`로 종료한다. 만료 원문을 유지하거나 보존 정책을 늦추지 않는다. 경계 정보가 없으면 `retention-unknown`; 이는 마지막 유효성 확인 시점까지의 보수적 결과이지, 응답 이후에도 행이 변하지 않는다는 보장은 아니다.
- **벽시각 역행.** 만료돼 보이지 않던 과거 seq 행이 시계가 뒤로 움직이면서 다시 나타나면 최상단 재탐색만으로는 빠짐을 알 수 없다. 서명된 커서는 마지막 관측 벽시각을 보존하고, API는 전후 probe 및 실제 목록 읽기 시각을 차례로 비교한다. 관측된 역행은 미전달 페이지를 폐기하고 `clock-reversed`로 중단하며, 구형 호스트처럼 관측이 없으면 `clock-unknown`이다. 관측 사이에 발생하고 완전히 복구된 시계 변경까지 감시한다는 보장은 없다.

## Claude 도구 결과와 슬래시 명령 (2026-10-30)

- Claude Code는 **도구 결과**(`content`가 `tool_result` 블록뿐인 배열)와 하네스 주입 문맥(isMeta + text 배열 — 스킬 본문 등)도
  `type:"user"` 행으로 쓴다. 예전 수집기는 문자열 아닌 content를 전부 `record-malformed` 영수증으로 남겨, Claude 세션이 이
  프로젝트에서 일하는 동안 마지막 수집 영수증이 항상 `withheld>0` → 이력 조회 `collection-partial`이었다(v1570 실측: 7일 malformed
  673건, 도구 결과 1126행/8일). 이 두 모양은 이제 영수증 없이 건너뛴다. **텍스트가 섞인 비-meta 배열**(이미지 붙인 프롬프트)과
  시각이 깨진 행은 사람 요청일 수 있으므로 계속 영수증이다 — 이미지 프롬프트의 글자는 아직 수집하지 않는다(8일 실측 2건).
- 사람이 친 `/명령 인자`는 `<command-message>/<command-name>/<command-args>` 래퍼로만 남는데, 공용 발췌기가 래퍼를 호스트 표식으로
  보고 **영수증도 없이** 버려 `complete:true`가 사람 요청 누락을 숨겼다(`/agentstoz-unfinished-work …` 실제 1건). 수집기만
  (`claudeTypedCommandExcerpt`) 인자가 있는 비-meta·비-sidechain 명령을 `/이름 인자` 그대로 저장한다. 인자 없는 명령(`/clear`),
  모델이 부른 스킬(isMeta, 이름에 `/` 없음), 래퍼 밖 글자나 태그 중복이 있는 행은 예전처럼 건너뛴다. 세션 맥락 렌더링
  (`extractOwnedClaudeSessionExcerpts`·`sessionTranscriptStream`)은 바꾸지 않았다. 커서가 이미 지난 과거 명령은 소급 수집되지 않는다.
